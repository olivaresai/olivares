ここを始める前に、[最初の 1 時間](/ja/how-to/first-hour/) を完了してください。
ツールはエンジンのホスト上で実行されます。Compose インストールではコンテナ内も含みます。
クライアント端末のログインやフォルダーは、そこに自動的には利用できません。

## 接続方法を選ぶ

**AI ツール**（`/agent-tools`）は、ツールをインストールし、ツール自身のログインフローを実行します。
ネイティブエンジンでは、既定のツールインスタンスはエンジンユーザー自身のログインを使います。
Olivares を通じてサインインしたアカウントは、別のインスタンスとして残ります。使用するアカウントを選択してください。
アカウントのスナップショットには、ツールが報告するメールアドレス、プラン、使用量の期間、モデルが表示されます。
欠けている値は利用できないままとなり、失敗した更新は古いものとしてマークされます。

**ツール**（`/agent-tools`）の **API キー** には、API キーとローカルモデルのエンドポイントが保持されます。
そこでプロバイダーを追加してテストし、その後 **新しいセッション** から使います。プロバイダーキーと
ツールのサブスクリプションは、接続するための異なる方法です。Ollama には、到達可能なエンドポイントと
モデルが必要で、API キーは不要です。[プロバイダーを追加する](/ja/how-to/add-a-provider/) を参照してください。

プロバイダーを指定しない `managed_injection` の Claude プロファイルでは、
`OLIVARES_SESSION_RUNTIME_WIF` または `OLIVARES_SESSION_RUNTIME_TOKEN_FILE` がホスト全体の
推論資格情報を提供します。プロバイダーのレコードに紐づいたプロファイルは、代わりにそのレコードを使います。
その資格情報を開けない場合、ホストの資格情報に戻らず、起動は拒否されます。`provider_account_home` の
プロファイルは、認可されたツールのログインを使い、どちらの変数も必要ありません。
[環境変数が適用される場所](/ja/how-to/add-a-provider/#環境変数とそれが今も効く場所) を参照してください。

## 開始と会話

**セッション → 新しいセッション** を開き、準備ができたツールを選びます。エンジンがプロファイルとフォルダーを入力します。
README の Compose インストールでは、**フォルダーを変更** を選び、`/project` と入力して、マウントされたホストの
プロジェクトで作業します。既定のフォルダーのままにする場合、パスを入力する必要はありません。**First message**
は空のまま開始し、その後会話で入力するか、**開始** を押す前に入力してください。

プロバイダーキーを使うツールは、保存されたモデルを使うか、接続テストが返したモデルを選択できます。
モデルが必要なのにテストがモデルを返していない場合は、先に **ツール** の **API キー** で接続をテストしてください。
Claude Code はネイティブの既定モデルを使えます。

README の Compose インストールでは、CLI をエンジンのコンテナ内で実行します。CLI はそこでローカルの
エンジンとその証明書を見つけます。ツールのサブスクリプションではなく、セットアップ中に作成した
Olivares の管理者アカウントでサインインしてください。

Codex のように、モデルを必要とするツールでプロバイダーキーを使う場合は、下の `session start` を実行する前に、
**ツール** の **API キー** で既定値を保存してください。プロバイダーにもツールのプロファイルにも
設定済みのモデルがない場合は、`session start` コマンドに `--model <tested-model-id>` を追加し、
プレースホルダーを接続テストが返したモデル ID に置き換えてください。**新しいセッション** で選択した
モデルは、そのコンソールからの起動にのみ適用されます。CLI からの起動のモデルは設定されません。

ホストのターミナルで、Compose ファイルを一度設定します:

```sh
export COMPOSE_FILE="$HOME/olivares/deploy/compose/docker-compose.yml"
docker compose exec olivares olivares login
docker compose exec olivares olivares tool ls
docker compose exec olivares olivares tool providers
docker compose exec olivares olivares session start /project --name first-hour
docker compose exec olivares olivares session send first-hour "Explain this project."
```

ネイティブインストールでは、同じ Olivares コマンドをエンジンのホストで直接実行し、`/project` をプロジェクトの
パスに置き換えてください。クライアントは、選んだツールと接続を表示します。複数のツールがある場合は、`--tool`
で 1 つを選択します。`--profile` は既存のプロファイルを選択します。クライアントのターミナルを閉じても、
セッションはエンジン上で実行され続けます。その出力に再接続するには:

```sh
docker compose exec olivares olivares session follow first-hour
```

## 承認、中断、停止、再開

**その他のオプション** の下の **操作ごとに確認** を選ぶと、ツールは操作の前に確認を求めます。**ルール** では、
あなたの対応を待っているリクエストが、キューの横に、そのコマンド、影響範囲、要求したルールとともに開いて表示されます。
**今回だけ承認**（`A`）を選ぶか、**拒否**（`D`）を選んでメモを追加します。組織の承認を必要とする起動も同様に、
そこで待機します。起動が承認されたら、メッセージを送ってください。

現在のターンを終了しつつ会話を開いたままにするには **中断** を使います。プロセスを終了するには **停止** を使います。
求められた場合は確定してください。**再開** は、同じプロファイル、アカウント、フォルダーで同じセッションを再起動し、
資格情報とポリシーを再確認します。再開後に新しいメッセージを送ってください。

```sh
docker compose exec olivares olivares session interrupt first-hour
docker compose exec olivares olivares session stop first-hour
docker compose exec olivares olivares session resume first-hour
docker compose exec olivares olivares session send first-hour "Continue explaining this project."
```

アカウントが変更されたか利用できない場合は、起動が拒否されます。別のログインへの切り替えは許可されません。
中断された Grok のターンは、確認応答のない ACP キャンセルを使います。終了したとみなす前に、
相関付けられたターンの結果を待ってください。

## 任意のプロファイルと git の設定

設定済みのツールホームが既にある場合、**セッション** の **プロバイダープロファイル** タブ
（`/sessions?tab=profiles`）で、管理者はプロファイルを登録し、起動の準備状況を確認できます。
名前付きアカウントのプロファイルとソースのバインドは、**ツール** のそのアカウントの詳細にもあります。
ホームは実行ホスト上に存在している必要があります。そのプロファイルを選ぶには、**新しいセッション** で
**その他のオプション → 詳細な起動オプション** を使います。バイナリの上書きでは実行ファイルを選びます。
それ以外の場合、エンジンは検証済みの最新の管理対象インストールを試し、次に `PATH` 上のツールを試します。
[設定](/reference/configuration/) を参照してください。

コミットが 1 つ以上ある git リポジトリのトップフォルダーでは、**新しい git ワークツリーで作業する** を選ぶと、
セッション用のブランチと作業ディレクトリが作成されます。再開ではこれらが再利用されます。ブランチとコミットを
含むハンドオフでは **新しいセッションのワークツリーで開く** が提示されます。そのコミットを含むリポジトリを持つ、
登録済みのフォルダーを選んでください。エンジンは、ワークツリーを作成する前に、サポートされていない、
または安全でないリポジトリ設定を拒否します。

フォルダーには、新しいワークツリー用のセットアップコマンドを 1 つ保存できます。ワークツリーの開始が
受け付けられる前に、人がその正確なテキストを SHA-256 で承認する必要があります。1 文字変更しても
再承認が必要です。承認されたコマンドは、新しいワークツリーでセッションの最初のターンの前に
1 回実行されます。失敗すると開始は停止し、その出力が表示されます。セットアップが失敗した場合、
再開時にコマンドは再実行されますが、セットアップが成功した後や記録された `--no-setup` で開始した後は再実行されません。
[フォルダーのセットアップコマンドを承認する](/ja/reference/session-runtime-api/#フォルダーのセットアップコマンドを承認する)
を参照してください。

クリーンアップは、コミットされていない作業や未マージの作業を破棄することを拒否します。**ワークツリーとブランチも破棄する**
は、その損失を明示的に許可します。無視されたファイルは、ワークツリーとともに削除されます。ワークツリーは、リポジトリの
git メタデータを共有します。ワークツリーのオプションについては
[セッション CLI リファレンス](/ja/reference/cli/#command-olivares-session-start) を、プロファイルの権限、ライフサイクル呼び出し、
分離の制限については [セッションランタイム API](/ja/reference/session-runtime-api/) を参照してください。
