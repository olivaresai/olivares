**AI コントロールタワー**とは、AI ガバナンスのための組織全体のダッシュボードと
ワークフローのレイヤーです。登録されたエージェントを一望し、承認をルーティングし、
チケットを起票し、ポスチャを経営層に報告する単一の場所です。例として
**ServiceNow AI Control Tower** や、ハイパースケーラーのエージェント管理プレーン
（Microsoft の Entra Agent ID / Agent 365 のサーフェス、AWS AgentCore のガバナンス機能）
が挙げられます。

すでにいずれかに投資しているなら、正しい問いは「タワーか Olivares か？」ではありません。
「何がタワーに真実を供給するのか？」です。私たちの答えは意図的に、**私たちは統合する、
競合しない**、というものです。

:::tip[要点]
コントロールタワーは、**ワークフロー、チケット管理、組織全体のダッシュボード、自身の
エコシステム内のエージェントのガバナンス**に強みがあります。一方で、**異種混在の
セルフホスト型マルチクラウドの estate** と、**グラウンドトゥルース**——エージェントが
実際に何に触れたかをデータプレーンと突き合わせて検証すること——には弱みがあります。
Olivares AI は**タワーの下にあるソースレイヤー**です。帰属付きのインベントリ、
Permitted-vs-Observed のドリフト、改ざん検知可能な証跡を生成し、それらを**上へ
プッシュ**します。
:::

## コントロールタワーが得意とすること

- **ワークフローと ITSM**：承認、変更記録、インシデントチケット、オーナーシップ——
  組織の既存プロセスであり、AI ガバナンスは並行したサイロを立ち上げるのではなく、
  ここに組み込まれるべきものです。
- **エグゼクティブレポート**：多数の AI イニシアチブを横断する、経営層向けの一枚の画面。
- **エコシステムネイティブのガバナンス**：ハイパースケーラーのタワーは、*そのハイパー
  スケーラーのクラウド内の*エージェント——その ID、そのポリシー、そのランタイム——を
  うまくガバナンスします。

これらは本物の強みであり、私たちはそれを再現しません。Olivares AI は ITSM 製品では
なく、CISO のレポートダッシュボードになろうともしていません。

## タワーが残すギャップ

| ギャップ | なぜ重要か | Olivares AI が提供するもの |
|---|---|---|
| **異種混在の estate** | エージェントはクラウド、オンプレ、ラップトップ、CI にまたがって動く——単一ベンダーのランタイムだけではない | SQL／オブジェクト／ウェアハウスストア、MCP、ツール、ローカルの開発エージェントを横断した estate 全体のインベントリとアクセスマップ |
| **グラウンドトゥルース** | タワーは*登録された*ものを示すが、エージェントが*実際に行ったこと*を裏付けることはほとんどない | 自己申告のテレメトリを pgAudit / CloudTrail / eBPF と突き合わせて検証——事実としての Permitted-vs-Observed |
| **開発エージェントへのエンフォースメント** | タワーは観測するが、ローカルエージェントのアクションを deny-closed で止められるものは少ない | [Claude Code フック PEP](/ja/how-to/connectors/claude-code-hooks-pep/) と deny-closed のアクチュエーションゲート |
| **改ざん検知可能な証跡** | ダッシュボードは可変だが、監査人は不変の証拠を求める | 追記専用、Ed25519 署名付きの台帳；OSCAL 証跡パッケージ；ボックス外での検証 |
| **主権（sovereignty）** | SaaS タワーはあなたのガバナンスデータを自社クラウドで処理する | セルフホスト／エアギャップ；データプレーンが境界の外に出ることはない |

## どのように組み込むか（双方向）

Olivares AI は、あなたのタワーの**下**に位置してそれに供給し、ロスター（roster）を
公開するタワーから**読み取る**ように作られています。

- **ポスチャと証跡を上へプッシュする。** コントロールタワーが取り込むためにインベントリ
  とポスチャをエクスポートし（`GET /v1/m/posture/export`）、監査台帳と検出結果を
  **SIEM/ITSM** に転送して、すでに運用しているワークフローに着地させます。
  → [監査を Splunk へ転送する](/ja/how-to/forward-audit-to-splunk/)
- **ID ロスターを下から読み取る（読み取り専用）。** ID フェデレーションコネクターは、
  **Microsoft Entra Agent ID**、**AWS AgentCore Identity**、**Google Agent Identity**
  からエージェントのロスターを同期し、**Microsoft Agent 365** と
  **ServiceNow AI Control Tower** から読み取り専用で同期します。それらを SPIFFE/WIF
  ロスターにマッピングすることで、アクセスマップはエッジを実在の、ガバナンス下にある
  ID に帰属させます。
  [Olivares AI が IdP とどう組み合わさるか](/ja/explanation/architecture/where-it-fits-with-your-idp/)を参照してください。

この関係は**設計上、相補的**です。タワーがワークフローと経営層向けのビューを所有し、
Olivares AI がグラウンドトゥルースと、タワーの数字を信頼できるものにする不変の証跡を
所有します。

## タワーで十分な場合

エージェントの estate 全体が**単一の**ハイパースケーラーや SaaS エコシステムの中に
収まっており、そのベンダーのネイティブタワーがそれをガバナンスし、かつ**主権要件も
異種混在／セルフホストのフットプリントもない**場合、別個のコントロールプレーンは
必要ないかもしれません——ネイティブタワーとその監査エクスポートでカバーできます。
Olivares AI が必要になるのは、estate が**混在している**とき、**レジストリではなく
裏付けの取れたグラウンドトゥルース**が必要なとき、または**ベンダーがホストする
コントロールプレーンをガバナンス証跡に使えない**ときです。
