El repositorio incluye un stack Compose bajo `deploy/compose/`: un despliegue
endurecido de nodo único (SQLite embebido, cero dependencias externas) más dos
overlays — un override **multi-tenant con Postgres** y un perfil de **copia de seguridad
para recuperación ante desastres**. Este tutorial te lleva desde `up -d` hasta un control
plane configurado con copias de seguridad.

El contenedor envuelve el **mismo binario único** que cualquier otra instalación; solo
difiere el empaquetado. Los comandos de abajo son los propios puntos de entrada
documentados del stack (`deploy/compose/*.yml`), y el flujo de primer arranque que conducen
es el mismo que se verifica de extremo a extremo contra el binario en el
[tutorial de nodo único](/tutorials/getting-started/single-node/).

<Aside type="caution" title="Hasta que existan las imágenes v26.9.1, compila en local">
Una versión etiquetada anterior ya publicó imágenes firmadas. El canon de este árbol es **v26.9.1**. El
testigo de superficies de instalación sigue registrando Docker Hub y GHCR como
**not-published** para `26.9.1` hasta que corra el trabajo de release de esa
etiqueta (`docs/releases/v26.9.1-install-surfaces.json`). La misma nota está en
[Desplegar con Docker](/how-to/docker-deployment/). Hasta que existan las
etiquetas `26.9.1`, compila la imagen distroless endurecida desde el código
fuente y apunta el stack a ella:

```bash
task image                                   # builds olivares:dev
echo 'OLIVARES_IMAGE=olivares:dev' >> deploy/compose/.env
```

Cuando exista la imagen `26.9.1`: establece
`OLIVARES_IMAGE=docker.io/olivaresai/olivares@sha256:<digest>` y
[verifícala](/how-to/verify-a-release/) primero — por digest, nunca un tag.
</Aside>

## 1. Levanta el stack de nodo único (SQLite)

<Steps>

1. Arráncalo:

   ```bash
   docker compose -f deploy/compose/docker-compose.yml up --wait --wait-timeout 120
   ```

   Lo que obtienes, por diseño:

   | Propiedad | Valor |
   |---|---|
   | Puertos | `8443` (HTTPS: REST + UI web), `8444` (gRPC) — publicados en **todas las interfaces del host**, porque esto es un servidor. Pon `OLIVARES_BIND=127.0.0.1` en `.env` para restringirlos al host |
   | Datos | volumen nombrado `olivares-data` → `/var/lib/olivares` (almacén SQLite, clave de firma de auditoría, material TLS) |
   | Endurecimiento | corre como `65532:65532`, root de solo lectura, todas las capabilities descartadas, `no-new-privileges`, tmpfs `/tmp` |
   | Healthcheck | ejecución directa de `olivares readyz` dentro del binario — sin shell, curl ni wget. Sólo un HTTP 200 de `/readyz` local es saludable |

2. Pregunta al motor dónde está, y lee el token de configuración de un solo uso de los logs:

   ```bash
   # where the console answers, and whether setup is still pending. The image is
   # distroless: `docker exec … bash` has nothing to run, this needs no shell.
   docker compose -f deploy/compose/docker-compose.yml exec olivares olivares first-boot

   # the one-time setup token, printed once at first boot
   docker compose -f deploy/compose/docker-compose.yml logs olivares \
     | sed -n '/FIRST-BOOT SETUP/,/========================/p'
   ```

3. Crea el primer administrador, inicia sesión, y crea tu organización —
   exactamente como en el [tutorial de nodo único](/tutorials/getting-started/single-node/#3-claim-the-one-time-setup-token)
   (la API es la misma; el certificado TLS es autofirmado en el primer arranque, así que
   `curl -k` para el bootstrap):

   ```bash
   curl -ksf -X POST https://localhost:8443/v1/setup \
     -H 'Content-Type: application/json' \
     -d '{"token":"<olst_ token>","email":"you@example.com","password":"<strong-password>"}'
   ```

</Steps>

<Aside type="tip" title="¿Te perdiste el token?">
Un reinicio no lo vuelve a imprimir (solo se almacena su hash). Mientras no exista ningún
administrador, acuña uno de repuesto sin reiniciar nada — el motor en marcha lo acepta al
instante y el token anterior deja de funcionar:

```bash
docker compose -f deploy/compose/docker-compose.yml exec olivares \
  olivares first-boot --new-token
```
</Aside>

<Aside type="tip" title="Los cuatro comandos, y por qué cada uno necesita el `-f`">
El stack nombra su propio proyecto de Compose, así que el contenedor del motor es
`olivares` (no `compose-olivares-1`) y los servicios de los overrides son
`olivares-postgres-1` y `olivares-backup-1`. Compose sigue buscando un fichero compose en
el **directorio de trabajo**, y éste vive en `deploy/compose/` — así que un `docker compose
ps` a secas en la raíz del repositorio responde *"no configuration file provided"*. Pasa
`-f` siempre, o haz `export COMPOSE_FILE=deploy/compose/docker-compose.yml` una vez.

```bash
docker compose -f deploy/compose/docker-compose.yml exec olivares olivares first-boot
docker compose -f deploy/compose/docker-compose.yml logs olivares
docker compose -f deploy/compose/docker-compose.yml ps
docker compose -f deploy/compose/docker-compose.yml down
```

`olivares quickstart` es la vía del **binario local**, no ésta: aquí el servidor ya está
corriendo — el comando del contenedor es `serve` — y `quickstart` arrancaría un segundo
motor dentro del contenedor.
</Aside>


## 2. Cablea fuentes

Las fuentes se declaran en un único fichero de operador nombrado por `OLIVARES_SOURCES_CONFIG`
([conectar una fuente](/how-to/connect-a-source/)). Para el contenedor, monta el
fichero y establece la variable con un pequeño override:

```yaml
# deploy/compose/docker-compose.sources.yml (yours — not shipped)
services:
  olivares:
    environment:
      OLIVARES_SOURCES_CONFIG: /etc/olivares/sources.json
    volumes:
      - ./sources.json:/etc/olivares/sources.json:ro
```

```bash
docker compose -f deploy/compose/docker-compose.yml \
               -f deploy/compose/docker-compose.sources.yml up -d
docker compose -f deploy/compose/docker-compose.yml logs olivares | grep "ingest: wired source"
```

Recuerda que las rutas dentro de `sources.json` son rutas de **contenedor** — un tail de
log pgAudit, por ejemplo, necesita que el directorio de logs de Postgres también esté
montado de solo lectura dentro del contenedor.

## 3. Copias de seguridad DR cifradas (el perfil `backup`)

El stack incluye un servicio de copia de seguridad de un solo disparo que produce un bundle
**cifrado y con continuidad de ledger segura** (`olivares dr backup`) y poda los bundles
con más de 14 días de antigüedad:

```bash
# Write your KEK passphrase once (keep it OUT of the repo / image):
printf 'a strong DR passphrase' > deploy/compose/dr-pass

docker compose -f deploy/compose/docker-compose.yml \
               -f deploy/compose/docker-compose.backup.yml \
               --profile backup run --rm backup
```

Envuelve ese comando en el cron del host para un RPO programado, y **espeja el
volumen `olivares-backups` offsite** — una copia de seguridad en el mismo host no es
recuperación ante desastres, y la passphrase debe viajar por separado de los bundles (3-2-1).
El procedimiento completo, incluyendo el simulacro de restauración (`olivares dr verify`),
está en [copia de seguridad y restauración](/how-to/backup-and-restore/).

## 4. Opcional: el override multi-tenant con Postgres

Para la topología multi-tenant, superpón el override de Postgres. Levanta un
Postgres 16, aprovisiona el **rol de mínimo privilegio `olivares_app`** (sin
superuser, sin `BYPASSRLS` — el motor *se niega* a arrancar contra un rol privilegiado,
porque la seguridad a nivel de fila es el backstop del tenant), y apunta el
motor a él:

```bash
cp deploy/compose/.env.example deploy/compose/.env
# set POSTGRES_SUPERUSER_PASSWORD and OLIVARES_DB_PASSWORD in .env

docker compose -f deploy/compose/docker-compose.yml \
               -f deploy/compose/docker-compose.postgres.yml up -d
```

<Aside type="caution" title="El Postgres de compose es una topología de demostración">
El override conecta con `sslmode=disable` dentro de la red de compose —
correcto para evaluación, **no** para producción. Un despliegue de Postgres de producción
usa TLS con `sslmode=verify-full` y un secreto DSN — esa es la
[vía de Kubernetes/Helm](/tutorials/getting-started/kubernetes/).
</Aside>
