Le chart Helm dans `deploy/helm/olivares` déploie le control
plane avec les mêmes valeurs par défaut sécurisées que tous les autres chemins : un
**StatefulSet core** (non-root, système de fichiers racine en lecture seule, toutes
les capacités supprimées), TLS activé, exposition équivalente à la loopback (un
Service `ClusterIP` — rien de public tant que vous ne le décidez pas), et aucune
identifiant par défaut. À partir de là, vous activez à votre choix
Postgres, la **HA active-passive**, des **sauvegardes DR chiffrées** planifiées
et le **DaemonSet de collecteurs** pour l'ingestion distribuée.

Tout ce qui suit a été rendu et vérifié contre le chart de ce
dépôt (`helm lint` + `helm template`, y compris les configurations de HA et de
sauvegarde et les garde-fous propres au chart). Le chart requiert
**Kubernetes ≥ 1.25**.

<Aside type="caution" title="Statut de publication du chart — en toute honnêteté">
La release moteur v26.9.1 est publique, mais le chart a son propre cycle et aucune
publication `chart-v*` à ce jour. Installez les sources relues depuis
`deploy/helm/olivares`, comme ci-dessous, et épinglez l'image par digest. Si un chart
est publié plus tard, vérifiez cet artefact séparé avant de l'utiliser.
</Aside>

## 1. L'installation par défaut (nœud unique, SQLite)

<Steps>

1. Installez depuis le checkout :

   ```bash
   helm install olivares deploy/helm/olivares
   ```

   Cela rend exactement trois objets de charge de travail — un `StatefulSet` (1 réplique,
   SQLite sur un PVC persistant de 8 Gi), un `Service` `ClusterIP` (8443 HTTPS,
   8444 gRPC) et un `ServiceAccount` **sans aucun** privilège sur l'API Kubernetes.
   Les sondes interrogent `/readyz` (readiness — se draine quand le store est indisponible ou que la
   réplique n'est pas leader) et `/livez` (liveness — processus uniquement, jamais une
   dépendance, de sorte qu'une panne du store ne peut jamais provoquer une boucle de redémarrage).

2. Lisez le jeton de configuration à usage unique dans le log du pod (il n'est imprimé que sur stdout
   — sous Kubernetes, c'est le log du conteneur) :

   ```bash
   kubectl logs -l app.kubernetes.io/component=core | sed -n '/FIRST-BOOT SETUP/,/========================/p'
   ```

3. Faites un port-forward et terminez la configuration au premier lancement
   ([le même flux que partout](/tutorials/getting-started/single-node/#3-claim-the-one-time-setup-token)) :

   ```bash
   # The Service is named <release>-olivares-core:
   kubectl port-forward svc/olivares-core 8443:8443
   curl -ksf -X POST https://127.0.0.1:8443/v1/setup \
     -H 'Content-Type: application/json' \
     -d '{"token":"<olst_ token>","email":"you@example.com","password":"<strong-password>"}'
   ```

</Steps>

<Aside type="danger" title="N'exécutez jamais en production avec `persistence.enabled=false`">
Avec la persistance désactivée, le répertoire de données est un `emptyDir` : la **clé de signature
d'audit** et le jeton de configuration sont perdus à chaque replanification, ce qui casse définitivement
la vérifiabilité du ledger. Le défaut (`persistence.enabled=true`) est la seule posture
de production ; sauvegardez aussi la clé hors de la machine
([sauvegarde et restauration](/how-to/backup-and-restore/)).
</Aside>

Alternativement, sans aucun Helm, le dépôt fournit un manifeste plat avec
les mêmes valeurs par défaut sûres en nœud unique, régénéré depuis le chart par la CI :

```bash
kubectl apply -f deploy/manifests/install.yaml
```

Pour Argo CD / Flux / Kustomize (`kustomize build --enable-helm`), voir
`deploy/gitops/` — des wrappers déclaratifs sur ce même chart.

## 2. Postgres (multi-tenant)

Le moteur requiert un rôle de base de données à **moindre privilège** : `LOGIN`, pas de
superuser, **pas de `BYPASSRLS`** — la sécurité au niveau ligne est le filet de sécurité tenant, et
le moteur refuse de démarrer contre un rôle privilégié. Provisionnez le rôle avec
le canonique `deploy/postgres/01-app-role.sql` (le chart peut l'exécuter pour vous
en tant que Job de pré-installation), placez le DSN dans un Secret, et pointez le chart dessus :

```bash
kubectl create secret generic olivares-pg \
  --from-literal=dsn='postgres://olivares_app:***@db:5432/olivares?sslmode=verify-full' \
  --from-literal=admin-dsn='postgres://olivares_admin:***@db:5432/olivares?sslmode=verify-full'

helm install olivares deploy/helm/olivares \
  --set core.engine=postgres \
  --set postgres.dsnSecret=olivares-pg \
  --set postgres.adminDsnKey=admin-dsn
```

La clé `admin-dsn` porte un rôle `NOSUPERUSER BYPASSRLS` dédié, et sous
Postgres vous en avez besoin **dès le premier démarrage** — pas seulement
pour les sauvegardes. Le rôle applicatif ci-dessus reste
`NOSUPERUSER NOBYPASSRLS`, donc une lecture inter-tenant faite à travers lui
est limitée par la sécurité au niveau des lignes au tenant autorisé et ne
peut jamais être lue comme l'ensemble du parc ; le moteur refuse une telle
lecture au lieu de renvoyer une liste courte. Le setup de premier
démarrage de [§1](#1-linstallation-par-défaut-nœud-unique-sqlite) est l'une
de ces lectures — `POST /v1/setup` crée la première organisation — donc sans
cette clé il répond `501 cross_tenant_admin_pool_not_configured`.
`GET /readyz` répond alors `503` avec `status=setup_blocked`, le même code
et un remède fixe dans le corps. Ce 503 n'est pas un succès : c'est
l'observation que le setup ne peut pas encore s'exécuter, et
`POST /v1/setup` revérifie sa propre autorité.

Le manifeste plat livré et le chemin Helm par défaut câblent `/readyz` comme
`readinessProbe` du conteneur. Une installation PostgreSQL non initialisée
sans cette énumération autoritative reste donc Not Ready jusqu'à ce que le
prérequis soit corrigé, ce qui **peut coincer un rollout** (un pod jamais
Ready ne satisfait jamais la barrière de mise à jour du StatefulSet).
`/livez` reste 200 — processus seulement, le pod n'est pas redémarré.
`/pod-readyz` reste aussi 200 : c'est la sonde de santé de pod HA configurée
séparément (magasin joignable, sans contrôle de leadership ni sonde de
capacité de premier démarrage), utilisée avec un routage d'écrivain distinct
pour qu'un standby sain puisse être Ready pendant que `/readyz` continue de
drainer les non-écrivains. Un 200 de `/livez` ou `/pod-readyz` ne signifie
**pas** que le rollout par défaut est débloqué. Ne reconfigurez pas la sonde
de readiness par défaut pour masquer un setup en échec.

Lorsque l'état de setup ne peut pas être observé, `/readyz` répond `503`
avec `status=setup_unavailable` et `code=setup_state_unavailable`, et
**omet** `setup_required` parce que ce booléen est inconnu. C'est distinct
d'une installation vide connue (`setup_required=true`).

Une installation **déjà** configurée continue de servir sans la clé : ce
qu'elle ne peut pas faire, c'est le travail inter-tenant autoritatif — la
liste des organisations, la couverture multi-tenant et `backup`, qui
l'EXIGE (voir [§4](#4-sauvegardes-chiffrées-planifiées)). Provisionnez le
rôle avec `olivares db init --admin-role olivares_admin …` (voir
`deploy/postgres/README.md`) et pointez `--admin-dsn` vers lui.

## 3. HA active-passive

Avec Postgres comme store partagé, exécutez plusieurs répliques. L'une est élue
leader (un verrou consultatif Postgres) ; les standbys répondent à `/readyz` par
`503 {"status":"standby"}` afin que le Service ne route que vers le leader, et un
standby prend le relais automatiquement quand le leader disparaît.

Deux choses sont structurellement requises, et le chart **impose les deux** (nous
avons vérifié que les garde-fous se rendent comme des échecs durs, pas des avertissements) :

| Exigence | Pourquoi | Garde-fou du chart si absent |
|---|---|---|
| `core.engine=postgres` | Le fichier SQLite est local à un seul pod — il ne peut pas être un store partagé. | `core.replicaCount > 1 requires core.engine=postgres …` |
| `core.auditSigningKeySecret` | Chaque réplique doit signer le ledger d'audit avec la **même** clé Ed25519, sinon la chaîne de hachage bifurque au basculement. | `core.replicaCount > 1 requires core.auditSigningKeySecret …` |

```bash
kubectl create secret generic olivares-audit-key \
  --from-file=audit-signing.key=<base64-ed25519-private-key-file>

helm install olivares deploy/helm/olivares \
  --set core.engine=postgres \
  --set postgres.dsnSecret=olivares-pg \
  --set core.replicaCount=3 \
  --set core.auditSigningKeySecret=olivares-audit-key
```

Les tailles HA canoniques sont 3 ou 5 répliques, active-passive. Cette conception
à écriture unique est délibérée (elle correspond au modèle de cohérence du produit) ; les
[chiffres de production-readiness](/how-to/monitor-with-prometheus/) documentent les
paliers de disponibilité qu'elle prend en charge.

## 4. Sauvegardes chiffrées planifiées

Le chart fournit un `CronJob` qui exécute `olivares dr backup` — un bundle chiffré,
**sûr pour la continuité du ledger** (snapshot du store + clés de signature scellées sous
votre KEK + manifeste de pointe de chaîne par tenant) :

```bash
kubectl create secret generic dr-kek --from-literal=passphrase='<strong passphrase>'

helm upgrade olivares deploy/helm/olivares --reuse-values \
  --set backup.enabled=true \
  --set backup.kekSecret=dr-kek \
  --set postgres.adminDsnKey=admin-dsn   # obligatoire sous Postgres avec les sauvegardes
```

Sous Postgres, le chart **refuse de se rendre** sans `postgres.adminDsnKey` : le
`pg_dump` de la sauvegarde **avorte** s'il tourne sous le rôle applicatif contre
des tables en `FORCE ROW LEVEL SECURITY`, donc un CronJob câblé au seul DSN
applicatif **échouerait à chaque exécution** et vous laisserait **sans aucune
sauvegarde**. Le garde-fou transforme cette panne silencieuse en échec dur à
l'installation.

Valeurs par défaut : toutes les 6 heures (`backup.schedule` définit votre RPO), rétention
locale de 14 jours, un PVC de destination dédié. **Mirroitez la destination hors site et
gardez la KEK séparée des bundles** — une sauvegarde sur le même cluster n'est pas de la
reprise après sinistre. Faites des exercices de restauration avec `olivares dr verify` ; la
procédure complète est dans [sauvegarde et restauration](/how-to/backup-and-restore/).

## 5. DaemonSet de collecteurs (ingestion distribuée)

Pour la topologie distribuée, un `DaemonSet` de collecteurs exécute les connecteurs de source
sur chaque nœud et **pousse** les observations vers le core via gRPC — les collecteurs
n'ont aucun listener entrant. Le chart requiert un jeton d'ingestion et accepte
un matériel mTLS optionnel :

```bash
helm upgrade olivares deploy/helm/olivares --reuse-values \
  --set collectors.enabled=true \
  --set collectors.ingestTokenSecret=olivares-ingest-token   # ingest:write bearer token
```

Donnez leurs sources aux collecteurs via `collectors.sourcesConfig` (le même
[JSON de sources](/how-to/connect-a-source/) que partout), et activez le mTLS
à certificat client vérifié pour le canal collecteur→core avec
`tls.grpcClientCaSecret` — voir [durcissement](/how-to/security-hardening/).

## Surveillance

Activez `serviceMonitor` si vous exécutez l'opérateur Prometheus ; dans tous les cas le
moteur expose `/metrics` sans authentification (il ne porte aucune donnée tenant) et le
dépôt fournit des règles d'alerte prêtes à l'emploi. Voir
[surveiller avec Prometheus](/how-to/monitor-with-prometheus/).
