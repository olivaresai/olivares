Эта страница — путь **эксплуатации** официальных CLI провайдеров. Плоскость
управления запускает собственный дочерний процесс под **профилем провайдера**.
Она не устанавливает провайдера, не создаёт его home и не открывает
интерактивный вход в браузере.

Это не путь коннектора или hook. Чтобы инвентаризировать или управлять
файлами конфигурации Grok Build или Codex, используйте
[Интеграция Grok Build](/how-to/integrations/grok/) или
[Интеграция Codex](/how-to/integrations/codex/). Чтобы совместно разместить
Claude Code на том же хосте, используйте
[Запуск Claude Code с Olivares](/how-to/run-claude-code-with-olivares/).

Источник этого поведения: раздел `[26.9.0]` в `CHANGELOG.md` (профили
провайдера, драйвер Codex, драйвер Grok), сгенерированные справочники
[консоли](/reference/console/) и
[конфигурации](/reference/configuration/), `cmd/olivares/sessionruntime.go`
и `web/src/features/agentops/types.ts`.

## Предусловия

Выполните их до запуска. Отсутствующий пункт — отказ, а не запасной путь.

1. Olivares AI установлен, и первый администратор существует.
   См. [Ваш первый час](/how-to/first-hour/) про токен установки.
   Дополнительная административная аутентификация (`admin_step_up`) по умолчанию
   имеет значение `none`. Если администратор включает `totp` или `passkey`, выполните
   требования этой политики перед привилегированными операциями
   (`core/api/middleware.go` `requireStepUp`).
2. Официальная CLI провайдера уже установлена на **этом узле**. Профиль
   регистрирует home, которые уже существуют. Сервер разрешает пути
   (абсолютные, символические ссылки разрешены, существующий каталог) и не
   создаёт, не устанавливает и не входит
   (`web/src/features/agentops/types.ts` `CreateProfileRequest`).
3. У вас есть `sessions:profile:read`, чтобы открыть **Provider profiles**
   (`/provider-profiles`), и `sessions:profile:write` для регистрации.
   Привязка источника требует `sessions:profile-binding:write` плюс
   администрирование источников. Запуск требует `sessions:run:write`.
   Права: [справочник консоли](/reference/console/).
4. Для драйвера нужен исполняемый файл на **этом узле**. Явно закреплённый
   двоичный файл имеет приоритет; иначе движок находит его при запуске.
   Проверки готовности и политики по-прежнему действуют для каждого драйвера.

| Драйвер | Закрепите эту переменную окружения | Если не задана |
|---|---|---|
| Claude Code | `OLIVARES_SESSION_RUNTIME_CLAUDE_BIN` | Новейшая проверенная управляемая установка, затем `claude` в `PATH` движка. |
| Codex | `OLIVARES_SESSION_RUNTIME_CODEX_BIN` | Новейшая проверенная управляемая установка, затем `codex` в `PATH` движка. |
| Grok | `OLIVARES_SESSION_RUNTIME_GROK_BIN` | Новейшая проверенная управляемая установка, затем `grok` в `PATH` движка. |

Значение закрепляет официальный исполняемый файл для этого узла. Без
закрепления установленный инструмент доступен без перезапуска движка. Если
нет ни управляемой установки, ни исполняемого файла в `PATH`, запуск отклоняется.
Для `OLIVARES_SESSION_RUNTIME_OPENCODE_BIN` действует тот же порядок поиска.

Для профилей Claude с `managed_injection`, которые не указывают провайдера,
`OLIVARES_SESSION_RUNTIME_WIF` или `OLIVARES_SESSION_RUNTIME_TOKEN_FILE` задаёт
учётные данные вывода на хосте. Профиль, привязанный к провайдеру, использует его
учётные данные; при ошибке запуск отклоняется без перехода к данным хоста.
Профиль с `provider_account_home` использует разрешённый вход инструмента и
не требует ни одной из этих переменных. См.
[Добавить провайдера](/ru/how-to/add-a-provider/).
Codex и Grok используют только AUTHORIZED `auth_source` профиля:
`provider_account_home` или `managed_injection`, без запасного пути и без
значения по умолчанию (`CHANGELOG.md` `[26.9.0]`; `ProviderProfileDTO.auth_source`).

:::caution[Что эта страница не утверждает]
`CHANGELOG.md` `[26.9.0]` указывает, что поведение драйвера Grok доказано
против собственного поддельного ACP-потомка через реальные HTTP, runtime,
хранилище и группу процессов. **Совместимость с аутентифицированной
официальной учётной записью Grok — отдельная работа и здесь не утверждается.**
:::

## 1. Зарегистрировать профиль провайдера

Профиль провайдера — устойчивая идентичность **одного** настроенного
экземпляра провайдера на **одной** среде выполнения: драйвер, владеющая
среда и канонические `config_home` / `user_home`, под которыми работает
потомок. Это идентичность конфигурации и хранения, а не аутентифицированная
учётная запись провайдера (`CHANGELOG.md` `[26.9.0]` B1; текст консоли
`agentops.profiles.subtitle`).

### Консоль

1. Откройте **Provider profiles** (`/provider-profiles`).
2. Выберите **Register profile**.
3. Укажите драйвер (`claude`, `codex` или `grok`), существующий `config_home`
   и существующий `user_home`. `environment_ref` можно опустить (этот узел).
4. Сохраните. Список показывает `profile_ref`, драйвер, состояние и включён
   ли профиль в этой среде. Пути **не** входят в обычный список.
5. Чтобы увидеть сохранённые home, используйте **Reveal configuration**
   (`sessions:profile:admin`). Это чтение по требованию и сбрасывается при
   скрытии. Значения учётных данных по-прежнему нет.

Переименование, отключение и включение сохраняют тот же id и те же home.
**Retire** необратим, подтверждается вводом и освобождает home для **нового**
id.

### Что движок отказывает

- Профиль, драйвер которого не зарегистрирован на этом узле, остаётся видимым
  и не запускается (`operable` не гарантия запуска;
  `GET …/launch-readiness` — панель требований).
- Профиль другой среды выполнения показан как чужой и никогда не запускается
  с этого узла.
- Запуск, который передаёт `HOME`, `CLAUDE_CONFIG_DIR`, `CODEX_HOME` или
  `GROK_HOME`, отклоняется. Эти имена принадлежат профилю
  (`agentops.create.profileEnvConflict`).

Снимка этого экрана в опубликованном наборе нет. Не считайте изображение
вкладки Connectors этой формой.

## 2. Привязать источник (необязательно, для наблюдаемой атрибуции)

Источник можно закрепить за профилем на точной ревизии roster, которую
применил этот узел. Ключ — постоянный id строки, никогда редактируемое имя
(`CHANGELOG.md` `[26.9.0]` B1; **Source bindings** `/provider-bindings`).

1. Откройте **Source bindings** (`/provider-bindings`).
2. Привяжите постоянный `id` источника и `applied_revision`, которую
   подключил reconciler этого узла. `GET /v1/console/sources` сообщает оба.
3. Отзовите привязку, чтобы остановить **новую** атрибуцию профиля. Более
   ранний конверт сохраняет историческую привязку при воспроизведении.

Без привязки известная регистрация всё ещё появляется как строка наблюдения
`source`. Она не сливается в управляемый запуск. См.
[Живая эксплуатация и сеансы](/reference/modules/ii-sessions/).

## 3. Запуск

Продуктивная конечная точка создания требует `provider_profile_ref`. Если её
опустить, остаётся старое тело запроса, которое этот API отклоняет
(`CHANGELOG.md` `[26.9.0]` B2; флаг CLI `--provider-profile`).

Диалог запуска предлагает **активные** профили. Единственный активный профиль
выбирается заранее; если их несколько, не выбирается ни один, и **Start**
просит выбрать. Выборы workspace и template можно очистить; профиль нельзя
(`CHANGELOG.md` `[26.9.0]` Fixed).

### Консоль

1. Откройте **Сессии** (`/sessions`). `/agentops` открывает тот же экран
   ([справочник консоли](/reference/console/)).
2. Откройте **New session**, затем **Advanced launch options** (в
   **More options**, когда инструмент готов).
3. Проверьте **Provider profile** (`agentops.create.profile`) и при желании
   введите **First message**.
4. При желании задайте workspace, template, model и effort в
   **Advanced options**. Для Grok model и effort остаются открытыми строками
   провайдера на официальных флагах агента (`CHANGELOG.md` `[26.9.0]`).
5. Нажмите **Start**. Пока запуск невозможен, строка под кнопкой говорит, чего
   не хватает. Публикуется только **ссылка** профиля. Сервер разрешает home.

Выбор **Папки** определяет, где работает инструмент. Значение **Временная папка
для этой сессии** даёт запуску собственный каталог; зарегистрированная папка
используется как есть. Это отдельно от workspace, который авторизует сессию.
**Контекст → Сведения** показывает сохранённые workspace и папку сессии;
обычная временная папка не является предупреждением.

### Собственный git worktree (необязательно)

По умолчанию сессия работает в выбранной папке. Если это корневая папка
репозитория git, можно запросить **новый git worktree**: отметьте **Работать в
новом git worktree** под **Папкой** или выполните
`olivares session start . --worktree`. Сессия работает в собственном worktree на
новой ветке (`olivares/` и восемь символов её id), поэтому две сессии одного
репозитория не используют общие файлы. Слейте ветку из своего checkout как
обычно; это обычная ветка репозитория.

- Worktree хранятся в `<data directory>/session-worktrees`.
  `OLIVARES_SESSION_WORKTREE_DIR` меняет расположение,
  `OLIVARES_SESSION_WORKTREE_BRANCH_PREFIX` — префикс ветки.
- **Возобновить** продолжает в том же worktree. Если удалён только его каталог,
  движок восстанавливает его на той же ветке.
- **Очистить**, **Удалить** и `olivares session rm` удаляют worktree и его ветку,
  если ветка слита в текущую ветку workspace, worktree находится на этой ветке и
  не содержит незакоммиченных файлов. Иначе освобождение отклоняется (409) с
  указанием того, что будет потеряно: неслитая работа, отсоединённый HEAD или
  другая ветка, либо недоступный движку worktree (например, его workspace удалён).
  Отметьте **Также отбросить worktree и ветку** или добавьте `--discard-worktree`,
  чтобы продолжить; для недоступного worktree это освобождает сессию и оставляет
  worktree на месте. Игнорируемые git файлы, например результаты сборки,
  удаляются вместе с worktree.
- Запрос отклоняется (422) до создания чего-либо, если папка не является корнем
  репозитория git, в репозитории нет коммита, workspace или его папки доступны
  только для чтения, изоляция не `native`, либо конфигурация git репозитория
  задаёт фильтр (`filter.<name>.clean`, `smudge` или `process`) или включает другой
  файл. Сессии без этой опции работают как прежде.
- Движок запускает git с отключёнными хуками репозитория и монитором файловой
  системы, без вашей конфигурации git (поэтому настроенный там фильтр Git LFS не
  применяется: файлы LFS выглядят в worktree как файлы-указатели), с ограничениями
  времени и объёма вывода. Сессия в worktree может писать в общий каталог git
  репозитория. Все его сессии используют этот каталог: worktree изолирует файлы,
  но не метаданные git.

### Открыть работу, указанную в передаче

Передача может указывать положение работы в git: её содержимое принимает
необязательные `branch` и `sha` (полный id коммита). Предложите её через API или
`olivares message handoff offer --context-file`, чей JSON может содержать оба
поля. Передача без этих полей работает как прежде.

При чтении такой передачи панель показывает ветку и коммит текстом, а
**Открыть в worktree новой сессии** открывает запуск с выбранным worktree и
указанной начальной точкой. Запуск ждёт выбора workspace, в репозитории которого
есть коммит. Очистка выбора папки сохраняет этот запрос; чтобы запустить обычную сессию,
явно снимите отметку worktree. Из командной строки:

```sh
olivares session start . --worktree-from <commit or branch> --name review
```

`--worktree-from` подразумевает `--worktree`. Сессия работает на собственной новой
ветке от этого коммита, поэтому ветка отправителя и ваш checkout не меняются.
Если коммита нет в репозитории workspace, запуск отклоняется (422) до создания
чего-либо: сначала получите его там через fetch. Коммит, на который не указывает
ни одна ветка, тег или удалённая ветка, тоже отклоняется. Панель **Изменения ветки**
сессии показывает то, что есть в её ветке, но отсутствует в текущем коммите
workspace; для пути она открывает рядом текст на общей базе слияния и на вершине
ветки. Она показывает только закоммиченную работу в разрешённых подпутях workspace
с учётом его DLP-политики; незакоммиченные изменения находятся в **Изменениях**.

### CLI

```sh
olivares agent session create --provider-profile <profile_ref>
```

Добавьте `--server`, `--tenant` и `--token-file` (или активный клиентский
контекст), как в [справочнике CLI](/reference/cli/). Изоляция в этом выпуске
— `native`; `container` и `sandbox` отклоняются с HTTP 422 до создания
запуска. Для встроенного исполнителя выберите `native`.

Результат: ресурс запуска. Управляемая живая строка уникальна по области
наблюдения и внешнему id. Чтения, которые называют строку, используют
`live_ref`, а не голый id сеанса провайдера, который могут разделять два home.

## 4. Прервать или остановить

| Намерение | Консоль | CLI | Результат |
|---|---|---|---|
| Завершить активный ход, сохранить процесс и беседу | управление interrupt живого сеанса | `olivares agent session interrupt <run-ref>` | ход заканчивается; процесс остаётся пригоден для следующего (`CHANGELOG.md` `[26.9.0]`) |
| Завершить запуск | управление stop | `olivares agent session stop <run-ref>` | ресурс запуска; runtime по-прежнему собирает потомка |

Запуски, связанные с работой, отправляют точное ограждение аренды. Устаревшие
или неопределённые результаты остаются явными. Возобновление продолжается
только на том же доказанном home.

Прерывание Grok использует ACP `session/cancel` — уведомление без
подтверждения. Прерывание разрешает ожидающие согласования, отменяет и
оставляет ход открытым, пока не вернётся коррелированный результат самого
prompt (`CHANGELOG.md` `[26.9.0]`). Не считайте тихое отменение
подтверждённой квитанцией провайдера.
