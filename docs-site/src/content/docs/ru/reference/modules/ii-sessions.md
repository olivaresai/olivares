Модуль II — это представление **живой работы** estate: что каждая сессия агента
делает прямо сейчас, её живые суммарные токены и стоимость, выводимое состояние
Claude Code и реконструируемая временная шкала. Тогда как модуль I (инвентаризация)
материализует устойчивый estate, модуль II ведёт **живое операционное наложение** на
каждую сессию поверх того же потока наблюдений — и показывает только то, что этот
поток честно несёт.

v26.9.0 также **запускает** официальные CLI провайдеров как собственных потомков
под [профилем провайдера](/how-to/operate-provider-sessions/). Этот управляемый
путь — тот же модуль. Он не заменяет наложение и не сливает два home, которые
объявляют один и тот же id сеанса провайдера (`CHANGELOG.md` `[26.9.0]` B1/B2).

## Что это такое

Модуль II — управляемый шиной модуль слоя Core, родственный инвентаризации. Он ведёт
живую запись с ключом по внешней ссылке каждой сессии, построенную из совместного
потока наблюдений — никогда не опрашиваемую, никогда не сфабрикованную. На каждую
сессию он отслеживает:

- **текущее действие** (последний использованный инструмент) и ресурс/режим, которого
  оно коснулось;
- **живые суммарные токены и стоимость**, считываемые из выборок стоимости
  (канонический ledger стоимости и FinOps — это модуль XI, а не здесь; это только
  живая цифра);
- **выводимое состояние Claude Code** (`cc_state`); и
- **временную шкалу**, к которой каждое наблюдаемое событие добавляется в порядке
  приёма.

## Его контракт и сущности

Модуль регистрирует две сущности в области арендатора. `sessions.live` хранит живую
запись на каждую сессию — текущее действие/ресурс/режим, ссылку на модель, живые
входные/выходные токены, живую стоимость, счётчики событий и вызовов инструментов, а
также метки времени первого/последнего события. `sessions.timeline` хранит одну
воспроизводимую строку на каждое событие, упорядоченную по приёму. **Столбца с
хранимым жизненным циклом нет**: совместный поток не несёт сигнала о завершении или
сбое, поэтому единственный честный признак активности — выводимое `cc_state`.

`cc_state` выводится **во время чтения** из недавности событий — `active` / `idle` /
`ended` — и переходит в состояние скрытого уклонения, когда коннектор поднимает эту
находку (модуль никогда не записывает его сам). Чтения обслуживаются под маршрутами
модуля (живой список, одна сессия, временная шкала на сессию) плюс живой поток SSE;
каждое чтение требует разрешения на чтение сессии, а **открытие потока автоматически
проходит аудит**. Канал SSE строго **изолирован по арендатору** (клиент получает
только снимки для своего авторизованного арендатора) и работает **по принципу
наилучших усилий** (медленный клиент пропускает промежуточный кадр и получает
следующий — приём никогда не блокируется).

## Provider profiles and `live_ref`

**Профиль провайдера** — устойчивая идентичность одного настроенного экземпляра
провайдера в одной среде выполнения: драйвер, среда и канонические
`config_home` / `user_home`. Это не аутентифицированная учётная запись
провайдера. Регистрация, переименование, отключение/включение и вывод живут
под `/v1/m/sessions/provider-profiles`. Пути появляются только на admin-чтении
`configuration`. Запуск называет `provider_profile_ref`; сервер разрешает homes
и сохраняет несекретный снимок на run до spawn (`CHANGELOG.md` `[26.9.0]` B1;
`web/src/features/agentops/types.ts`).

Наблюдение складывается в живую строку своего **канала**, который сервер
вычисляет из регистрации источника, проштампованной хостом
(`CHANGELOG.md` `[26.9.0]` B2):

| Channel | Meaning |
|---|---|
| `legacy` | no registration |
| `observed` | a source dedicated to a profile by a binding approved at host admission for the exact applied revision |
| `source` | a known registration with no verifiable profile |
| `managed` | a run the plane launched; the only row carrying `canonical_sid` and `run_ref` |

Каждая живая строка предоставляет `live_ref` и `attribution`. Два homes,
объявляющие один и тот же id сессии провайдера, — две строки с двумя шкалами.
Читайте одну строку через `GET /v1/m/sessions/live/by-id/{live_ref}` (и её
запрос timeline / stream / runs). Голые маршруты внешнего id остаются и
**legacy**: отвечают только для legacy-строки.

Драйверы регистрируются **на узел** закреплением официального двоичного файла
(`OLIVARES_SESSION_RUNTIME_CLAUDE_BIN`, `_CODEX_BIN`, `_GROK_BIN` — см.
[Конфигурация](/reference/configuration/)). Если не задано, профили этого
драйвера остаются наблюдаемыми и не запускаются. Шаги оператора:
[Управлять сеансом провайдера](/how-to/operate-provider-sessions/).

## Что он потребляет (и что выводит)

Модуль II потребляет тот же поток наблюдений с минимальными данными, что и
инвентаризация — [`edge.observed`](/ru/reference/events/), `cost.sampled` и
`finding.reported`. Только рёбра, чьим инициатором является **сессия**, порождают
живую работу; выборки стоимости, привязанные к сессии, добавляются к живой цифре
токенов/стоимости (никакой `CostRecord` здесь не записывается); находки с субъектом-
сессией аннотируются, а находка анти-уклонения помечает состояние уклонения. Два поля
**выводятся живо** из тех же сигналов: `agent_ref` — из агента, приписанного сессии,
и `summary` — из находки уплотнения контекста (forensic), чей заголовок по контракту
безопасен в качестве сводки — никогда не сфабрикованная LLM сводка.

:::caution[Честные ограничения]

- **`goal` остаётся пустым — честно.** Совместный поток несёт минимальные данные и
  **не** содержит цель сессии или список задач; они маскируются на коннекторе, и в
  канале нет внутрипроцессного текста промпта. Живая запись моделирует это поле, чтобы
  контракт и UI были готовы и любой будущий канал метаданных мог его заполнить, но
  модуль **никогда его не выдумывает**.
- **Нет хранимого жизненного цикла.** В потоке нет сигнала завершения/сбоя, поэтому
  активность сессии — это **выводимое** `cc_state` по недавности, а не сохранённый
  статус. Состояние `ended` означает *отсутствие недавних событий*, а не
  подтверждённое чистое завершение.
- **Живая цифра — не ledger.** Живые токены/стоимость — это операционное считывание
  из выборок стоимости; авторитетная, сверяемая запись стоимости — это ledger FinOps
  модуля XI. Не считайте живую цифру биллинговой истиной.
- **Минимальность данных — свойство канала связи.** Передаются и сохраняются только
  ссылки, классификации и счётчики активности/стоимости — никогда полезная нагрузка,
  промпты, команды или PII.
:::
