Модуль II — это представление **живой работы** estate: что каждая сессия агента
делает прямо сейчас, её живые суммарные токены и стоимость, выводимое состояние
Claude Code и реконструируемая временная шкала. Тогда как модуль I (инвентаризация)
материализует устойчивый estate, модуль II ведёт **живое операционное наложение** на
каждую сессию поверх того же потока наблюдений — и показывает только то, что этот
поток честно несёт.

Olivares <!-- release -->0.10<!-- /release --> также **запускает** официальные CLI провайдеров как собственных потомков
под [профилем провайдера](/how-to/operate-provider-sessions/). Этот управляемый
путь — тот же модуль. Он не заменяет наложение и не сливает два home, которые
объявляют один и тот же id сеанса провайдера (`CHANGELOG.md` `[26.9.0]` B1/B2).

## Что это такое

Модуль II — управляемый шиной модуль слоя Core, родственный инвентаризации. Он ведёт
живую запись с ключом по внешней ссылке каждой сессии, построенную из совместного
потока наблюдений — никогда не опрашиваемую, никогда не сфабрикованную. На каждую
сессию он отслеживает:

- **текущее действие** (последний использованный инструмент) и ресурс/режим, которого
  оно коснулось;
- **живые суммарные токены и стоимость**, считываемые из выборок стоимости
  (канонический ledger стоимости и FinOps — это модуль XI, а не здесь; это только
  живая цифра);
- **выводимое состояние Claude Code** (`cc_state`); и
- **временную шкалу**, к которой каждое наблюдаемое событие добавляется в порядке
  приёма.

## Его контракт и сущности

Модуль регистрирует две сущности в области арендатора. `sessions.live` хранит живую
запись на каждую сессию — текущее действие/ресурс/режим, ссылку на модель, живые
входные/выходные токены, живую стоимость, счётчики событий и вызовов инструментов, а
также метки времени первого/последнего события. `sessions.timeline` хранит одну
воспроизводимую строку на каждое событие, упорядоченную по приёму. **Столбца с
хранимым жизненным циклом нет**: совместный поток не несёт сигнала о завершении или
сбое, поэтому единственный честный признак активности — выводимое `cc_state`.

`cc_state` выводится **во время чтения** из недавности событий — `active` / `idle` /
`ended` — и переходит в состояние скрытого уклонения, когда коннектор поднимает эту
находку (модуль никогда не записывает его сам). Чтения обслуживаются под маршрутами
модуля (живой список, одна сессия, временная шкала на сессию) плюс живой поток SSE;
каждое чтение требует разрешения на чтение сессии, а **открытие потока автоматически
проходит аудит**. Канал SSE строго **изолирован по арендатору** (клиент получает
только снимки для своего авторизованного арендатора) и работает **по принципу
наилучших усилий** (медленный клиент пропускает промежуточный кадр и получает
следующий — приём никогда не блокируется).

## Provider profiles and `live_ref`

**Профиль провайдера** — устойчивая идентичность одного настроенного экземпляра
провайдера в одной среде выполнения: драйвер, среда и канонические
`config_home` / `user_home`. Это не аутентифицированная учётная запись
провайдера. Регистрация, переименование, отключение/включение и вывод живут
под `/v1/m/sessions/provider-profiles`. Пути появляются только на admin-чтении
`configuration`. Запуск называет `provider_profile_ref`; сервер разрешает homes
и сохраняет несекретный снимок на run до spawn (`CHANGELOG.md` `[26.9.0]` B1;
`web/src/features/agentops/types.ts`).

Наблюдение складывается в живую строку своего **канала**, который сервер
вычисляет из регистрации источника, проштампованной хостом
(`CHANGELOG.md` `[26.9.0]` B2):

| Channel | Meaning |
|---|---|
| `legacy` | no registration |
| `observed` | a source dedicated to a profile by a binding approved at host admission for the exact applied revision |
| `source` | a known registration with no verifiable profile |
| `managed` | a run the plane launched; the only row carrying `canonical_sid` and `run_ref` |

Каждая живая строка предоставляет `live_ref` и `attribution`. Два homes,
объявляющие один и тот же id сессии провайдера, — две строки с двумя шкалами.
Читайте одну строку через `GET /v1/m/sessions/live/by-id/{live_ref}` (и её
запрос timeline / stream / runs). Голые маршруты внешнего id остаются и
**legacy**: отвечают только для legacy-строки.

Драйверы регистрируются на каждом узле при запуске. При запуске сеанса движок
использует новейшую проверенную управляемую установку, затем CLI из своего `PATH`.
`OLIVARES_SESSION_RUNTIME_CLAUDE_BIN`, `_CODEX_BIN`, `_GROK_BIN` и `_OPENCODE_BIN`
явно переопределяют этот выбор (см. [Конфигурация](/reference/configuration/)).
Если исполняемый файл не найден, запуск отклоняется. Остальные проверки готовности,
включая аутентификацию профиля и политику запуска, остаются в силе. Шаги оператора:
[Управлять сеансом провайдера](/how-to/operate-provider-sessions/).

Сообщение может нести изображения. `olivares session send <session> --attach shot.png "what
is wrong here?"` и редактор сообщения в консоли (вставка, перетаскивание или скрепка)
сохраняют каждое изображение PNG, JPEG, WebP или GIF вместе с сессией — не более четырёх на
сообщение и по 3.75 MB каждое — и отправляют их вместе с текстом; сообщению нужен его текст,
поэтому одно изображение не отправляется (CLI и редактор запрашивают текст). Claude Code
получает блок содержимого с изображением, а Codex — свой собственный ввод изображений;
инструмент без ввода изображений отклоняет сообщение с указанием названия инструмента, до того как что-либо
будет отправлено. API: `POST /v1/m/sessions/runs/{ref}/attachments` (изображение, base64),
`GET .../attachments/{id}` и `attachments` в `.../input`. Изображения хранятся в каталоге
данных, отдельно для каждого тенанта и сессии, и удаляются вместе с сессией.

## Папки сессий на ресурсах NFS или SMB

Папка сессии — это путь на хосте движка, поэтому сетевой ресурс становится папкой, как только хост его смонтировал. `olivares netfolder add` делает это собственными юнитами mount systemd; монтированием по-прежнему управляет systemd, а юниты — обычные файлы, которые можно читать и редактировать. Запускайте от root на хосте движка:

```sh
printf '%s\n' "$SMB_PASSWORD" | sudo olivares netfolder add files //fileserver/projects --user svc --password-stdin
sudo olivares netfolder add data fileserver:/export --mode write_no_delete
olivares netfolder ls
```

Источник — `//server/share` для SMB или `server:/export` для NFS, как их записывает `mount(8)`. Имя состоит из строчных букв и цифр и задаёт точку монтирования `/srv/olivares/mnt/<name>`. `--mode` — режим доступа к папке (по умолчанию `rw`). Юниты указывают учётную запись `olivares` владельцем каждого файла, который показывает папка SMB, поэтому движок должен работать под этой учётной записью. `ls` показывает каждую папку как `mounted`, `unmounted` (она монтируется при первом использовании, а `ls` этого не запускает) или `not responding`. Существующая папка никогда не перезаписывается.

Для примера с SMB команда записывает эти юниты; они измерены на Debian 13 (Linux 6.12) с экспортом NFSv4.2 и общим ресурсом Samba 4.22 (SMB 3.1.1). Имена файлов — это то, что печатает `systemd-escape -p /srv/olivares/mnt/files`, с добавленными `.mount` и `.automount`.

```ini
# /etc/systemd/system/srv-olivares-mnt-files.mount
[Unit]
Description=Olivares network folder files
After=network-online.target
Wants=network-online.target

[Mount]
What=//fileserver/projects
Where=/srv/olivares/mnt/files
Type=cifs
Options=credentials=/etc/olivares/netfolders/files.cred,uid=olivares,gid=olivares,vers=3.1.1,nodev,nosuid,soft,echo_interval=5
TimeoutSec=30
```

```ini
# /etc/systemd/system/srv-olivares-mnt-files.automount
[Unit]
Description=Olivares network folder files (mounted on first use)

[Automount]
Where=/srv/olivares/mnt/files
TimeoutIdleSec=0

[Install]
WantedBy=remote-fs.target
```

Для NFS записывается `Type=nfs4`, `What=fileserver:/export` и `Options=nodev,nosuid,vers=4.2,soft,timeo=50,retrans=2`, без файла учётных данных. На хосте, где включён SELinux с политикой устройства, к параметрам добавляется `context=system_u:object_r:olivares_workspace_t:s0` — метка, которую движок и его инструменты сессий уже используют для папки. Чтобы удалить папку, выполните `systemctl disable --now` для двух её юнитов, удалите их и её файл учётных данных и отмените регистрацию папки.

- **Все, у кого есть папка, действуют как одна учётная запись.** Файлы читаются и записываются от имени учётной записи, которую представляет монтирование: `uid=` и `gid=` для SMB, сопоставление пользователей экспорта для NFS. Ресурс не различает людей. Olivares решает, кто получает папку.
- **Собственная папка человека читается от его имени.** `--owner <ID пользователя>` регистрирует SMB-папку как собственную папку человека, как личную папку: её содержимое принадлежит только ему, а администраторы по-прежнему находят папку, чтобы управлять ею. Укажите через `--user` и пароль собственную SMB-учётную запись этого человека, и файловый сервер применит его права: два человека, подключающие один и тот же ресурс, видят каждый то, что может открыть его собственная учётная запись. Добавляйте по одной папке на человека, каждую со своим именем. NFS не различает людей и не принимает владельца. Администратор вводит пароль человека один раз, и он остаётся в файле учётных данных, доступном только root, как и пароль общей учётной записи; сеанс человека его никогда не получает. Kerberos-билет на сеанс, чтобы человеку не приходилось никому передавать пароль, не реализован. Проверено на двух учётных записях домена Samba AD с одним ресурсом: папка каждого человека показывала его собственный каталог и общий, читала его собственный файл, а файловый сервер отказывал в файле другого человека.
- **Учётные данные хранятся в файле.** Команда записывает `username=` и `password=` в файл `credentials=` — владелец root, режим 0600 — из пароля, полученного со стандартного ввода. Пароль не попадает ни в один юнит, параметр монтирования, аргумент процесса или строку журнала: `mount.cifs` получает только путь. NFS с `sec=sys` не требует учётных данных.
- **Automount-юнит делает загрузку независимой от файлового сервера.** При загрузке ничего не ждёт ресурса. Первое использование монтирует его; если сервер в этот момент недоступен, падает это использование, а не загрузка.
- **Используйте `soft`.** `hard`-монтирование NFS, по умолчанию, оставляет процесс, обратившийся к мёртвому серверу, зависшим там, где его нельзя остановить. С параметрами выше чтение или запись на смонтированном ресурсе завершается ошибкой ввода-вывода или «Host is down» через 20–30 секунд, а ресурс снова работает, когда сервер отвечает.
- **Папка, которая не отвечает, сообщается.** Регистрация папки, её открытие, перечисление и запуск в ней сессии каждый ждут ресурса по 10 секунд, затем отказывают с сообщением "The folder ... is not responding. If it is on a network share, check that its file server is up and reachable." и статусом 424. Сессия не запускается.
- **`write_no_delete` выполняется.** Landlock применяет его на уровне файловой системы ядра, над сетевой файловой системой. В реальных запусках сессии на обоих ресурсах сессия создавала и изменяла файлы, а переименование, unlink и rmdir были отклонены, как на локальном диске; `rw` их разрешал. Хост, который не может ограничить сессию, по-прежнему отказывает в запуске.
- **Папка — граница.** В тех же запусках в обоих режимах запись в родительскую папку, находящуюся на том же ресурсе, была отклонена и не оставила файла. Сессия пишет только внутри своей папки.

## Что он потребляет (и что выводит)

Модуль II потребляет тот же поток наблюдений с минимальными данными, что и
инвентаризация — [`edge.observed`](/ru/reference/events/), `cost.sampled` и
`finding.reported`. Только рёбра, чьим инициатором является **сессия**, порождают
живую работу; выборки стоимости, привязанные к сессии, добавляются к живой цифре
токенов/стоимости (никакой `CostRecord` здесь не записывается); находки с субъектом-
сессией аннотируются, а находка анти-уклонения помечает состояние уклонения. Два поля
**выводятся живо** из тех же сигналов: `agent_ref` — из агента, приписанного сессии,
и `summary` — из находки уплотнения контекста (forensic), чей заголовок по контракту
безопасен в качестве сводки — никогда не сфабрикованная LLM сводка.

:::caution[Честные ограничения]

- **`goal` остаётся пустым — честно.** Совместный поток несёт минимальные данные и
  **не** содержит цель сессии или список задач; они маскируются на коннекторе, и в
  канале нет внутрипроцессного текста промпта. Живая запись моделирует это поле, чтобы
  контракт и UI были готовы и любой будущий канал метаданных мог его заполнить, но
  модуль **никогда его не выдумывает**.
- **Нет хранимого жизненного цикла.** В потоке нет сигнала завершения/сбоя, поэтому
  активность сессии — это **выводимое** `cc_state` по недавности, а не сохранённый
  статус. Состояние `ended` означает *отсутствие недавних событий*, а не
  подтверждённое чистое завершение.
- **Живая цифра — не ledger.** Живые токены/стоимость — это операционное считывание
  из выборок стоимости; авторитетная, сверяемая запись стоимости — это ledger FinOps
  модуля XI. Не считайте живую цифру биллинговой истиной.
- **Минимальность данных — свойство канала связи.** Передаются и сохраняются только
  ссылки, классификации и счётчики активности/стоимости — никогда полезная нагрузка,
  промпты, команды или PII.
:::
