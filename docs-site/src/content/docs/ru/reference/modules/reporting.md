Reporting (`modules/reporting`) создаёт отчёты, когда модуль включён. Он объединяет
данные платформы о соответствии, аудите и FinOps в один документ,
чтобы аудитор мог скачать доказательства, а не копировать JSON из нескольких API.

**Редакция:** Business Compliance Packs предоставляет каталоги стандартов, оценки, регуляторный календарь, представления DORA/HIPAA, запечатывание доказательств, экспорт OSCAL и отчёты HTML/PDF по запросу. Community возвращает `501` для этих функций и сохраняет управление риском, размещением данных, записями и экспорт сохранённых доказательств в JSON/CSV. Обновления сохраняют существующие записи.

## Встроенные отчёты

Open-core-модуль предоставляет по запросу пять типов отчётов:

- `compliance-evidence` — состояние соответствия по фреймворкам, статусы контролей и доказательства.
- `audit-summary` — сводка событий аудита и проверка целостности ledger.
- `finops-report` — расходы на AI по моделям и провайдерам.
- `access-review` — пользователи и данные доступа для периодической проверки.
- `executive-summary` — краткая сводка по управлению, рискам, затратам и внедрению.

`GET /v1/m/reporting/reports` перечисляет типы и форматы. Отчёт создаётся через
`GET /v1/m/reporting/reports/{type}`; по умолчанию возвращается HTML, а
`?format=pdf` скачивает PDF. Для маршрутов требуется `reporting:report:read`.

## Включить модуль и скачать отчёт

После входа в движок через CLI администратор может включить reporting:

```sh
olivares modules on reporting
```

Движок перезапускается, если включение меняет набор работающих модулей. Прежде
чем запрашивать отчёт, дождитесь повторного подключения консоли или успешной
проверки готовности установленного сервиса. Healthcheck Compose использует
`olivares readyz`.

```sh
olivares reporting reports ls -o json
olivares reporting reports get finops-report --format html --out spend.html
```

Включение reporting также активирует необходимый ему модуль compliance и
зависимости этого модуля. Каталог перечисляет форматы, доступные в работающем
движке; проверьте его перед запросом PDF. Генерация читает сохранённые данные
выбранного тенанта. В пустой установке нет расходов для отчёта.

Чтобы явно задать период, передайте и `--from`, и `--to` с датами ISO или метками
времени RFC 3339. В скрипте `--out -` пишет документ в stdout, а квитанцию скачивания
в stderr. Документ имеет формат HTML или PDF, а не JSON.

`olivares modules off reporting` удаляет reporting из выбранных модулей. Если
ни одному включённому модулю или дополнению редакции reporting не нужен, его
маршруты отключаются без удаления сохранённых данных. Пока он отключён, запросы
reporting возвращают `404` с `module_not_enabled`; включение восстанавливает
маршруты. Выбор модулей и исходные данные отчётов переживают перезапуск движка.
Документы по запросу скачиваются; сохраните файл, если нужен именно этот отчёт.

## Чёткие границы

- Для PDF Chromium запускается в headless-режиме. Если в `PATH` нет `chromium`,
  `chromium-browser` или `google-chrome`/`chrome`, запрос PDF возвращает `501`; HTML
  остаётся доступным.
- Для compliance-evidence нужен источник данных о соответствии. Если он не
  подключён, документ явно сообщает «Data source not configured», а не
  выдумывает доказательства.
- Модуль рендерит документы из уже имеющихся в платформе данных. Он не заменяет
  audit ledger, оценку соответствия или авторитетный источник FinOps.

- Генерация HTML и доступ к каталогу требуют аутентифицированного вызывающего с
  `reporting:report:read` в выбранном тенанте. Отказ в аутентификации — `401`;
  вызывающий без полномочий для этого тенанта получает `403`.
- Доступность каталога не подтверждает покрытие данных каждого отчёта. В текущем
  access-review заполняются имена идентичностей; email, роли, разрешения и поля
  последнего доступа его адаптер данных не заполняет.
- Группы расходов в отчётах FinOps идентифицируют модели и провайдеров по
  сохранённым ID, а не по отображаемым именам.
