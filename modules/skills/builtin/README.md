# Built-in skills catalog

Skills shipped inside the binary, as data. The product only reads them: nothing here runs at
install, and a pack's scripts are recorded in its revision, never executed.

| Source | Pinned release | What is vendored |
| --- | --- | --- |
| ECC (MIT) | v2.2.3 | 285 of its 293 skills, one pack per ECC install module (`ecc-<module>`); agents and rules under `data/` |
| Matt Pocock's skills (MIT) | 1.2.3 | 26 of the 27 skills in its engineering and productivity categories (`mattpocock-engineering`, `mattpocock-productivity`) |

`PIN.json` is the single record: the source repository, release and commit, then each archive with its
SHA-256 and its skill and file counts. Every pack is a `tar.gz` of the upstream
bytes plus the upstream `LICENSE`. License texts and the NOTICE entry are
`LICENSES/third-party/{ecc,mattpocock-skills}.txt` and the repository `NOTICE`; the per-edition NOTICE
generated by `scripts/license-gate.py` starts from it.

## Not shipped: nine skills

The importer validates every pack (`portable-v1`: every `metadata` value is a string). Nine upstream skills put a mapping in `metadata` and are refused, so `exclude` in
`PIN.json` leaves them out, with the reason: ECC's eight supply-chain skills (`carrier-relationship-management`,
`customs-trade-compliance`, `energy-procurement`, `inventory-demand-planning`, `logistics-exception-management`,
`production-scheduling`, `quality-nonconformance`, `returns-reverse-logistics`; the only skills ECC licenses
under Apache-2.0) and `engineering/pr` from Matt Pocock's. The bytes are not patched and the validator is not
relaxed. They return when upstream fixes the frontmatter, or when the validator deliberately accepts nested metadata.

## Install a pack

A built-in pack enters a tenant's catalog like any other source, as an immutable revision that
assignments then pin:

```
POST /v1/m/skills/packs
Idempotency-Key: <key>

{"name": "ecc-security", "source": {"kind": "builtin", "ref": "ecc-security"}}
```

`ref` is a pack `id` from `PIN.json`. The revision records the upstream repository, the pinned commit
and the archive digest. A new release of the product carries newer data; install it as a new revision of
the same pack (`POST /v1/m/skills/packs/{id}/revisions`). Existing assignments keep their pinned revision.

## Update path

1. Edit `sources` in `PIN.json`: the new `commit` (and `release`), or the `select` map of a source.
2. `python3 -I scripts/skills-catalog.py build` rebuilds every archive and rewrites `PIN.json`.
3. Review the diff: the pack and skill counts, the new digests, and the NOTICE entry if a license changed.
4. `python3 -I scripts/skills-catalog.py verify` fetches the pinned commits again and fails if a committed
   archive differs, so a reviewer can check the bytes without trusting the committer.

`build` stops when ECC adds a skill that none of its install modules lists, when a skill declares a
license other than the source's, when an `exclude` path is not in the commit, or when the fetched archive is
not the pinned commit. The Go test in this package installs every pack through the importer, so a new
upstream skill the validator refuses fails there and is either excluded with its reason or fixed upstream.
