# Commit outcome hosted oracle — expected exits (design of `commit-outcome-oracle.yml`)

**Placement.** Repository `olivaresai/olivares`. The workflow is `.github/workflows/commit-outcome-oracle.yml`. The mutants and this file are `ci/oracles/commit-outcome/*.patch` and `ci/oracles/commit-outcome/EXPECTED.md`. Every job runs on `ubuntu-latest`. `oracle`, `routes` and `generated` each assert `runner.environment == github-hosted` in their first step, and `verdict` asserts it in its only step. PostgreSQL 16 (`pgvector/pgvector:pg16`, pinned digest) is a service of `routes` only. No cache and no artifact from another run is used.
**Triggers.** Each push to `feat/commit-outcome-proxy-measurement`, or to a branch named `feat/commit-outcome-proxy-measurement-<suffix>`, runs the whole workflow once on the pushed head. `workflow_dispatch` runs it on a named head; its `candidate_sha` must be 40 hex digits and the head of the dispatched ref, and an empty or malformed value is refused. Every job runs on both events; a branch deletion is not measured. Concurrency is per commit, so a newer push never replaces a pending run. Every run asserts `candidate == github.sha == HEAD` and a clean checkout. It records the event, the runner name and placement, and the variables `CI_RUNNER`/`CI_RUNNER_LIGHT`. The exits below are those of a head that carries the commit outcome change, its tests and these files. On any other head, the PASS line prints only if every expectation below holds there too.
**Commands.** Run from the top of the checkout with `-json` appended (implies `-v`). Each label keeps its command, raw `-json` stream, stderr and raw exit.
**Mutants.** `git apply` runs only after `git apply --numstat` proves the patch deletes exactly N lines of one file. Patches apply by context and offset: without `--3way` the `index` blob ids are ignored. The safety rests on the numstat, the context and the restore: `git checkout -- <file>`, then the blob is re-proved equal to `HEAD:<file>`.
**Marker.** After the numstat and `--check` pass and before `git apply`, the step writes `in-flight` = (step label, file, `pending`); the verdict turns it into `measured`. The next step that checks the tree (`pristine`/`restore`) reads it. For `pending`, the step ended after the marker and before its verdict: killed at its step ceiling, or exited on an error, a failed apply included. It then writes `<step label>  INABILITY the step ended while its mutant was pending …` to `verdicts.tsv` and restores the `HEAD:` blob. For `measured`, it restores the blob without a line. A stop before the marker left the tree untouched. On a workflow cancellation no later step that reads the marker runs, because each is gated on `!cancelled()`. So no INABILITY line is written and the PASS line cannot print; the `always()` upload keeps the marker as it was.
**Classes.** GREEN: raw exit 0, exactly the listed results, nothing failed or skipped (SKIP is not PASS). KILLED: raw exit 1; exactly the leaf and its parents fail; every other selected test passes; the leaf printed the listed text. INABILITY: no test result (build failure or empty selection), `panic: test timed out`, `COULD_NOT_LOOK` in the leaf (a cleanup that could not stop its worker included), or a mutant step that ended while its marker was `pending`. SURVIVED: the leaf passed. OTHER: anything else. Only GREEN and KILLED pass. An inability is never a kill.

## Job `verdict` and the SDK gate
It prints one line, `commit-outcome oracle PASS at <sha> (<event>): …; repository variables CI_RUNNER=… CI_RUNNER_LIGHT=…`, only when `oracle`, `routes` and `generated` succeeded and every output equals its expectation: steps 1/3/5 `GREEN 8`, step 6 `GREEN 10`, M1 and M2 `KILLED`, routes `GREEN 25` before and after, six M11 `KILLED`, both engine families `GREEN n>0`, and generated `NONE`. An empty output is a measurement that never happened, and it is red (`::error::no verdict`, exit 1).
**SDK suites, outside this workflow:** `gh workflow run mainline-ci.yml --repo olivaresai/olivares --ref <branch>`.
- That run must show: `head_sha` equal to the candidate; `classify` giving `code=true` (event ≠ push); and `sdk-tests` succeeding with its python, typescript and java steps run.
- Placement is decided by the jobs API of that run: `gh api repos/olivaresai/olivares/actions/runs/<run>/jobs` must show, for `classify` and `sdk-tests`, a `runner_name`, `labels` = `ubuntu-latest` and a GitHub-hosted `runner_group_name`.
- Supporting evidence only: `identity.txt` and this workflow's verdict line show `CI_RUNNER`/`CI_RUNNER_LIGHT` as a job without an `environment:` sees them (repository and organization variables). A repository-level 404 from `…/actions/variables/CI_RUNNER` alone proves nothing, because an organization variable of the same name would still apply.
- The sdk-tests selectors are Java `ClientTest#neverRetriesCommitOutcomeUnknown`/`#stillRetriesOther503OnGet`, Python `test_commit_outcome_unknown_is_never_retried`/`test_other_503_get_still_retried`, and TS "never retries commit_outcome_unknown"/"still retries another 503 GET".
- None of these is ever a pass: a skipped, cancelled or undispatchable `sdk-tests` run means the SDK suites were not measured, and a self-hosted runner means they were not measured on a GitHub-hosted one.
- The Go client pair and the web vitest files run in the pull request's own `pr-ci` (`pr-test-shard`, `pr-web`), not here.
