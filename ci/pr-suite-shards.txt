# The SHARD PARTITION of the pull-request functional suite (.github/workflows/pr-ci.yml).
#
# WHY IT EXISTS, measured on the hosted 4-vCPU runner (run 35293935807, 2026-09-18). The
# suite ran in ONE job and took 77 min 8 s of step and 78 min 55 s of job over 280
# packages. Two earlier runs of the same suite did not even finish: 264 packages green
# and the 60-minute step ceiling cut them, twice. Raising the ceiling makes the suite
# PASS; it does not make the answer ARRIVE, and every contribution waits for the answer.
#
# WHY IT WAS SPLIT AGAIN, measured 2026-09-20 on the public repository. The package split
# below reached its floor and then went through it. `cmd/olivares` hit `panic: test timed
# out after 45m0s` at 2700.093 s on the shard of a change that adds one test file to
# `core/api`; `core/internal/store/sqlstore` hit the same clock at 2700.024 s on the shard
# of a change that adds one test to `core/auth`. Between those two the same shards passed
# twice. A required check whose verdict depends on the runner's variance and not on the
# change is not a verdict, and the previous entry of this file said where the floor was:
# "one package takes 1461.7 s on its own. No package-level split goes under it."
#
# WHAT THE MEASUREMENT SAYS ABOUT THE TWO PACKAGES, because the split follows from it. The
# same tree measured `cmd/olivares` at 1418, 1698, 1705 and 2526 s on 2026-09-19 and at
# 2567 s on 2026-09-20, against 1355.8 s when it ran inside the unsharded sweep: the spread
# is 78 % of the smallest, and the timeout is what happens when the spread stacks. Two
# causes are on the record and neither is a guess. The memory ceiling this repository
# shipped for the runner deaths (a derived GOMEMLIMIT in scripts/with-pg-env.sh) buys the
# 8693 MiB peak down to 4538 MiB and pays for it in throughput: 2852 tests started by
# t+1318 s with it against 3115 without. And the package grew — the race partition of the
# same package was calibrated at 2145 top-level tests and now enumerates 2429.
#
# THE FLOOR OF A PACKAGE SPLIT, and how this one goes under it: the tests of ONE package go
# to DIFFERENT shards by NAME. That is what scripts/race-groups.json already does for the
# -race sweep of this same root package, and the record below is the same idea in this
# file's grammar.
#
# THE PARTITION IS DECLARED, NOT COMPUTED. A hash of the package name balances nothing
# when one package is 22 % of the clock, and it cannot be read: a person who adds a
# package cannot tell where it landed, and a person who reads a red shard cannot tell
# what else was in it. The lists below are the whole answer, and
# scripts/check-pr-suite-shards.sh proves they cover the suite exactly once.
#
# FORMAT — one record per line, fields separated by whitespace, `#` starts a comment.
#
#   shard <name>                 declares a shard. THE ORDER IS THE MATRIX ORDER.
#   pkg   <shard> <pattern>      an import-path pattern that shard owns.
#                                `<path>/...` is the subtree; anything else is exact.
#   group <shard> <package> <name> <family>…
#                                a NAME GROUP: the top-level tests of ONE package whose
#                                name begins with Test<family>, run by that shard and by
#                                no other. The single family `*` is the REMAINDER — every
#                                top-level test, fuzz target and example of the package
#                                that no other group of it names. The remainder is
#                                COMPUTED from the source at run time, so a test added
#                                tomorrow is already in the partition; without it a new
#                                name would match no group, and `go test -run` over an
#                                expression that selects nothing EXITS 0.
#   leg   <shard> <task>         a Taskfile leg that shard runs after its packages.
#   optional <pattern>           this pattern MAY match nothing, because the module it
#                                names is not published in every tree. Everywhere else a
#                                pattern that matches nothing is stale and is a finding.
#   go-timeout-minutes <n>       `go test -timeout` inside a shard.
#   step-ceiling-minutes <n>     the workflow step ceiling. Must exceed the go timeout.
#   job-ceiling-minutes <n>      the workflow job ceiling.
#
# ASSIGNMENT RULE: THE LONGEST MATCHING PATTERN WINS — the same rule as
# scripts/race-groups.json, and for the same reason: it lets a broad pattern and a
# surgical one live side by side without either listing the other's packages.
# `core/...` and `core/internal/...` both match the four remaining core/internal packages;
# the second is longer, so shard `store-a` owns them. Two patterns of the SAME length
# matching one package is not a tie to break quietly — it is a package in two shards, and
# it is a finding. A package with `group` records is outside this rule entirely: its
# groups own it, one shard each, and a pattern that ALSO names it exactly is a finding,
# because every test of it would then run twice.
#
# WHY THE FAMILIES ARE FIRST LETTERS AND NOT SUBJECTS. The race partition names about 500
# families by hand because it needs eight balanced turns; this needs four and three, and
# the first letter of the name after `Test` is the coarsest predicate that balances them
# to within 7 %. It has one property a hand-written family list does not: it needs NO
# MAINTENANCE when a test is added, because every name begins with some letter — a
# contributor can tell where a new test lands by reading its first letter, and the letters
# nobody named are exactly the remainder. The counts below are from the source of this
# tree (2429 top-level tests and 2 fuzz targets in cmd/olivares; 1270 in sqlstore).

shard root-a
shard root-b
shard root-c
shard root-rest
shard store-a
shard store-b
shard store-rest
shard sessions
shard modules

# --- the four shards of the root package ------------------------------------------------
# THE ARITHMETIC. 2700 s is the sizing basis: it is the only number that BOUNDS the package
# from below, because the run that produced it did not finish. Four groups put no group over
# 27.0 % of it — 730 s, 12.2 min — which is the number to compare against the rule this file
# uses for a group: nothing predicted above 20 min on a hosted runner. Three groups would
# have been 900 s, and 900 s is only 25 % under 20 min on a package whose last five complete
# measurements disagree by 78 %; that is the margin this partition exists because we lost.
#
#   a  TestA… TestB… TestC…                   657 of 2431 = 27.0 %  → 730 s
#   b  TestD… through TestK…                   639          = 26.3 %  → 710 s
#   c  TestL… through TestR…                   645          = 26.5 %  → 716 s
#   rest  everything else — TestS… to TestZ…,  490          = 20.2 %  → 545 s
#         the two fuzz targets, and every name
#         no letter above claims
#
# The remainder is the SMALLEST group on purpose: it is the one that grows without anybody
# deciding, so it starts with the most room. `-run` selects fuzz targets and examples as
# well as tests, so they are in the universe and the remainder carries them; a partition
# written as if only `Test*` existed would have dropped both fuzz targets without a word.
group root-a    github.com/olivaresai/olivares/cmd/olivares a    A B C
group root-b    github.com/olivaresai/olivares/cmd/olivares b    D E F G H I J K
group root-c    github.com/olivaresai/olivares/cmd/olivares c    L M N O P Q R
group root-rest github.com/olivaresai/olivares/cmd/olivares rest *

# The eight sibling packages of cmd/olivares and the 178 connector packages ride with the
# first group: 25.4 s of test time between the connectors, chosen for costing nothing to
# BUILD as well as nothing to run.
pkg root-a github.com/olivaresai/olivares/cmd/...
pkg root-a github.com/olivaresai/olivares/connectors/...

# The rest of core, the operator and the control plane ride with the remainder group, which
# is the smallest of the four: 674.6 s of test time, 337 s at the two lanes the sweep

pkg root-rest github.com/olivaresai/olivares/core/...
pkg root-rest github.com/olivaresai/olivares/operator/...
pkg root-rest github.com/olivaresai/olivares-cloud-cp/...

# --- the three shards of the store package ------------------------------------------------
# Same arithmetic on the same basis: 2700 s, the floor left by the 45-minute timeout of
# 2026-09-20. Its complete measurements are older and smaller (1461.7 s, then 1231.2 s on
# 2026-09-18) and sizing against those would rebuild the margin that just failed.
#
#   a     TestA… through TestD…               434 of 1270 = 34.2 %  → 923 s
#   b     TestE… TestF… TestG… TestH… TestI…  433         = 34.1 %  → 921 s
#         and TestP…
#   rest  everything else                     403         = 31.7 %  → 857 s
#
# `b` is not a letter RANGE and that is the arithmetic showing: TestP… alone is 224 of the
# 1270, the largest letter of the package, so it travels with the small ones instead of
# with its neighbours. The groups go to DIFFERENT shards for a reason that is not balance:
# this package serialises on Postgres, and each shard has its own pair of database services.
# Two groups of it in one shard would queue on one database and buy nothing.
group store-a    github.com/olivaresai/olivares/core/internal/store/sqlstore a    A B C D
group store-b    github.com/olivaresai/olivares/core/internal/store/sqlstore b    E F G H I P
group store-rest github.com/olivaresai/olivares/core/internal/store/sqlstore rest *

# The four remaining core/internal packages, the clients, the SDK and the provider ride with
# the first group. `core/internal/...` is longer than `core/...`, so these four land here and

pkg store-a github.com/olivaresai/olivares/core/internal/...
pkg store-a github.com/olivaresai/olivares/clients/...
pkg store-a github.com/olivaresai/olivares/sdk/...
pkg store-a github.com/olivaresai/olivares/terraform-provider-olivares/...

# --- the clocks -------------------------------------------------------------------
# THE PREDICTED WALL CLOCK, shard by shard, from the numbers above. A shard runs its whole
# packages in one `go test` and each of its groups in another, one after the other, because
# `-run` is an option of the COMMAND and not of a package.
#
#   root-a      730 + 30     760 s   12.7 min
#   root-b      710          710 s   11.8 min
#   root-c      716          716 s   11.9 min
#   root-rest   545 + 337    882 s   14.7 min
#   store-a     923 + 35     958 s   16.0 min
#   store-b     921          921 s   15.4 min
#   store-rest  857          857 s   14.3 min
#   sessions    995          995 s   16.6 min
#   modules     998          998 s   16.6 min
#
# go-timeout 30m: this clock is PER TEST BINARY, so what it has to cover is the longest
# single invocation and not the slowest shard — modules/sessions at 995 s, then the store's
# first group at 923 s. 30 min leaves 81 % of headroom over 16.6 min, and it is LOWER than
# the 45 it replaces on purpose: 45 was the number a package reached twice in one day, and a
# timeout that only fires after three quarters of an hour is a diagnosis that arrives after
# the contribution has already waited for it. Go panics with its goroutine dump, the package
# name and now the group's `-run`; the step ceiling only cancels.
#
# step 35m: the slowest step is a shard's wall clock plus the build. The build is measured:
# the shard that ran cmd/olivares on 2026-09-20 took 2726 s of step with 2567 s inside that
# one package, so 159 s built 189 packages and ran the other 188. 995 + 180 = 1175 s, 19.6
# min, and 35 leaves 79 % of headroom over it while staying above the Go timeout.
#
# job 45m: the step plus checkout, setup-go, the pinned go-task install and the two Postgres
# services — the same 10 minutes this file has always left between the two ceilings.
#
# THESE ARE PREDICTIONS AND THEY REST ON ONE ASSUMPTION: that a group's seconds are its share
# of the package's tests. The counts are exact and the package totals are measured, but no
# per-test duration has ever been measured on a runner, so the share is a proxy. The first
# two hosted runs are what turns it into a measurement — read the seconds `go test` prints
# per group, and if any group is more than 30 % off its prediction, move letters between the
# groups of that package and nothing else. Re-measure it once the shards have run: a ceiling
# that was never measured is a guess that nothing corrects.
go-timeout-minutes 30
step-ceiling-minutes 35
job-ceiling-minutes 45
