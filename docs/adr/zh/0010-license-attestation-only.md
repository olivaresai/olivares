# ADR-0010: 许可仅用于证明——绝不用于限制功能

- **Status:** accepted
- **Date:** 2026-06
- **Deciders:** Fran Olivares
- **References:** licensing design (final decision); API/authz/audit contract (§7, §13.5)

## 背景与待解决的问题

商业化的开放核心（open-core）产品必须决定其许可强制机制在运行时*做什么*。一种诱惑是把功能锁在许可校验之后。对于一个本身也是潜在授权绕过面（authorization-bypass surface）的安全产品而言，这种做法与"纯双重许可、不限制任何功能"的理念相冲突。

## 决策驱动因素

- 不削弱开放版产品。
- 不让许可校验成为一个授权绕过面。
- 可在隔离网络（air-gapped）中运行，无需许可服务器。

## 考虑过的选项

- **仅证明型许可校验（attestation-only）**，绝不阻断任何东西。
- 按许可层级**限制功能（feature-gating）**。

## 决策结果

选定方案：**仅证明（attestation only）**。许可校验记录持有者及其状态，仅作信息提示之用；它在**开放（AGPL）二进制文件中**绝不禁用、降级或阻断任何请求、模块或启动过程。校验是**离线**的（一个 Ed25519 签名；无许可服务器）。开放二进制文件是完整的 CORE 治理平台；商业版增加了独立、附加的 `enterprise/` add-on（这是开放核心，而不是「同一个完整产品」——见下文修订和 ADR-0011）。

### 后果

- **好处：** 开放版产品绝不会被削弱；许可校验无法被转变为授权绕过；产品可在隔离网络中运行。
- **坏处／权衡：** 商业差异化来自*许可条款*以及独立的 `enterprise/` 模块，而非来自对核心的限制。
- **中性：** 许可测试在设计上是 fail-open（失败时放行）。

## 为何否决了其他选项

- **限制功能（feature-gating）**——会使开放版成为一个更差的产品，侵蚀信任，并把一个可被伪造的许可变成与安全相关的限制门。否决。

## 修订 (2026-06-23)

本 ADR 在精确界定范围后仍然成立：**许可证密钥绝不限制开放二进制文件。** 该模型是**开放核心**（ADR-0011 的修订），因此此前「免费版与授权版是同一个完整产品」的说法并不准确，现已在上文更正——商业版具有附加的 `enterprise/` add-on（正是本 ADR 一直所称的「独立的 `enterprise/` 模块」）。经过证明的 claim 仅由封闭的 enterprise 构建*使用*，且仅用于授予这些附加 add-on 的权益——这是客户自身商业构建中的本地决定。Olivares 自己的云服务仍绝不能为了计费而信任自报的状态。

**修订 (2026-07-27, B10)。** 本说明先前描述的唯一与席位相关的使用——`enterprise/seats` 读取 `license.Claims.MaxUsers` 以解除 community 用户席位上限——已经取消：所有版本中的自托管用户帐户均为**无限**，3 人上限已移除，且 `MaxUsers` 在任何地方都只用于显示。这加强而非限制了本 ADR：现在无论开放还是商业构建，均不会读取许可证来限制用户。见 `LICENSING.md` 和 商业定价规范（私下维护）。
