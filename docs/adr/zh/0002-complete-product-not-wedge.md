# ADR-0002: 交付完整产品（28 个模块），而非切入点功能

- **Status:** accepted
- **Date:** 2026-06-02
- **Deciders:** Fran Olivares
- **References:** product decisions register (P1); module catalog (the 28 modules)

## 背景与待解决的问题

基础设施类产品常见的市场切入策略是采用一个狭窄的"切入点"（wedge）——先交付一项
锐利的能力，赢得一个滩头阵地，再逐步扩张。对 Olivares AI 而言，候选的切入点功能
就是单独的读/写访问图（read/write access map）。问题在于：是发布这个切入点功能，
还是发布完整的 control plane。

## 决策驱动因素

- 第一印象：企业买家（CTO/SOC/安全负责人）评估 control plane 时，是把它当作一个
  平台、而非一项功能来看待的。
- R/RW 图在一个*完整平台之内*比作为独立工具更有价值。
- 避免重新架构：模块化平台可以在不返工的前提下接纳新模块。

## 考量过的选项

- **完整产品** —— 把全部 28 个模块作为一个连贯的平台发布（自有模型管理/微调是一项
  规划中的能力，并不属于这 28 个模块之一）。
- **狭窄的切入点** —— 单独发布 R/RW 图，日后再扩张。

## 决策结果

所选方案：**完整产品**。首发版本即为围绕 Claude 与 Claude Code 构建的完整平台——
资产清点、实时会话、R/RW 图、治理、来源/凭据范围限定、部署、知识、安全、特权会话
录制、模型/提供方管理、内联推理代理、FinOps、评估、合规、SIEM 转发器、目录、输出
集成、事件流、语音、沙箱、红队演练与健康度——并以引擎自身的 API、多租户和仪表盘作为
核心/控制台能力。R/RW 图是**该产品之内的一项关键差异化能力**，而非产品本身。

### 影响

- **好处：** 第一天就有一个完整、可信的平台；访问图在上下文中落地。
- **坏处/权衡：** v1 需要构建并保持诚实的面要大得多；各模块的深度参差不齐，必须
  如实记录（见*诚实与限制*）。
- **中性：** 自有模型管理/微调是一项规划中的能力，并不属于已交付的这 28 个模块之一。

## 为何否决其他方案

- **狭窄的切入点** —— 否决：它低估了一个平台型产品的价值，并且有让 R/RW 图被误认为
  一个普通"会话查看器"而非其真正所是的最小权限漂移（least-privilege drift）引擎的
  风险。
