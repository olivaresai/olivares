# ADR-0012: 分布式采集——采集器经 gRPC + mTLS 向核心推送

- **Status:** accepted
- **Date:** 2026-06-04
- **Deciders:** Fran Olivares (boot decision CB-1)
- **References:** roadmap boot decisions (CB-1 → option C); runtime-ingestion contract

## 背景与待解决的问题

采集（ingestion）平面需要一项拓扑决策。采集器在客户主机上进行观测；核心负责聚合。备选方案从仅进程内（in-process）一直到完全分布式的推送模型，对隔离性、网络信任边界和打包方式都有不同影响。

## 决策驱动因素

- 让数据平面留在客户基础设施上，并对网络跨越点做强化处理。
- 在简单场景下保留单一二进制文件。
- 将采集器的依赖与核心隔离。

## 考虑过的选项

- **C——远程推送：** 采集器在本地运行源连接器，并经 **gRPC + mTLS** 向核心**推送**观测数据，采集器上**没有入站监听端口**。
- **B——进程外本地（out-of-process local）：** 连接器作为本地子进程运行（AutoMTLS），即单节点基底。
- **A——进程内（in-process）：** 源直接链入二进制文件（第一方快速通道）。

## 决策结果

选定方案：**以 C（远程推送）作为分布式目标**，以 B 作为单节点基底，并保留 A 作为第一方源的进程内快速通道。所有传输方式均进入 v1；C **不**被推迟。该机制位于运行时之内；分布式打包（DaemonSet/Helm）随供应链相关工作一并交付。

### 后果

- **好处：** 数据跨越网络边界时经过强化（mTLS + bearer + authz）；采集器不暴露任何入站端口；单一二进制文件得以保留。
- **坏处／权衡：** 分布式部署引入更多活动部件。
- **中性：** 单一二进制的默认形态使用进程内／本地子进程通道。

## 为何否决了其他选项

- 单凭 **A** 或 **B** 都无法覆盖多主机规模；它们分别作为快速通道与单节点基底保留，而非作为分布式的答案。
