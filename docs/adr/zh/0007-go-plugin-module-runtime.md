# ADR-0007: 通过 go-plugin（gRPC）实现进程外的模块/连接器运行时

- **Status:** accepted
- **Date:** 2026-06
- **Deciders:** Olivares AI
- **References:** stack design (module runtime); license-boundary design

## 背景与问题陈述

平台必须允许第一方和第三方连接器与模块对其进行扩展，而不将它们的依赖树拖入引擎，
也不会用引擎的 copyleft 许可证污染采用宽松许可证的连接器生态。

## 决策驱动因素

- 将连接器的依赖与引擎的构建/SBOM 隔离开。
- 跨进程边界提供一份稳定、带版本的合同。
- 保持 Apache-2.0 连接器边界的洁净（连接器绝不链接 AGPL 引擎）。

## 考虑过的方案

- **基于 gRPC 的 `hashicorp/go-plugin`**，用于进程外的模块/连接器，外加进程内
  编译的核心模块。
- **仅进程内插件**（Go `plugin` 包或编译进二进制）。

## 决策结果

选定方案：**`hashicorp/go-plugin`（gRPC）**，用于进程外的连接器/模块，第一方连接器
被内嵌并作为隔离的子进程启动，核心模块则编译进来。连接器 SDK 是一个 Go 接口加上一份
带版本的 gRPC/protobuf 合同。

### 后果

- **优点：** 连接器的依赖不会进入引擎的二进制/SBOM；Apache/AGPL 边界保持洁净并在 CI 中
  强制执行；第三方可以独立发布连接器。
- **缺点 / 权衡：** 多了一份需要维护版本的 gRPC 合同，以及进程外组件的一跳 IPC（进程间通信）。
- **中性：** 单一二进制文件仍然内嵌第一方连接器（以子进程隔离），因此它仍是单一构件。

## 为何否决其他方案

- **仅进程内** —— 会把每个连接器的依赖全都拉进引擎，并使许可证边界无法以机械方式强制执行。
