# ADR-0001: 使用 MADR 记录架构决策

- **Status:** accepted
- **Date:** 2026-06-07
- **Deciders:** Olivares AI
- **References:** documentation/product session establishing the ADR register

## 背景与问题陈述

control plane 的架构决策此前散记在若干规划与
契约文档中（架构、技术栈、许可、各会话契约以及
“boot decisions”）。这段历史是真实且良好分隔的，但它并非一种新
贡献者或评估者能逐条决策阅读的形式：*决定了什么*、*为什么*，
以及 *拒绝了什么*。当理由只存在于冗长的规划行文中时，上下文会在
会话之间丢失。

## 决策驱动因素

- 一份持久的、按决策索引的记录，能在贡献者之间存续。
- 一种轻量格式，不会自成一个文档项目。
- 可作为产品文档的一部分发布。

## 已考虑的选项

- **MADR（Markdown Any Decision Records）。** 极简、被广泛采用、原生 Markdown。
- **一套定制的决策日志。** 更自由，但没有共享约定。
- **不做正式的 ADR。** 仅将理由保留在规划文档中。

## 决策结果

所选方案：**MADR**。每一项已做出的决策都被记录为一个编号的
`docs/adr/NNNN-*.md`，包含背景、所选方案、后果与被拒绝的
备选方案，并发布在文档站点的 *Explanation* 部分。

### 后果

- **好处：** 决策可被发现且能自我说明；新贡献者不会
  重新争论已尘埃落定的问题。
- **坏处 / 取舍：** 需要一点持续的纪律，在做出决策时添加一条记录。
- **中性：** 现有的规划文档仍是 ADR 所引用的来源，而非被 ADR
  取代的东西。

## 为何拒绝这些备选方案

- **定制日志** —— 重新发明一个已被解决的约定；对外部贡献者更难上手。
- **不做 ADR** —— 把理由埋藏在行文中，而这正是上下文一直在丢失的方式。
