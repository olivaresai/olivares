# ADR-0019: 将 Cedar 作为正向、带作用域的授权引擎（而非仅拒绝的叠加层）

- **Status:** accepted
- **Date:** 2026-06-15
- **Deciders:** Fran Olivares
- **References:** ADR-0013（PDP — Cedar + OPA）

## 背景与问题陈述

ADR-0013 将 Cedar 置于 `auth.PolicyEvaluator` 接缝之后，作为一个 **仅拒绝的叠加层**：
一条隐式的基础 `permit(principal, action, resource)` 被编译在
运维方策略之前，因此 Cedar 的决策只可能是 `forbid`（一种限制）。
于是授权 **在租户层面是扁平的**——内置 RBAC 在整个租户范围内授予某项
权限，而策略只能将其收窄。无法表达一种 **正向、带作用域的授权**：
"该管理员只能在工作区 X 中管理 agent"、"查看者只能读取文件夹 Y 之下的资源"、"该角色可以写入
`payments` agent 组"。作用域平面（workspace → agent-group → agent →
resource/folder）对这棵树进行了建模，但没有任何东西沿着它*强制执行*授权；
access map 仅仅在*观测*（`AccessEdge.Permitted` = "未知为已许可"）。

## 决策驱动因素

- 表达作用域绑定到树（workspace、agent-group、资源
  子树）以及条件（模型、敏感度、AAL）的正向授权——在真实路径上强制执行。
- 保留 ADR-0013 所确立的拒绝叠加与默认拒绝保证（forbid 仍然
  覆盖；缺失的授权仍然拒绝）。
- 不要手工重新实现层级/成员关系解析——使用经过形式化
  验证、原生对其建模的引擎。
- 向后兼容：一个未编写任何授权的部署必须做出与之前完全相同的决策，并且
  在热路径上不付出任何代价。

## 决策结果

**将内嵌的 Cedar 引擎从仅拒绝的叠加层提升为一个三值、
作用域感知的授权引擎，置于一个 **新的** `auth.ScopedAuthorizer` 接缝之后，与拒绝叠加层并列（而非嵌入其中）。**

1. **三值决策，无需 base-permit 取巧。** cedar-go 的 `Authorize` 是
   默认拒绝且 forbid 覆盖 permit 的，其 `Diagnostic.Reasons` 会指明
   起决定作用的策略。这从单次求值中恢复了 Authorizer 所需的效果：
   `Allow` → **Grant**；带 reasons 的 `Deny` → **Forbid**；不带
   reasons 的 `Deny` → **Abstain**（默认拒绝）。ADR-0013 的基础 permit 被移除——
   一条 `permit` 现在真正进行授权，一条 `forbid` 仍然进行限制，而一条空的/无关的
   策略则弃权，从而让 RBAC 决策成立（向后兼容不变式）。

2. **Authorizer 代数变为** `Allow = (RBAC ∨ Grant) ∧ ¬Forbid ∧ ¬deny-overlay`。
   作用域引擎先运行（一条 forbid 会短路，覆盖 RBAC 和任何
   授权）；基础是租户范围的 RBAC 授权 OR 一条正向的作用域授权；
   原生 ABAC 引擎 + 任何外部 PDP 随后将其收窄（纵深防御）。默认拒绝
   与 fail-closed 得以保留；一个为 nil 的作用域引擎会将 Authorizer 退化为其
   ADR-0013 行为。

3. **授权权威就是按租户编写的 Cedar 策略**（策略编写
   界面），现在以授权模式编译。引擎将请求的*真实*资源（按实体 id
   从存储中读取——无法伪造）的谱系解析为
   一个 Cedar 实体图，其 `Parents` 编码了包含关系，于是 Cedar 的传递性 `in`
   完成层级遍历。**我们没有新增一个独立的结构化授权行存储**：
   *投影到* Cedar 的结构化/控制台授权编写是结构化编写层的职责；
   作用域引擎消费该策略并强制执行它。

4. **授权仅限于按租户；全局 env Cedar 与 OPA 保持仅拒绝。** 一条
   过于宽泛的全局 *forbid* 只会拒绝（安全）；一条过于宽泛的全局 *permit* 则会
   跨租户授权（不安全）。这种不对称性是决定性的：正向授权存在于
   按租户编写的策略中（引擎以租户为键检索它），而部署
   范围的 env Cedar (`OLIVARES_PDP_*`) 与 OPA 仍然是仅限制的叠加层。

### 影响

- **好处：** 企业级的作用域授权（workspace/agent-group/folder/model/
  敏感度/AAL）在 REST + gRPC 的咽喉点强制执行；经过验证的引擎解析
  层级/成员关系；向后兼容与默认拒绝保持完好；热路径在
  某个租户选择启用授权之前不付出任何代价（引擎在任何存储读取之前就弃权）。
- **坏处 / 权衡：** 启用了授权的租户在实体级请求上需付出一次小的、受门控的存储读取以解析
  某个实体的作用域（按租户的作用域缓存是已记录的
  后续工作）；作用域树条件只在已激活的引擎中针对实时层级解析，
  而不在编写时的 dry-run 中解析。
- **行为变更（已记录）：** 一条曾被 ADR-0013 叠加层
  无声中和的运维方 `permit` 规则，现在会进行授权。仅含 forbid 的已编写策略不受影响。

## 为何驳回了备选方案

- **在作用域引擎中使用独立的结构化授权行 schema**——会重复 Cedar 自身的策略
  模型与层级解析；经过验证的引擎已经将授权表达为
  实体图上的策略。结构化编写应归属于结构化编写层，投影到
  引擎已经消费的 Cedar。
- **每条授权生成一条 Cedar 策略**——无法扩展（策略集膨胀、每次授权编辑都产生
  抖动）；在已解析的实体图上使用模板化策略，可让一条规则覆盖
  整个 workspace/组/子树。
- **让全局 env Cedar 具备授权能力**——一条全局 permit 上被遗忘的
  租户保护会跨租户授权。授权被限制在按租户的策略中。
