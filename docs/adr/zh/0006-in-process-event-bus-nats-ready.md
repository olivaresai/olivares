# ADR-0006: 默认使用进程内事件总线，并对 NATS 保持传输无关性

- **Status:** accepted
- **Date:** 2026-06
- **Deciders:** Olivares AI
- **References:** SDK/runtime/event-bus contract; stack design

## 背景与问题陈述

连接器（connector）将观测数据提升到内部事件总线上；模块（module）和输出连接器按类型订阅。
单一二进制文件必须在没有消息代理（message broker）的情况下工作，而多主机部署又需要一条分布式
总线。

## 决策驱动因素

- 单一二进制文件的默认形态不依赖任何代理。
- 通向分布式总线的路径不应强迫订阅者做出改动。

## 考虑过的方案

- **进程内 Go 通道（channel）作为默认实现，置于一个传输无关的 `Bus` 接口之后**，
  使得分布式实现（NATS）可以替换它。
- **从一开始就使用代理（NATS）。**

## 决策结果

选定方案：**以进程内 Go 通道总线作为 v1 默认实现**，`Bus` 接口**不暴露任何通道**，
从而可以在多主机部署中切入 **NATS** 实现，**无需改动任何一个订阅者**。投递是
异步且至少一次（at-least-once）的；消费者依据自然键时间戳去重。

> **由 ADR-0017（2026-06-12）修订：** 上一句中的“至少一次（at-least-once）”作为对总线
> 投递的描述是错误的——实现以及 S02 §4 合同都是至多一次（at-most-once）（处理器出错会记录日志，
> 队列中的事件在关闭时丢弃）；至少一次（at-least-once）适用于源级别的重新发射（`Gather` 重跑），
> 而这正是消费者所去重的对象。ADR-0017 记录了已交付的 NATS 后端：进程内本地扇出
> 保持不变 + NoEcho 桥接，跨节点至多一次（at-most-once），v1 中没有 JetStream。

### 后果

- **优点：** 单一二进制文件无需任何代理；分布式路径是即插即用的。
- **缺点 / 权衡：** 至少一次（at-least-once）语义把去重的责任推给了消费者。
- **中性：** NATS 是可选的，仅用于分布式拓扑。

## 为何否决其他方案

- **从一开始就使用代理** —— 会给每一次安装都加上一个外部依赖，违背单一二进制 /
  气隙（air-gap）目标，而其价值只有分布式拓扑才需要。
