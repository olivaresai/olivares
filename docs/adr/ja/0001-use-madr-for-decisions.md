# ADR-0001: MADR を用いてアーキテクチャの決定を記録する

- **Status:** accepted
- **Date:** 2026-06-07
- **Deciders:** Olivares AI
- **References:** ADR 登録簿を確立するドキュメント／製品セッション

## 背景と問題提起

control plane のアーキテクチャ上の決定は、複数の計画文書と契約文書（アーキテクチャ、
スタック、ライセンス、セッションごとの契約、そして「ブート決定」）にまたがって記録
されていました。その履歴は実在し、よく分離されていますが、新しい貢献者や評価者が
決定ごとに読める形式にはなっていません。すなわち、*何が* 決定され、*なぜ* で、
*何が却下されたのか* です。根拠が長い計画散文の中だけに存在すると、セッション間で
コンテキストが失われます。

## 決定の推進要因

- 貢献者の間で生き残る、耐久性のある、決定でインデックス化された記録。
- それ自体がドキュメントプロジェクトにならない軽量な形式。
- 製品ドキュメントの一部として公開可能であること。

## 検討した選択肢

- **MADR (Markdown Any Decision Records)。** 最小限で、広く採用されており、Markdown ネイティブ。
- **独自の決定ログ。** より自由度が高いが、共通の慣習がない。
- **正式な ADR なし。** 根拠を計画文書のみに留める。

## 決定の結果

選択した選択肢: **MADR**。すでに行われた各決定は、背景、選択した選択肢、結果、
却下された代替案を伴う番号付きの `docs/adr/NNNN-*.md` として記録され、ドキュメント
サイトの *Explanation* セクションに公開されます。

### 結果

- **良い点:** 決定は発見可能で自己説明的になる。新しい貢献者が解決済みの問題を
  蒸し返さない。
- **悪い点 / トレードオフ:** 決定が行われたときに記録を追加するという、小さな継続的な
  規律。
- **中立:** 既存の計画文書は、ADR が置き換えるものではなく、ADR が引用するソースの
  ままである。

## 代替案が却下された理由

- **独自ログ** — 解決済みの慣習を再発明する。外部の貢献者にとってより難しい。
- **ADR なし** — 根拠を散文の中に埋もれさせたままにする。これがコンテキストが
  失われていた原因である。
