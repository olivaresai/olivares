# ADR-0002: ウェッジではなく、完全な製品（28 モジュール）を出荷する

- **Status:** accepted
- **Date:** 2026-06-02
- **Deciders:** Fran Olivares
- **References:** product decisions register (P1); module catalog (the 28 modules)

## 背景と課題

インフラ製品の一般的な市場投入戦略は、狭い「ウェッジ」だ。すなわち、鋭い 1 つの機能を出荷し、
足がかり（ビーチヘッド）を獲得してから、後で拡張していく。Olivares AI における候補のウェッジは、
read/write access map 単体だった。問いは、このウェッジを出荷するのか、それとも完全な
control plane を出荷するのか、という点にあった。

## 意思決定の要因

- 第一印象：エンタープライズの購買担当者（CTO/SOC/セキュリティ）は、control plane を機能ではなく
  プラットフォームとして評価する。
- R/RW map は、単体ツールとしてよりも、完全なプラットフォームの*内部*にある方が価値が高い。
- 再アーキテクチャの回避：モジュール型のプラットフォームであれば、再設計なしに新しいモジュールを
  受け入れられる。

## 検討した選択肢

- **完全な製品** — 28 モジュールすべてを 1 つの一貫したプラットフォームとして出荷する
  （自社モデルの管理／ファインチューニングは計画中の機能であり、28 のうちの 1 つではない）。
- **狭いウェッジ** — R/RW map 単体を出荷し、後で拡張する。

## 決定の結果

選択した選択肢：**完全な製品**。初回リリースは、Claude および Claude Code を中心に構築された
フルプラットフォームである。インベントリ、ライブセッション、R/RW map、ガバナンス、
ソース／クレデンシャルのスコーピング、デプロイ、ナレッジ、セキュリティ、特権セッションの
記録、モデル／プロバイダー管理、インライン推論プロキシ、FinOps、評価（evals）、
コンプライアンス、SIEM フォワーダー、カタログ、出力統合、イベンティング、音声、サンドボックス、
レッドチーミング、ヘルス — これらに加えて、エンジン自身の API、マルチテナンシー、ダッシュボードを
コア／コンソールの機能として備える。R/RW map は、その製品の**内部にある差別化された主要な機能の
1 つ**であって、製品そのものではない。

### 結果として生じること

- **良い点：** 初日から完全で信頼に足るプラットフォームが存在し、access map が文脈の中で着地する。
- **悪い点／トレードオフ：** v1 で構築し、正直さを保ち続けるべき表面積がはるかに大きい。深さは
  モジュールごとに異なり、正直に文書化しなければならない（*正直さと限界*を参照）。
- **中立的な点：** 自社モデルの管理／ファインチューニングは計画中の機能であり、出荷される 28 の
  モジュールの 1 つではない。

## 代替案を却下した理由

- **狭いウェッジ** — 却下：プラットフォーム製品の価値を過小に見せてしまい、R/RW map が、実際には
  least-privilege drift エンジンであるにもかかわらず、コモディティ化した「セッションビューア」と
  受け取られるリスクがある。
