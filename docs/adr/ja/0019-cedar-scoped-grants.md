# ADR-0019: Cedar を肯定的かつスコープ付きの付与エンジンとする（拒否専用オーバーレイではなく）

- **Status:** accepted
- **Date:** 2026-06-15
- **Deciders:** Fran Olivares
- **References:** ADR-0013 (PDP — Cedar + OPA)

## 背景と課題

ADR-0013 は Cedar を `auth.PolicyEvaluator` シームの背後に **拒否専用オーバーレイ** として配置した。
暗黙のベースとなる `permit(principal, action, resource)` がオペレーターのポリシーよりも先にコンパイル
されるため、Cedar の判定は常に `forbid`（制限）にしかなり得なかった。したがって認可は
**テナントレベルでフラット** であった — 組み込みの RBAC がテナント全体にわたって権限を付与し、ポリシーは
それを狭めることしかできなかった。**肯定的でスコープ付きの付与（grant）** を表現する手段は存在しなかった。
たとえば「この管理者はワークスペース X 内のエージェントのみを管理できる」「閲覧者はフォルダ Y 配下の
リソースのみを読み取れる」「このロールは `payments` エージェントグループへ書き込める」といったものである。
スコーピングプレーン（ワークスペース → エージェントグループ → エージェント → リソース/フォルダ）は
ツリーをモデル化したが、それに沿って付与を *強制* するものは何もなかった。アクセスマップは単に *観測* する
だけだった（`AccessEdge.Permitted` =「許可されていると判明していない」）。

## 決定の要因

- ツリー（ワークスペース、エージェントグループ、リソースサブツリー）と条件（モデル、機微度、AAL）に
  スコープ付けされた肯定的な付与を表現し、実経路上で強制する。
- ADR-0013 が確立した拒否オーバーレイとデフォルト拒否の保証を維持する（forbid は依然として上書きし、
  付与が存在しなければ依然として拒否する）。
- 階層／メンバーシップの解決を手作業で再実装しない — それをネイティブにモデル化する、形式的に検証された
  エンジンを用いる。
- 後方互換性: 付与が一切記述されていないデプロイメントは、従来とまったく同じ判定を下さねばならず、
  ホットパスで何のコストも払ってはならない。

## 決定の結果

**組み込みの Cedar エンジンを拒否専用オーバーレイから、三値の、スコープ認識型の付与エンジンへと格上げし、
拒否オーバーレイの内部ではなくその傍らに置く、新しい `auth.ScopedAuthorizer` シームの背後に配置する。**

1. **三値判定、ベース permit のハックなし。** cedar-go の `Authorize` はデフォルト拒否であり、
   forbid が permit を上書きする。そしてその `Diagnostic.Reasons` は決定的なポリシーを名指しする。これにより、
   Authorizer が必要とする効果を単一の評価から回復できる。`Allow` → **Grant**、理由付きの `Deny` →
   **Forbid**、理由なしの `Deny` → **Abstain**（デフォルト拒否）。ADR-0013 のベース permit は撤廃される —
   いまや `permit` は真に付与し、`forbid` は依然として制限し、空または無関係なポリシーは棄権（abstain）して
   RBAC の判定が有効なまま残る（後方互換性の不変条件）。

2. **Authorizer の代数は次のようになる:** `Allow = (RBAC ∨ Grant) ∧ ¬Forbid ∧ ¬deny-overlay`。
   スコープ付きエンジンが最初に実行される（forbid は短絡し、RBAC と任意の付与を上書きする）。ベースは
   テナント全体の RBAC 付与 OR 肯定的なスコープ付き付与である。続いてネイティブの ABAC エンジン＋任意の
   外部 PDP がそれを狭める（多層防御）。デフォルト拒否とフェイルクローズドは維持される。スコープ付きエンジンが
   nil の場合、Authorizer は ADR-0013 の挙動に縮退する。

3. **付与の権威はテナントごとに記述された Cedar ポリシーそのものである**（ポリシー記述サーフェス）。
   これがいまや付与モード（grant mode）でコンパイルされる。エンジンは、リクエストの *真の* リソースの
   系譜（エンティティ ID でストアから読み取る — 偽装不能）を、`Parents` が包含関係をエンコードする
   Cedar エンティティグラフへと解決する。これにより Cedar の推移的な `in` が階層ウォークを担う。**我々は
   別個の構造化付与行ストアを追加していない**: Cedar に *投影する* 構造化／コンソール上の付与記述は構造化記述レイヤーの
   関心事である。スコープ付きエンジンがポリシーを消費してそれを強制する。

4. **付与はテナントごとに限定される。グローバルな env Cedar と OPA は拒否専用のままである。** 広すぎる
   グローバルな *forbid* は拒否するだけである（安全）。だが広すぎるグローバルな *permit* はテナント横断で
   付与してしまう（危険）。この非対称性が決め手となる。肯定的な付与はテナントごとに記述されたポリシー
   （エンジンがテナントをキーとして扱う）に存在し、一方でデプロイメント全体の env Cedar（`OLIVARES_PDP_*`）
   と OPA は制限専用オーバーレイのままである。

### 帰結

- **良い点:** エンタープライズ級のスコープ付き認可（ワークスペース／エージェントグループ／フォルダ／モデル／
  機微度／AAL）が REST ＋ gRPC のチョークポイントで強制される。検証済みエンジンが階層／メンバーシップを
  解決する。後方互換性とデフォルト拒否は損なわれない。テナントが付与をオプトインするまで、ホットパスは
  何のコストも払わない（エンジンはストアを読み取る前に棄権する）。
- **悪い点 / トレードオフ:** 付与を有効にしたテナントは、エンティティレベルのリクエストにおいてエンティティの
  スコープを解決するため、小さくゲートされたストア読み取りのコストを払う（テナントごとのスコープキャッシュは
  文書化済みのフォローアップである）。スコープツリー条件は、有効化されたエンジン内の生きた階層に対してのみ
  解決され、記述時のドライランでは解決されない。
- **挙動の変更（文書化済み）:** ADR-0013 のオーバーレイが暗黙のうちに無効化していたオペレーターの `permit`
  ルールが、いまや付与（GRANT）する。forbid のみで記述されたポリシーは影響を受けない。

## 代替案を却下した理由

- **スコープ付きエンジンにおける別個の構造化付与行スキーマ** — Cedar 自身のポリシーモデルと階層解決を重複させる。検証済み
  エンジンはすでに、エンティティグラフ上のポリシーとして付与を表現している。構造化された記述は構造化記述レイヤーに属し、
  エンジンがすでに消費している Cedar へ投影する。
- **付与ごとに 1 つの Cedar ポリシーを生成する** — スケールしない（ポリシーセットの増大、付与編集のたびの
  チャーン）。解決済みエンティティグラフ上のテンプレート化されたポリシーであれば、1 つのルールで
  ワークスペース／グループ／サブツリー全体をカバーできる。
- **グローバルな env Cedar を付与可能にする** — グローバルな permit にテナントガードを付け忘れると、
  テナント横断で付与してしまう。付与はテナントごとのポリシーに閉じ込められる。
