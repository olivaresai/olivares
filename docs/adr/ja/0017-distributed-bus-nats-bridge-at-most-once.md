# ADR-0017: 分散イベントバス = プロセス内ローカルファンアウト + NATS ブリッジ、コア NATS は at-most-once（v1 では JetStream なし）

- **Status:** accepted（ADR-0006 の配送セマンティクスの記述を修正）—
  **ADR-0021 により拡張**。at-least-once の JetStream バックエンドをクローズドな
  enterprise アドオンとして出荷し、以下で予期されたサブスクライバーごとの冪等性対応ではなく、
  バス境界での重複排除によって重複安全性の問題を解決する。このオープンな Core NATS
  ブリッジは at-most-once のままで、変更されない。
- **Date:** 2026-06-12
- **Deciders:** design pressure-tested by a 3-lens adversarial panel before implementation
- **References:** `docs/contracts/S02-sdk-runtime-eventbus.md §4`,
  `core/eventbus/natsbus`, subscriber idempotency census (recon, 2026-06-12)

## 背景と課題

ADR-0006 はバスをプロセス内のまま、NATS のスロットを残していた。HA が出荷され、マルチノードが存在するようになった——だが
バスはノードをまたがない。スタンバイで発行されたイベント（バックグラウンドソース、アイデンティティスイープ）は
リーダーの処理に決して届かない。イベンティングプラットフォームのキャプチャ——耐久性の
境界——はそれを静かに取りこぼす。2 つの問いを、既定値ではなく証拠をもって答える必要があった。
**(a)** 分散バックエンドはローカルの配送経路を置き換えるのか、それとも橋渡しするのか、**(b)**
コア NATS（at-most-once）か JetStream（at-least-once）か。

ADR-0006 はバスを「at-least-once；コンシューマが重複排除する」と記録していた。**この記述は
実装の説明として誤っていた**。プロセス内バスは at-most-once であり（ハンドラのエラーはログに記録されるが
リトライされない。キューに入れられたイベントはクローズ時にドロップする — `core/eventbus/inproc.go`）、
S02 §4 の契約は再配送のない blocking なバックプレッシャーを記述しており、
`modules/eventing/capture.go` は「バス自体は at-most-once（S02）であり、リプレイはキャプチャから始まる」と
述べている。ADR-0006 の at-least-once という表現は、バスの配送ではなく、ソースレベルの再発行
（`Gather` の再実行）を記述したものだった。

## 決定の要因

- 2026-06-12 のサブスクライバ調査: 約 17 のバスサブスクライバの大半は重複セーフではない
  （eventing は二重キャプチャし、security/notify は重複を永続化または送信し、count/aggregate の畳み込みは
  膨張する）。今日の時点で at-least-once 配送を行えば、アップグレードを装った意味論的な後退となる。
- S02 §4 の文書化された保証——飽和時に Publish はブロックし、「イベントを静かに失うことは
  パブリッシャをスロットルすることよりも悪い」——は屋台骨である。`olivares_ingest_duration_seconds` は
  バックプレッシャーの SLI として文書化されており（docs/17 §1.4）、collector-backpressure の runbook は
  「イベントは失われない——バスはドロップではなくブロックする」と述べている。ローカルのホットパスを
  サーバ経由でルーティングすれば、本番トラフィックの 100% でその契約を反転させることになる（LB はスタンバイをドレインする）。
- バックエンドが救出するために存在するトラフィック（スタンバイ起源のイベント）は LOW ボリュームの経路であり、
  ローカル経路がホットなものである。設計は、コールドな経路のためにホットな経路を犠牲にしてはならない。

## 検討した選択肢

- **A. 純粋な NATS トランスポート** — すべての publish/subscribe がサーバを経由する。コードパスは 1 つ。
  却下: ローカル経路で S02 §4 を反転させ（契約が blocking で no-loss を約束する箇所で、
  サイレントな slow-consumer ドロップが生じる）、同一ノード配送にサーバ再起動/再接続の損失ウィンドウを加え、
  ingest SLI の意味を劣化させる。
- **B. ハイブリッド: プロセス内ローカルファンアウト + NoEcho を伴う NATS ブリッジ（選択）。**
- **C. JetStream（at-least-once）** — v1 では却下: 調査はサブスクライバが
  重複セーフでないことを示している。JetStream が着手可能になるのは、サブスクライバ全体にわたる
  冪等性のパスの後のみである（以下の明示的なアップグレード経路として追跡）。

## 決定の結果

選択した選択肢: **B + コア NATS**。`core/eventbus/natsbus` はプロセス内バスを埋め込む。Publish はまず
ローカルにファンアウトし（S02 §4 のすべての保証は無傷——blocking なバックプレッシャー、ローカル損失ゼロ、パニックの
分離、ホットパスでのコーデックなし）、その後イベントを best-effort で NATS にブリッジする。ブリッジ
接続は **NoEcho** を設定するため、その単一のワイルドカードサブスクリプションは REMOTE 起源の
イベントのみを受信する。それを再マテリアライズし（3 つの観測ペイロードは frozen proto の `Event` oneof、
モジュール定義の型は JSON + デコーダレジストリ）、ローカルのファンアウトに注入する——二重配送はなく、
型をまたいでパブリッシャごとの順序が保たれる（ノードごとに 1 接続、1 つの順序付きサブスクリプション）。

**クロスノードの意味論、正直に文書化: at-most-once。** 損失ウィンドウ: NATS サーバの再起動
（永続化なし）、再接続バッファのオーバーフロー/再接続できなかった場合（「バッファ済み ≠ 配送済み」）、
そしてブリッジサブスクリプションの pending バッファが埋まったときの slow-consumer ドロップ——いずれも計数され
（`olivares_eventbus_bridge_*`）アラート可能であり、決してサイレントではない。HA: リモートイベントは
**リーダー上でのみ**注入され（`SetInjectGate(store.Leader().Active)`）、これによりスタンバイ側の副作用クラス
（重複通知、重複した派生 findings、ErrNotLeader のログストーム）をバス境界で消し去る。≤2 秒のフェイルオーバの
重複期間は二重注入を起こしうるが、eventing キャプチャの
`(tenant_id, event_id)` ユニークインデックスが吸収する。設定（`OLIVARES_BUS_CONFIG`）は fail-boot-closed である。
プロセス内に静かにフォールバックしたノードは、分断された状態で動作してしまう。

### 帰結

- **良い点:** スタンバイ起源の観測がリーダーに届く（クロスノードのギャップを埋める）。デフォルトのシングルノード
  バイナリはバイト単位で影響を受けない。ローカル配送の意味論は変わらない。クロスノードの損失は
  計数され、サイレントではない。
- **悪い点／トレードオフ:** クロスノード経路はスタンバイ起源のトラフィックによってのみ行使される——その
  コーデック/注入経路は専用の統合テスト（埋め込み nats-server）を持つ。まさに本番では
  まれにしか行使されないためである。ブリッジされたイベントは、ブリッジが設定された
  ノードでは publish ごとに 1 回のエンコードを加える。
- **中立:** JetStream は at-least-once のアップグレード経路として残り、サブスクライバの
  冪等性パスがゲートとなる（調査がその作業リストである）。`Bus` インターフェースは何も獲得していない——Stats と
  名前付きサブスクリプションはオプションの拡張インターフェースである。

## 代替案を却下した理由

要因を参照: A はコールドな経路を単純化するためにホットパスで文書化された契約を反転させる。C は
明らかに重複を誤って扱うサブスクライバに重複を送り込む。
