# ADR-0018: リアルタイム音声バックエンド — v1 では休眠状態として文書化し、統合は v1 以降に

- **Status:** accepted
- **Date:** 2026-06-12
- **Deciders:** Fran Olivares
- **References:** `modules/liveingest/voice.go:28`
  (`PublishVoiceTelemetry`), `modules/voice` (モジュール XVI)

## 背景と課題

音声テレメトリのプローブはエンドツーエンドで構築・検証済みである。`liveingest.PublishVoiceTelemetry`
は許可リスト済みの `voice.Telemetry` を `voice.telemetry.observed` として発行し、モジュール XVI は
それを厳格に再検証するコンシューマーによってセッションメタデータへ取り込む。だが、本番経路のどこからも
このプロデューサーは呼び出されていない — このビルドにはリアルタイム音声バックエンドが存在しない — ため、
観測側（observe）は空である。これは純粋なシーム（接合点）にすぎない。問われるのは、いま（たとえば
LiveKit のような）バックエンドを統合するのか、それとも姿勢（posture）を宣言するのか、という点である。

## 決定の結果

**v1 はプローブを休眠状態のまま出荷し、そのことを明言する。** 誠実な姿勢はすでにコードで強制されている。
プロデューサーは破棄可能なサンプルを拒否し、何も捏造しない。liveingest の `Start` は「voice
telemetry probe wired but dormant — no realtime voice backend in this build emits turn metadata」
とログ出力する。観測側は、偽って満たされている状態ではなく、目に見えて空のままに保たれる（決して暗黙の
ギャップを生まず、同様に決して充足を捏造しない）。具体的なリアルタイムバックエンド（LiveKit または
同等品）の統合は、**需要があればそのときに行う v1 以降のセッション** とする。

スケールアウト作業の過程で、このシームはマルチノードでも誠実なものにされた。将来いずれかのノード上で
プローブに供給するディスパッチャーが現れても、NATS ブリッジ経由でリーダーの voice モジュールに到達できる
（コンポジションルートが `voice.Telemetry` ペイロードデコーダーを登録する）。これにより、休眠中のシームが
HA 下で暗黙のうちに単一ノード専用のシームになることはなかった。

### 帰結

- **良い点:** 投機的な依存関係がない。シームはテスト済み（プロデューサー＋コンシューマー＋NATS ブリッジ
  デコーダー）であり、将来の統合は設計ではなく配線（wiring）で済む。
- **悪い点 / トレードオフ:** 音声の観測ペインは v1 では空のままとなる — UI 契約において宣言済みのシーム
  として文書化されており、これが真実の状態である。
- **中立的な点:** この決定はアーキテクチャに依存するものではなく、需要に依存するものである。
