# ADR-0016: 外部コネクタエコシステム — 公開 SDK、署名付きアドミッション、releases/OCI 配布、キュレーションされた検証済みインデックス

- **Status:** accepted
- **Date:** 2026-06-11
- **Deciders:** Fran Olivares (v1 scope decided 2026-06-09)
- **References:** `LICENSING.md` (license boundary), ADR-0007 (go-plugin runtime),
  ADR-0011 (AGPL/Apache/commercial), ADR-0015 (supply chain),
  `docs/contracts/S02-sdk-runtime-eventbus.md`,
  `docs/contracts/S142-external-connector-sdk.md`

## 背景と課題

コネクタ SDK（`sdk`、`sdk/plugin`）は初日から、コネクタが AGPL エンジンを決してリンクしないよう
設計されてきた（Apache-2.0、依存ゼロ、gRPC
プラグイントランスポート — ADR-0007、ADR-0011）。そして ADR-0007 は明示的に、
「第三者がコネクタを独立して出荷できる」ことを想定していた。しかし、その仕組みは
存在しなかった。SDK モジュールはタグ付けされておらず、モノレポの
ワークスペースを通じてのみ消費される。コンポジションルートは **組み込みのファーストパーティ**の
プラグインバイナリ（`go:embed`）のみを起動する。`LoadSourcePlugin` は渡された任意のパスを
**整合性やプロベナンスのチェックなし**に実行し、モジュール XIV のカタログは
内部エントリのみをキュレーションする。「自分のチームやパートナーがコネクタを
ビルドして公開できるか？」という問いに答えは存在しなかった。

エコシステムを開くことは、「ホストがオペレーターの指す任意の `.so` 形式バイナリを
ロードする」ことを意味してはならない。これはセキュリティ製品である。署名されず証明されていない
実行可能ファイルが観測プレーンに組み込まれれば、それはサプライチェーンの穴となる。

## 決定の要因

- 多様性という堀（amplitude moat）は、第三者が安全にコネクタを貢献できる場合にのみ
  **構成される**（`ARCHITECTURE.md`、`LICENSING.md`）。
- ライセンス境界（connector = Apache、`/core` を決して import しない）は、当社の CI だけでなく
  **第三者によって**検証可能でなければならない。
- 署名 + アドミッションの機構はすでに存在し、実績がある（モデルアドミッション、
  MCP エントリアドミッション、`core/secure/modelsign`）。再実装せず再利用する。
- v1 ではホスト型マーケットプレイスのインフラは設けない（商用判断は先送り）。

## 検討した選択肢

- **選択肢 A — ホスト型マーケットプレイスサービス**: Olivares.AI が運用する、
  アップロード/レビュー/配信を備えたレジストリサービス。
- **選択肢 B — SDK + 認証 + 署名、GitHub
  releases/OCI 上での配布、ドキュメントサイト内のキュレーションされた静的な「検証済みコネクタ」インデックス。
  ホスト側での deny-closed な署名付きアドミッション。**
- **選択肢 C — オープンなプラグインロード**（オペレーター提供のパス、署名なし）、
  認証はドキュメントのみとする。

## 決定の結果

選択した選択肢: **選択肢 B**（2026-06-09 に決定）。

1. **公開 SDK 契約。** `sdk` と `sdk/plugin` は、コネクタ作者向けに **安定版 v1**
   として宣言され、明示的なバージョニング/非推奨ポリシーを伴う
   （`sdk/VERSIONING.md`、ドキュメントサイトの安定性ページに掲載）。Semver
   タグ（`sdk/v1.*`、`sdk/plugin/v1.*`）はリポジトリの最初の公開リリースとともに
   到着する。それまでは作者はコミットを固定する（スキャフォールドの
   `-sdk-path` が開発ループをカバーする）。
2. **スキャフォールド + ガイド。** 依存ゼロのジェネレータ
   （`sdk/scaffold`、CLI `olivares-connector-new`）が、ツリー外の完全な
   コネクタリポジトリを生成する——契約に準拠したソース/出力スケルトン、ライフサイクル
   テスト、プラグインの `main`、README、そして**スタンドアロンの境界チェック**（当社の CI で
   `scripts/check-boundary.sh` が強制するのと同じ `go list -deps` ルール。これにより
   第三者は *自分の* CI で AGPL/Apache の境界を検証する）。
3. **配布チャネル。** リリースされたコネクタは **GitHub release
   アセット**（バイナリ + `sha256` + Sigstore アテステーションバンドル）として、かつ/または **OCI
   アーティファクト**（ORAS、referrer としてのアテステーション）として出荷される。v1 ではホスト型マーケットプレイスはない。
4. **署名付きアドミッション、ホストで deny-closed。** 外部プラグインが実行されるのは、
   オペレーターの sources 設定がそのダイジェストを固定し、かつ そのダイジェストに対する
   Sigstore/DSSE サプライチェーンアテステーション（SLSA プロベナンス / SBOM 述語）が、
   オペレーターが設定した信頼ポリシー（`connector_trust`）に対して検証された場合のみである。
   `modelsign.VerifyAttestation` を再利用する。ローダーはさらに実行時にチェックサムを
   固定する（go-plugin の `SecureConfig`）。**外部バイナリには observe モードも、
   署名なしを許可する抜け道も存在しない** — 開発ループは「自分の鍵で署名し、
   自分の公開鍵を信頼する」（bare-key モード）である。
5. **認証レコード（カタログオーバーレイ）。** モジュール XIV は `connector` という
   エントリ種別を獲得し、独自のアドミッションペアを持つ
   （`catalog.connector_admission_policy` / `catalog.connector_admission`）。
   エントリごとの検証済みプロベナンス/SBOM の判定、deny-closed な承認ゲート、
   observe モードのデフォルト——ホストの exec ゲートから切り離された、テナント向けの認証証跡である
   （多層防御。モデルアドミッションの admit-route + deployment-gate ペアと同様）。
6. **検証済みコネクタインデックス。** ドキュメントサイト内の**キュレーションされた静的ページ**
   （`reference/verified-connectors`）が、メンテナがそのリリースを再検証した
   （境界、署名、プロベナンス、最小データレビュー）サードパーティコネクタを一覧する。
   掲載はプルリクエストによって行われる。このインデックスは実施された検証の
   ドキュメントであり、信頼の起点では**ない** — オペレーターは依然として
   `connector_trust` で発行者のアイデンティティ/鍵を固定する。

### 帰結

- **良い点:** 第三者は AGPL エンジンに触れることなくコネクタをビルド・署名・出荷できる。
  ホストは証明されていないコードを決して実行しない。認証は実績のある機構を再利用する。
  運用すべき新サービスはゼロである。
- **悪い点／トレードオフ:** ドキュメント + releases を超える発見/インストールの UX はない（
  ホスト型マーケットプレイスならそれを提供できる）。オペレーターは信頼アンカーを手作業で管理する。
  外部の**出力**コネクタも同じ方法でビルド・出荷されるが、ホスト側の
  外部配線はまず観測ソースをカバーする（notify のコンポジションには
  まだ外部プラグインの経路がない）。
- **中立／フォローアップ:** ホストによる OCI の *pull*（現在はオペレーターが
  バイナリをディスクに置く。ダイジェスト固定により、トランスポートは信頼にとって無関係になる）、
  プロセス外モジュールは未配線のまま、コネクタアドミッションから探査される
  コンプライアンス能力、公開エクスポート時の npm スコープ `@olivaresai` と module-proxy タグ。

## 代替案を却下した理由

- **選択肢 A** — マーケットプレイスの運用は、明示的に先送りされた商用上のコミットメントである。
  v1 の需要がないまま、信頼上クリティカルなサービスを追加することになる。
- **選択肢 C** — 「任意のバイナリをロードする」ことは、まさにこの製品が
  ふさぐために存在するサプライチェーンの穴である。強制を伴わない散文としての認証は、
  監査向けの見せかけ（design-for-audit theater）にすぎない（`docs/SECURITY-HARDENING.md`）。
