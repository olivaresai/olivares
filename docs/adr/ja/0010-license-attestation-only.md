# ADR-0010: ライセンスはアテステーションのみ — 機能を決してゲートしない

- **Status:** accepted
- **Date:** 2026-06
- **Deciders:** Fran Olivares
- **References:** licensing design (final decision); API/authz/audit contract (§7, §13.5)

## コンテキストと課題

商用のオープンコア製品は、ライセンス強制が実行時に*何をするか*を決めなければならない。
誘惑となるのは、ライセンスチェックの背後に機能をゲートすることである。セキュリティ製品
であり、かつ認可バイパスの潜在的な攻撃面でもある製品にとって、これは「純粋なデュアル
ライセンス、何も制限しない」という哲学と相反する。

## 意思決定の要因

- オープン製品を不完全にしない。
- ライセンス検証を認可バイパスの攻撃面にしない。
- ライセンスサーバーなしで、air-gapped（エアギャップ）環境で動作させる。

## 検討した選択肢

- **アテステーションのみのライセンス検証**。何もブロックしない。
- ライセンス階層による**機能ゲーティング**。

## 決定の結果

選択した選択肢: **アテステーションのみ**。ライセンス検証は保有者とステータスを記録する
情報提供的なものであり、いかなるリクエスト・モジュール・ブートも**無効化・劣化・ブロック
しない**、ただし対象は**オープン（AGPL）バイナリ内**である。検証は**オフライン**（Ed25519
署名、ライセンスサーバーなし）で行われる。オープンバイナリは完全な CORE ガバナンス
プラットフォームであり、商用エディションは独立した追加的な `enterprise/` アドオンを加える
（これはオープンコアであり、「同一の完全な製品」ではない。下記の改訂および ADR-0011 を参照）。

### 帰結

- **良い点:** オープン製品が決して不完全にされない。ライセンスチェックを認可バイパスに
  転用できない。製品は air-gapped 環境で動作する。
- **悪い点 / トレードオフ:** 商用上の差別化は、コアのゲーティングではなく、*ライセンス
  条項*と独立した `enterprise/` モジュールから生まれる。
- **中立:** ライセンステストは設計上 fail-open（フェイルオープン）である。

## 代替案を却下した理由

- **機能ゲーティング** — オープン版をより劣った製品にし、信頼を損ない、なりすまし可能な
  ライセンスをセキュリティ上重要なゲートに変えてしまう。却下。

## 改訂 (2026-06-23)

この ADR は、対象を正確に限定して引き続き有効である。**ライセンスキーは決してオープン
バイナリをゲートしない。** モデルは**オープンコア**（ADR-0011 の改訂）であるため、以前の
「無償版とライセンス版は同一の完全な製品」という表現は不正確であり、上で訂正した。商用
エディションには追加的な `enterprise/` アドオンがある（これはこの ADR が常に述べてきた
「独立した `enterprise/` モジュール」である）。アテステーション済みの claim を*消費*するのは
クローズドな enterprise ビルドだけであり、その追加的なアドオンの権利付与にのみ用いる。これは
顧客自身の商用ビルド内でのローカルな判断である。Olivares 自身のクラウドも、請求のために
自己申告されたステータスを決して信頼してはならない。

**改訂 (2026-07-27, B10).** この注記が以前説明していた唯一の座席に関する消費、すなわち
community のユーザー座席上限を解除するために `enterprise/seats` が
`license.Claims.MaxUsers` を読むことは、なくなった。セルフホストのユーザーアカウントは
すべてのエディションで無制限であり、上限 3 は撤廃され、`MaxUsers` はどこでも表示専用である。
これはこの ADR を限定するのではなく強化する。オープン、商用を問わず、どのビルドも現在は
ユーザーを上限設定するためにライセンスを読まない。`LICENSING.md`
および 商用価格カノン（非公開で管理） を参照。
