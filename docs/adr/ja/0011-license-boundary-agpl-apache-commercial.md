# ADR-0011: ライセンス境界 — AGPL の製品、Apache の SDK/コネクター、商用の enterprise

- **Status:** accepted
- **Date:** 2026-06
- **Deciders:** Fran Olivares
- **References:** licensing design (final decision); stack license boundary

## コンテキストと課題

本製品には、製品を真にオープンに保ち、サードパーティのコネクターエコシステムをコピーレフト
の摩擦から解放し、かつ機能ゲーティングなしにクリーンな商用パスを残すライセンスモデルが
必要だった（ADR-0010 を参照）。

## 意思決定の要因

- 真にオープンでコピーレフトな製品（ソースアベイラブルでも、不完全でもない）。
- サードパーティが自由に拡張できる、寛容（permissive）なコネクターエコシステム。
- それを必要とする者のための、クリーンな商用例外。

## 検討した選択肢

- **純粋なデュアルライセンス:** AGPL の製品 + Apache-2.0 の SDK/コネクター + 商用例外。
- **機能ゲート型のオープンコア**（MIT/Apache のコア + 有償機能）。
- **すべてを寛容に**（MIT/Apache のコア）。
- **ソースアベイラブル**（BSL、SSPL、PolyForm）。

## 決定の結果

選択した選択肢: **純粋なデュアルライセンス**。`core/`、`modules/`、`web/` は
**AGPL-3.0-only**、`sdk/` と `connectors/` は **Apache-2.0**、`enterprise/` は
**商用**（`LicenseRef-Olivares-Commercial`）。この境界は、最初のコミットからファイル単位の
SPDX ヘッダーと CI チェックによって強制される。すなわち、Apache-2.0 のコネクターは
AGPL のエンジンを**決して** import しない。

### 帰結

- **良い点:** 製品は真にオープンでコピーレフトである。コネクターは寛容かつ摩擦のない
  ままである。境界は機械的に強制される。何も制限することなく商用パスが存在する。
- **悪い点 / トレードオフ:** コントリビューターは SPDX ヘッダーを正しく保ち、import
  境界を尊重しなければならない（CI が違反を検出する）。
- **中立:** 商用例外はセルフサービスに加えて、enterprise への問い合わせ窓口がある。

## 代替案を却下した理由

- **機能ゲート型のオープンコア** — 製品を制限する（ADR-0010 を参照）。却下。
- **すべてを寛容に** — 商用上の足場なしにコアを与えてしまう。
- **ソースアベイラブル（BSL/SSPL/PolyForm）** — OSS ではなく、コネクターエコシステムが
  依存する普及（アダプション）を断ち切ってしまう。

## 改訂 (2026-06-23) — モデルはオープンコアである

上記の**ライセンス境界は変更されておらず、正しい**。`core/`+`modules/`+`web/` は
AGPL-3.0-only、`sdk/`+`connectors/` は Apache-2.0、`enterprise/` は商用であり、Apache
コネクターは決して AGPL エンジンを import しない。訂正するのは*位置付け*である。出荷される
製品は**オープンコア**（GitLab の `ee/` モデル）であり、機能差のない「純粋なデュアル
ライセンス」では**ない**。AGPL ビルドは完全なガバナンスプラットフォームであり、アップセルの
ために内部から不完全にされることは決してない。しかし商用エディションと**同一ではない**。
`enterprise/` 系統（マルチ IdP フェデレーション、コンテンツファイアウォール/DLP、hook の
堅牢化、脅威インテリジェンスフィード、サーバーツールの egress、CyberArk Conjur、インシデント
クローズドループ）は、**オープンビルドには一度も存在しなかった追加的新規コード**である
（ラグプルではない）。したがって、「検討／選択: 純粋なデュアルライセンス」は AGPL/Apache の
*境界*に関する決定として読むべきであり、オープン版と商用版という*エディション*の決定は
オープンコアである。`LICENSING.md` を参照。

この ADR のライセンス**境界**は置き換えられない。別途変更されたのは商用系統の**配布**である。
`enterprise/` のソースは公開リポジトリに出荷されなくなり、ビルドタグによるゲーティングを
見せかけではなく実効的にするため、非公開リポジトリへ移動した。これは**ADR-0020** に記録した
配布上の決定であり、境界とアテステーション専用ライセンス（ADR-0010）は変わらない。

## 改訂 (2026-07-28) — 2026-06-23 の注記にある二つの失効した主張

上記のライセンス境界とオープンコアの位置付けは有効である。2026-06-23 の改訂にある
enterprise のリスト中の二項目はもはや製品を説明していない。ただし注記自体は、当時信じられて
いたことの時点付き記録であるため、書かれたとおりに残す。

1. **「community のユーザー上限を解除する座席の権利付与」は、もはや存在しない。** 決定 B10
   （2026-07-27）によりユーザー上限は完全に撤廃された。セルフホストのアカウントはすべての
   エディションで無制限であり、`core/auth.CommunitySeatLimit` は `0`、
   `enforceSeatCapTx` は無条件の no-op で、オープン、商用を問わずどのビルドもユーザーを
   上限設定するためにライセンスを読まない。現在の決定:
   商用価格カノン（非公開で管理）（`self_hosted.users: unlimited`）および
   `LICENSING.md`。
2. **「脅威インテリジェンスフィード」は、この add-on をどのように販売できるかを表すものでは
   ない。** `enterprise/threatintel` はビルドにコンパイルされたベースカタログに加えて、
   オペレーターが発行者キーをピン留めして適用する、オプションの署名済み・バージョン付き
   フィードアーティファクトを出荷する。Olivares はキュレートされたフィード配布を運営せず、
   リリース頻度も公表しない。商用カノン（商用価格カノン（非公開で管理）,
   `self_hosted.business.preset`）は、実際に署名済みフィードが運用されない限り、これを「フィード」
   として販売することを禁じている。オペレーター CLI は検証・適用するアーティファクトの名称と
   してこの語を維持する（`olivares threatintel verify|apply|pull`）。これはアーティファクトの
   名称であり、誰が公開するかについての主張ではない。

どちらの項目も、この ADR が決定するライセンス境界には影響しない。
