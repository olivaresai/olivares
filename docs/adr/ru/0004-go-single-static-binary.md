# ADR-0004: Движок на Go, один статический бинарник со встроенным веб

- **Status:** accepted
- **Дата:** 2026-06
- **Принявшие решение:** Fran Olivares
- **Ссылки:** реестр решений по стеку (T1, T5); архитектура стека

## Контекст и постановка задачи

Самостоятельно размещаемый (self-hosted), дружественный к air-gap control plane для
безопасности должен тривиально развёртываться, быть нативным для экосистемы
eBPF/OpenTelemetry/cloud-native и поставляться как один артефакт. Язык движка и способ
доставки UI оба следуют из этого.

## Движущие факторы решения

- Единый самодостаточный артефакт для self-hosting и air-gap.
- Нативный eBPF и зрелая среда выполнения модулей/плагинов.
- Сильная конкурентность для приёма данных (ingest) и шины событий.

## Рассмотренные варианты

- **Go**, один статический бинарник, веб встроен через `go:embed`.
- Движок на **Rust**.
- Движок на **Node/TypeScript**.
- **Отдельное SPA** (два артефакта) вместо встроенного UI.

## Принятое решение

Выбранный вариант: **Go**, скомпилированный в один статический бинарник, с веб-UI на
React, **встроенным через `go:embed`** и обслуживаемым с того же origin, что и API, —
так что весь продукт представляет собой **один файл**.

### Последствия

- **Хорошо:** один артефакт для поставки, проверки и запуска; нативный eBPF; отличная
  совместимость с cloud-native; конкурентность, подходящая для ingest.
- **Плохо / компромиссы:** UI собирается и встраивается как часть сборки бинарника.
- **Нейтрально:** Node/TypeScript используется только для веб-UI, а не для движка.

## Почему альтернативы были отклонены

- **Rust** — более медленная сборка/итерация и избыточен для потребностей v1.
- **Движок на Node/TS** — слабая поддержка eBPF и невозможность единого статического
  бинарника, несмотря на то что это зона комфорта.
- **Отдельное SPA** — два артефакта для развёртывания и версионирования; встроенный UI
  оставляет всё одним файлом.
