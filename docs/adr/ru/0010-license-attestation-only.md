# ADR-0010: Лицензия служит только для подтверждения — никогда не ограничивает возможности

- **Status:** accepted
- **Date:** 2026-06
- **Deciders:** Fran Olivares
- **References:** licensing design (final decision); API/authz/audit contract (§7, §13.5)

## Контекст и постановка проблемы

Коммерческий продукт с открытым ядром (open-core) должен решить, что именно *делает*
принудительное применение его лицензии во время выполнения. Велик соблазн ограничивать
возможности за проверкой лицензии. Для продукта в области безопасности, который к тому же
является потенциальной поверхностью обхода авторизации, это вступает в противоречие с
философией «чистой двойной лицензии, без каких-либо ограничений».

## Факторы, определяющие решение

- Не урезать открытый продукт.
- Не превращать проверку лицензии в поверхность обхода авторизации.
- Работать в изолированном (air-gapped) режиме, без сервера лицензий.

## Рассмотренные варианты

- **Проверка лицензии только для подтверждения**, которая никогда ничего не блокирует.
- **Ограничение возможностей** по уровню лицензии.

## Итоговое решение

Выбранный вариант: **только подтверждение**. Проверка лицензии регистрирует владельца и
статус и носит информативный характер; она **никогда не отключает, не ухудшает и не
блокирует** ни один запрос, модуль или запуск **в открытом (AGPL) бинарном файле**.
Проверка выполняется **офлайн** (подпись Ed25519; без сервера лицензий). Открытый
бинарный файл — это полная платформа управления CORE; коммерческая редакция добавляет
отдельные, аддитивные add-on'ы `enterprise/` (это открытое ядро, а не «один и тот же
полноценный продукт» — см. поправку ниже и ADR-0011).

### Последствия

- **Плюсы:** открытый продукт никогда не урезается; проверки лицензии нельзя превратить
  в обход авторизации; продукт работает в изолированном (air-gapped) режиме.
- **Минусы / компромиссы:** коммерческая дифференциация достигается за счёт *условий
  лицензии* и отдельных модулей `enterprise/`, а не за счёт ограничения ядра.
- **Нейтрально:** тесты лицензии по своей конструкции работают по принципу fail-open.

## Почему альтернативы были отклонены

- **Ограничение возможностей** — делает открытую редакцию худшим продуктом, подрывает
  доверие и превращает подделываемую лицензию в значимый для безопасности барьер.
  Отклонено.

## Поправка (2026-06-23)

Этот ADR остаётся в силе при точном определении области: **лицензионный ключ никогда не
ограничивает ОТКРЫТЫЙ бинарный файл.** Модель — **открытое ядро** (поправка к ADR-0011),
поэтому прежняя фраза «бесплатный и лицензированный продукты — это один и тот же
полноценный продукт» была неточной и исправлена выше: в коммерческой редакции есть
аддитивные add-on'ы `enterprise/` (это именно «отдельные модули `enterprise/`», которые
этот ADR всегда называл). Аттестованное утверждение *потребляется* только закрытой
enterprise-сборкой и лишь для предоставления прав на эти аддитивные add-on'ы — это
локальное решение в собственной коммерческой сборке клиента. Облако Olivares также
никогда не должно доверять самостоятельно заявленному статусу при выставлении счетов.

**Поправка (2026-07-27, B10).** Единственный связанный с местами случай потребления,
который ранее описывала эта заметка, — чтение `enterprise/seats`
`license.Claims.MaxUsers` для снятия лимита пользовательских мест community — исчез:
самостоятельно размещаемые учётные записи пользователей НЕ ОГРАНИЧЕНЫ в каждой редакции,
лимит 3 удалён, а `MaxUsers` повсюду используется только для отображения. Это усиливает
данный ADR, а не уточняет его: теперь ни одна сборка, открытая или коммерческая, не читает
лицензию, чтобы ограничивать пользователей. См.
`LICENSING.md` и коммерческий канон цен (ведётся приватно).
