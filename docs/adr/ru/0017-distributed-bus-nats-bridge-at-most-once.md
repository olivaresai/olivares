# ADR-0017: Распределённая шина событий = локальный in-proc fan-out + мост NATS, core NATS at-most-once (без JetStream в v1)

- **Status:** accepted (вносит поправку в строку семантики доставки из ADR-0006) —
  **расширено ADR-0021**, которая поставляет backend JetStream с доставкой at-least-once
  как закрытое enterprise-дополнение и устраняет проблему безопасности при дубликатах
  дедупликацией на границе шины (а не ожидавшейся ниже идемпотентностью каждого
  подписчика); этот ОТКРЫТЫЙ мост Core NATS остаётся at-most-once и не меняется.
- **Дата:** 2026-06-12
- **Принявшие решение:** дизайн под нагрузочным давлением 3-линзовой состязательной панели до реализации
- **Ссылки:** `docs/contracts/S02-sdk-runtime-eventbus.md §4`,
  `core/eventbus/natsbus`, перепись идемпотентности подписчиков (recon, 2026-06-12)

## Контекст и постановка проблемы

ADR-0006 оставил шину in-proc со слотом для NATS. HA поставлена, так что мультинодовость
существует — а шина не пересекает ноды: событие, опубликованное на standby (фоновые источники,
свипы идентичностей), никогда не достигает обработки на лидере; захват платформы событий —
граница долговечности — молча его пропускает. Два вопроса требовалось закрыть доказательствами,
а не значениями по умолчанию: **(a)** заменяет распределённый бэкенд локальный путь доставки или
служит ему мостом, и **(b)** core NATS (at-most-once) или JetStream (at-least-once)?

ADR-0006 зафиксировал шину как «at-least-once; потребители дедуплицируют». **Эта строка была
неверна как описание реализации**: in-proc шина — это at-most-once (ошибки обработчиков логируются,
а не повторяются; поставленные в очередь события сбрасываются при закрытии — `core/eventbus/inproc.go`),
контракт S02 §4 документирует блокирующее обратное давление БЕЗ повторной доставки, а
`modules/eventing/capture.go` гласит, что «сама шина — at-most-once (S02), и повтор начинается
ОТ захвата». Фраза at-least-once в ADR-0006 описывала повторную эмиссию на уровне источника
(`Gather` перезапускается), а не доставку по шине.

## Факторы решения

- Перепись подписчиков от 2026-06-12: большинство из ~17 подписчиков шины НЕ безопасны при
  дубликатах (eventing захватывает дважды, security/notify сохраняют или отправляют дубликаты,
  свёртки count/aggregate раздуваются). Доставка at-least-once СЕГОДНЯ была бы семантической
  регрессией, поданной как апгрейд.
- Письменная гарантия S02 §4 — Publish блокируется при насыщении, «терять события молча было бы
  хуже, чем тормозить публикующего» — несущая: `olivares_ingest_duration_seconds` документирован
  как ТОТ САМЫЙ SLI обратного давления (docs/17 §1.4), а руководство по обратному давлению
  коллектора гласит «события не теряются — шина блокирует, а не сбрасывает». Маршрутизация
  локального горячего пути через сервер инвертировала бы этот контракт на 100% продакшн-трафика
  (балансировщик дренирует standby).
- Трафик, ради спасения которого существует бэкенд (события с происхождением на standby) — это
  НИЗКОобъёмный путь; локальный путь — горячий. Дизайн не должен менять горячий путь на холодный.

## Рассмотренные варианты

- **A. Чистый транспорт NATS** — каждый publish/subscribe проходит через сервер; один путь кода.
  Отклонён: инвертирует S02 §4 на локальном пути (молчаливые сбросы медленных потребителей там,
  где контракт обещает блокировку без потерь), добавляет окна потерь при рестарте/переподключении
  сервера к доставке внутри той же ноды и обесценивает смысл SLI ingest.
- **B. Гибрид: локальный in-proc fan-out + мост NATS с NoEcho (ВЫБРАН).**
- **C. JetStream (at-least-once)** — отклонён для v1: перепись показывает, что подписчики не
  безопасны при дубликатах; JetStream становится доступной работой ТОЛЬКО ПОСЛЕ прохода по
  идемпотентности подписчиков (отслеживается как явный путь апгрейда ниже).

## Итог решения

Выбранный вариант: **B + core NATS**. `core/eventbus/natsbus` встраивает in-proc шину: Publish
сначала раздаёт локально (каждая гарантия S02 §4 цела — блокирующее обратное давление, ноль
локальных потерь, изоляция паник, никакого кодека на горячем пути), затем мостит событие в NATS
по принципу best-effort. Соединение моста выставляет **NoEcho**, поэтому его единственная
wildcard-подписка получает только события с УДАЛЁННЫМ происхождением, которые оно
ре-материализует (замороженный proto `Event` oneof для трёх payload'ов наблюдения, JSON +
реестр декодеров для типов, определённых модулями) и инжектит в локальный fan-out — никакой
двойной доставки, порядок по каждому публикующему сохранён между типами (одно соединение на
ноду, одна упорядоченная подписка).

**Межнодовая семантика, документированная честно: at-most-once.** Окна потерь: рестарт сервера
NATS (нет персистентности), переполнение буфера переподключения/так и не переподключившийся
(«буферизовано ≠ доставлено») и сбросы медленного потребителя, когда буфер ожидания подписки
моста заполняется — каждое посчитано (`olivares_eventbus_bridge_*`) и алертируемо, никогда не
молча. HA: удалённые события **инжектятся только на лидере**
(`SetInjectGate(store.Leader().Active)`), что убивает класс побочных эффектов на стороне standby
(дубликаты уведомлений, дубликаты производных находок, штормы логов ErrNotLeader) на границе
шины; перекрытие ≤2s при переключении может инжектить дважды, что поглощается уникальным
индексом `(tenant_id, event_id)` захвата eventing. Конфигурация (`OLIVARES_BUS_CONFIG`) —
fail-boot-closed: нода, которая молча откатилась бы на in-proc, работала бы в разбиении
(partitioned).

### Последствия

- **Хорошо:** наблюдения с происхождением на standby достигают лидера (закрывая межнодовый
  разрыв); единичный однонодовый бинарник по умолчанию байт-в-байт не затронут; семантика
  локальной доставки без изменений; межнодовые потери посчитаны, а не молчаливы.
- **Плохо / компромиссы:** межнодовый путь упражняется только трафиком с происхождением на
  standby — его путь кодека/инжекта несёт выделенные интеграционные тесты (встроенный
  nats-server) именно потому, что продакшн упражняет его редко; мостовые события добавляют одно
  кодирование на publish на нодах С настроенным мостом.
- **Нейтрально:** JetStream остаётся путём апгрейда до at-least-once, заблокированным проходом по
  идемпотентности подписчиков (перепись — это список работ); интерфейс `Bus` ничего не приобрёл —
  Stats и именованные подписки являются опциональными расширяющими интерфейсами.

## Почему альтернативы были отклонены

См. факторы: A инвертирует письменный контракт на горячем пути, чтобы упростить холодный; C
поставляет дубликаты подписчикам, которые доказуемо обращаются с ними неверно.
