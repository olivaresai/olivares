# ADR-0008: Непрозрачные серверные токены, а не JWT, для собственной аутентификации

- **Status:** accepted
- **Date:** 2026-06
- **Deciders:** Olivares AI (confirmed by adversarial review)
- **References:** API/authz/audit contract (§2, decision §13.2)

## Контекст и постановка проблемы

Требовалось выбрать механизм собственной аутентификации. В первоначальном объёме упоминались
«sessions/JWT». Для продукта в области безопасности режимы отказа bearer-учётных данных —
отзыв, утверждения (claims), несущие секреты, риск библиотеки разбора — имеют большое значение.

## Факторы, влияющие на решение

- Немедленный отзыв.
- Отсутствие секретов внутри токена.
- Минимальная поверхность атаки на криптографический разбор; безопасность по умолчанию.

## Рассмотренные варианты

- **Непрозрачные серверные токены** (случайный секрет, хранимый в хешированном виде, проверяемый на стороне сервера).
- **JWT** для собственных сессий.

## Принятое решение

Выбранный вариант: **непрозрачные серверные токены** для собственной аутентификации. Токены имеют префикс
по назначению (`olvs_` — сессия, `olvk_` — ключ API); сервер хранит только публичный селектор
и SHA-256 секрета, сравнивая их за постоянное время. JWT ограничен
стыком SSO/федерации, а не собственными сессиями.

### Последствия

- **Хорошо:** токены отзываемы, не несут секретов и не требуют криптографического разбора
  предоставленных злоумышленником утверждений; безопасность по умолчанию.
- **Плохо / компромиссы:** проверка требует обращения на стороне сервера (приемлемо для
  control plane (плоскости управления)).
- **Нейтрально:** федерация по-прежнему использует JWT там, где этого требует протокол.

## Почему альтернативы были отклонены

- **JWT для собственных сессий** — сложно отозвать до истечения срока, склонны нести
  утверждения и добавляют поверхность атаки на разбор/проверку без какой-либо выгоды здесь.
