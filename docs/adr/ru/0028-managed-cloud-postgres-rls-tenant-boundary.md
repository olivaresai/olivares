# ADR-0028: База данных managed cloud — управляемый PostgreSQL с row-level security как границей между тенантами

- **Status:** accepted (managed cloud; this record creates no infrastructure)
- **Date:** 2026-08-02
- **Deciders:** Fran Olivares
- **References:** ADR-0005 (SQLite by default, PostgreSQL at scale), ADR-0027
  (managed-cloud ingress), ADR-0029 (managed-cloud regions), ADR-0022 (source-scoping
  subject axes); the platform decision record for the managed cloud; PostgreSQL
  documentation on row security policies and the AWS database guidance on multi-tenant
  isolation with row-level security, consulted 2026-08-02:
  `https://aws.amazon.com/blogs/database/multi-tenant-data-isolation-with-postgresql-row-level-security/`.

## Контекст и постановка проблемы

ADR-0005 уже определил PostgreSQL как хранилище продукта при масштабировании, а в
продукте уже есть механизм row-level security для scoping по тенантам. Для managed cloud
не нужна новая модель данных; требуется решение о том, **кто эксплуатирует базу данных**
и **на что именно мы полагаемся, чтобы строки одного тенанта были недоступны другому**.

Вторая часть важнее первой. «Мы используем row-level security» не является свойством,
пока роли не организованы так, чтобы политики действительно применялись. PostgreSQL
исключает из политик таблицы две категории вызывающих сторон: superusers и роли с
атрибутом `BYPASSRLS`; кроме того, по умолчанию **владелец таблицы ОБХОДИТ RLS, если
только для таблицы не задано `FORCE ROW LEVEL SECURITY`**. Поэтому у приложения,
которое подключается под ролью, создавшей схему, *нет* изоляции тенантов, хотя кажется,
что она есть. Это самая дорогостоящая из возможных ошибок в данном дизайне, и она никак
себя не проявляет.

## Движущие факторы решения

- Изоляция тенантов должна обеспечиваться **базой данных**, а не тщательностью каждого
  будущего запроса.
- Единственный оператор не должен заниматься эксплуатацией PostgreSQL: обновления,
  failover и point-in-time recovery — именно та работа, от которой должно избавлять
  управляемый сервис.
- Восстановление должно быть свойством платформы, а не runbook, о запуске которого
  кому-то нужно помнить.
- Любое утверждение об изоляции должно быть **тестируемым извне приложения**.

## Рассмотренные варианты

- **A — самостоятельно управляемый PostgreSQL на virtual machines.** Полный контроль,
  минимальная удельная стоимость, и каждое обновление, каждая тренировка failover и
  проверка backup становятся нашей обязанностью.
- **B — managed PostgreSQL service облачного провайдера, multi-AZ**, с автоматическими
  backup и point-in-time recovery.
- **C — PostgreSQL-compatible cluster service провайдера** (архитектура с общим
  хранилищем и оплатой I/O за запрос в стандартной конфигурации).
- **D — сторонняя PostgreSQL platform**, доступная из того же региона.

## Результат решения

Выбранный вариант: **B — managed PostgreSQL, multi-AZ**, с row-level security как
границей между тенантами; приведённая ниже схема ролей считается частью решения, а не
деталью реализации.

Схема ролей является нормативной:

1. Приложение подключается под ролью, которая **не владеет** таблицами со scope по
   тенанту и **не имеет `BYPASSRLS`**.
2. На каждой таблице со scope по тенанту задано **`FORCE ROW LEVEL SECURITY`**, поэтому
   одно лишь владение не позволяет обойти политику; это защищает от будущей migration,
   которая изменит владельца таблицы.
3. Административная роль для migrations — не та роль, которая указана в строке
   подключения приложения.
4. **Область действия, указанная явно, чтобы её никогда не предполагали:** эта запись
   регулирует **плоскость данных тенантов** — схему со строками, принадлежащими тенантам,
   для которой engine уже генерирует `ENABLE ROW LEVEL SECURITY`, `FORCE ROW LEVEL SECURITY`
   и отдельную для каждого тенанта политику, привязанную к настройке сессии.
   **Собственные управляющие метаданные** managed plane (реестр тенантов, журнал
   биллинга, снимки использования) находятся в **отдельной схеме с отдельной моделью
   изоляции**: сегодня она полагается на scoping на уровне приложения с единственной
   ролью приложения и без SQL, доступного тенантам. Это вполне может быть правильным
   решением для управляющих метаданных, однако сейчас такая модель **унаследована, а не
   определена решением**, и это не то, что подразумевает для читателя фраза «мы используем
   row-level security». Тот, кто строит managed plane, должен **письменно указать, какая
   модель действует для этой схемы и почему**, прежде чем в ней будут храниться записи
   платящего клиента.

### Последствия

- **Плюс:** обновления, multi-AZ failover, автоматические backup и point-in-time recovery
  становятся свойствами платформы. Disaster-recovery runbook, поставляемый с продуктом,
  остаётся артефактом для self-hosted развёртываний, но перестаёт быть ежедневной
  эксплуатационной обязанностью managed plane.
- **Плюс:** изоляцию можно тестировать извне. Критерий приёмки — запрос, выполненный
  **под ролью приложения**, который пытается прочитать строки другого тенанта и не
  получает ни одной, а не утверждение в design document.
- **Минус / компромиссы:** более высокий постоянный месячный минимум, чем у обычной
  virtual machine, а обновления версии engine выходят по календарю провайдера, не по
  нашему.
- **Нейтрально:** административная роль managed service является привилегированной
  ролью базы данных, но **не** PostgreSQL superuser: у неё нет доступа к операционной
  системе, и она не может переписать конфигурацию аутентификации хоста. Это полезно
  сокращает blast radius, но row-level security обеспечивается не этим, а описанной выше
  схемой ролей.
- **Явно НЕ проверено, и предполагать это нельзя:** имеет ли эта административная роль
  `BYPASSRLS` на работающем engine. Это проверяется одним запросом
  (`SELECT rolbypassrls FROM pg_roles WHERE rolname = current_user;`) к реальному
  instance, и такая проверка относится к этапу, на котором instance впервые создаётся.
  Пока она не выполнена, ни в одном документе нельзя утверждать, что административная
  роль подчиняется политикам тенантов.

## Почему альтернативы были отклонены

- **A (самостоятельно управляемый PostgreSQL)** — отклонён, потому что возвращает ровно
  ту эксплуатационную нагрузку, которую managed plane должен поглотить, сосредоточив её
  на одном операторе: обновления версий, тренировки failover и проверка backup, которая
  реальна лишь тогда, когда кто-то регулярно выполняет восстановление из него.
  Преимущество в стоимости реально, но невелико в абсолютном выражении;
  эксплуатационный риск, напротив, не мал.
- **C (PostgreSQL-compatible cluster service)** — отклонён как преждевременный. Нагрузка
  представляет собой небольшую транзакционную схему с умеренной частотой записи;
  архитектура с общим хранилищем решает отсутствующие у этой нагрузки проблемы
  масштабирования, но имеет более высокий минимум и оплату I/O за запрос в стандартной
  конфигурации. Это остаётся естественным путём обновления, если частота записи
  когда-либо его оправдает.
- **D (сторонняя PostgreSQL platform)** — отклонён для основного хранилища. Поведение
  row-level security, модель superuser и доступные атрибуты ролей зависят от поставщика,
  и каждый из этих аспектов пришлось бы заново проверять относительно описанного выше
  свойства изоляции. Нет причин принимать специфичный для поставщика риск на той
  единственной границе, которая не должна дать сбой.
