# ADR-0016: Экосистема внешних коннекторов — публичный SDK, подписанный допуск, распространение через releases/OCI, курируемый проверенный индекс

- **Status:** accepted
- **Дата:** 2026-06-11
- **Принявшие решение:** Fran Olivares (объём v1 решён 2026-06-09)
- **Ссылки:** `LICENSING.md` (граница лицензии), ADR-0007 (рантайм go-plugin),
  ADR-0011 (AGPL/Apache/коммерческая), ADR-0015 (цепочка поставок),
  `docs/contracts/S02-sdk-runtime-eventbus.md`,
  `docs/contracts/S142-external-connector-sdk.md`

## Контекст и постановка проблемы

SDK коннекторов (`sdk`, `sdk/plugin`) с первого дня проектировался так, чтобы коннектор
никогда не линковался с движком под AGPL (Apache-2.0, ноль зависимостей, транспорт плагинов
по gRPC — ADR-0007, ADR-0011), и ADR-0007 явно предполагал, что «третьи стороны могут
поставлять коннекторы независимо». Но механизма не существовало: модули SDK не имеют тегов
и потребляются только через workspace монорепозитория, корень композиции запускает только
**встроенные first-party** бинарники плагинов (`go:embed`), `LoadSourcePlugin` исполняет любой
переданный ему путь **без проверки целостности или происхождения**, а каталог модуля XIV
курирует только внутренние записи. На вопрос «может ли моя команда или партнёр собрать и
опубликовать коннектор?» не было ответа.

Открытие экосистемы не может означать «хост загружает любой бинарник `.so`-вида, на который
укажет оператор»: это продукт безопасности; неподписанный, неаттестованный исполняемый файл,
встроенный в плоскость наблюдения, был бы дырой в цепочке поставок.

## Факторы решения

- Преимущество широты (amplitude moat) **складывается** только если третьи стороны могут
  безопасно вносить коннекторы (`ARCHITECTURE.md`, `LICENSING.md`).
- Граница лицензии (коннектор = Apache, никогда не импортирует `/core`) должна быть проверяема
  **самой третьей стороной**, а не только в нашем CI.
- Машинерия подписи + допуска уже существует и проверена (допуск моделей, допуск MCP-записей,
  `core/secure/modelsign`): переиспользовать, никогда не реализовывать заново.
- Никакой инфраструктуры размещённого маркетплейса в v1 (коммерческое решение отложено).

## Рассмотренные варианты

- **Вариант A — размещённый сервис-маркетплейс**: реестровый сервис, эксплуатируемый
  Olivares.AI, с загрузкой/ревью/раздачей.
- **Вариант B — SDK + сертификация + подпись, распространение через GitHub
  releases/OCI, курируемый статический индекс «проверенных коннекторов» на сайте документации;
  подписанный допуск по принципу deny-closed на хосте.**
- **Вариант C — открытая загрузка плагинов** (путь от оператора, без подписи),
  сертификация только как документация.

## Итог решения

Выбранный вариант: **Вариант B** (решён 2026-06-09).

1. **Публичный контракт SDK.** `sdk` и `sdk/plugin` объявляются **стабильными v1**
   для авторов коннекторов, с явной политикой версионирования/устаревания
   (`sdk/VERSIONING.md`, отражённой на странице стабильности сайта документации). Semver-теги
   (`sdk/v1.*`, `sdk/plugin/v1.*`) появятся с первым публичным релизом репозитория; до тех пор
   авторы закрепляют коммит (`-sdk-path` в скаффолде покрывает цикл разработки).
2. **Скаффолд + руководство.** Генератор без зависимостей
   (`sdk/scaffold`, CLI `olivares-connector-new`) выдаёт полный репозиторий коннектора
   вне дерева — корректный по контракту скелет источника/вывода, тест жизненного цикла,
   `main` плагина, README и **автономную проверку границы** (то же правило `go list -deps`,
   которое `scripts/check-boundary.sh` принуждает в нашем CI, так что третья сторона проверяет
   границу AGPL/Apache в *своём* CI).
3. **Канал распространения.** Выпущенный коннектор поставляется как **ассет GitHub
   release** (бинарник + `sha256` + комплект аттестаций Sigstore) и/или как **OCI-артефакт**
   (ORAS, аттестация как referrer). Никакого размещённого маркетплейса в v1.
4. **Подписанный допуск, deny-closed на хосте.** Внешний плагин запускается только
   если конфигурация источников оператора закрепляет его digest И аттестация цепочки поставок
   Sigstore/DSSE (предикат происхождения SLSA / SBOM) над этим digest проходит проверку по
   настроенной оператором политике доверия (`connector_trust`), переиспользуя
   `modelsign.VerifyAttestation`. Загрузчик дополнительно закрепляет контрольную сумму во
   время исполнения (go-plugin `SecureConfig`). **Нет режима наблюдения и нет лазейки
   allow-unsigned для внешних бинарников** — цикл разработки таков: «подпиши своим ключом,
   доверяй своему публичному ключу» (режим bare-key).
5. **Запись сертификации (наложение на каталог).** Модуль XIV получает вид записи `connector`
   со своей собственной парой допуска
   (`catalog.connector_admission_policy` / `catalog.connector_admission`):
   проверенные вердикты происхождения/SBOM по каждой записи, шлюз одобрения deny-closed,
   режим наблюдения по умолчанию — трасса сертификации, обращённая к тенанту, развязанная
   с exec-шлюзом хоста (эшелонированная защита, как пара admit-route + deployment-gate в
   допуске моделей).
6. **Индекс проверенных коннекторов.** **Курируемая статическая страница** на сайте
   документации (`reference/verified-connectors`) перечисляет коннекторы третьих сторон, чей
   релиз сопровождающие перепроверили (граница, подпись, происхождение, ревью минимизации
   данных). Включение — через pull request; индекс — это документация о проведённой
   верификации, **а не** корень доверия — операторы всё равно закрепляют идентичность/ключ
   издателя в `connector_trust`.

### Последствия

- **Хорошо:** третьи стороны собирают, подписывают и поставляют коннекторы, не касаясь
  движка под AGPL; хост никогда не исполняет неаттестованный код; сертификация переиспользует
  проверенную машинерию; ноль новых сервисов в эксплуатации.
- **Плохо / компромиссы:** нет UX обнаружения/установки помимо документации + релизов
  (размещённый маркетплейс дал бы такой); операторы управляют якорями доверия вручную; внешние
  **output**-коннекторы собираются и поставляются так же, но внешняя обвязка на стороне хоста
  покрывает в первую очередь источники наблюдения (у композиции notify пока нет пути для
  внешних плагинов).
- **Нейтрально / последующие шаги:** OCI *pull* хостом (сегодня оператор размещает бинарник
  на диске; закрепление digest делает транспорт нерелевантным для доверия); внепроцессные
  модули остаются неподключёнными; возможность compliance, зондируемая из допусков
  коннекторов; npm-scope `@olivaresai` и теги module-proxy при публичном экспорте.

## Почему альтернативы были отклонены

- **Вариант A** — эксплуатация маркетплейса — это коммерческое обязательство, которое было
  явно отложено; оно добавляет критичный для доверия сервис без спроса в v1.
- **Вариант C** — «загружай любой бинарник» — это ровно та дыра в цепочке поставок, которую
  этот продукт существует, чтобы закрыть; сертификация-как-текст без принуждения была бы
  театром «проектирования под аудит» (`docs/SECURITY-HARDENING.md`).
