# ADR-0027: Входящий трафик managed cloud — L4 passthrough для mTLS коллекторов, L7 для API control plane

- **Status:** accepted (managed cloud; this record creates no infrastructure)
- **Date:** 2026-08-02
- **Deciders:** Fran Olivares
- **References:** ADR-0012 (collectors push to the core over gRPC + mTLS), ADR-0028
  (managed-cloud database), ADR-0029 (managed-cloud regions), ADR-0009 (append-only
  hash-chained audit); the platform decision record for the managed cloud; AWS Elastic
  Load Balancing documentation, consulted 2026-08-02:
  `https://docs.aws.amazon.com/elasticloadbalancing/latest/network/network-load-balancers.html`,
  `https://docs.aws.amazon.com/elasticloadbalancing/latest/network/edit-target-group-attributes.html`,
  `https://docs.aws.amazon.com/elasticloadbalancing/latest/application/configuring-mtls-with-elb.html`.

## Контекст и постановка проблемы

ADR-0012 зафиксировал топологию приёма данных: коллекторы работают в инфраструктуре
клиента и **отправляют** наблюдения по gRPC с mutual TLS, а core **сам завершает этот
mTLS**.

Важно точно описать, что это даёт: неточная версия этой фразы ошибочна и, если в неё
поверить, стала бы критически важным допущением. Допуск в плоскость коллекторов опирается
на **два независимых фактора**:

1. **Транспортный барьер.** Сервер требует и проверяет клиентский сертификат, цепочка
   которого ведёт к настроенному CA коллекторов. Это доказывает владение ключом, для
   которого мы выпустили сертификат; сертификат не разбирается для получения субъекта и не
   обозначает никакого принципала.
2. **Bearer-принципал.** Аутентифицированная идентичность, с которой работают авторизация
   и audit chain (ADR-0009), поступает из bearer token запроса, а не из сертификата.

Оба фактора применяются **в собственном процессе продукта**. Ни один промежуточный
компонент не поручается ни за один из них. Именно об этом свойстве идёт речь в данном
документе: не «сертификат является идентичностью», а «ни один посредник не поручается ни
за один из факторов».

Managed cloud — первое развёртывание, в котором перед этим бинарником появляется load
balancer. То же развёртывание предоставляет и обычную публичную HTTPS-поверхность — REST
API, консоль, администрирование, — которой требуется противоположный подход: управляемый
публичный сертификат, web application firewall и маршрутизация по host/path. Один ingress
не может обслуживать оба случая, не пожертвовав чем-либо на одной из сторон.

## Движущие факторы решения

- Оба фактора допуска должны по-прежнему применяться посредством **TLS-сессии, которую
  завершает сам продукт**. Если managed cloud незаметно ослабит любой из них до «посредник
  сообщил нам, что всё в порядке», центральное утверждение продукта станет слабее.
- Публичная HTTP-поверхность должна иметь возможность использовать пограничные средства
  защиты L7, не заставляя продукт реализовывать их заново.
- Долгоживущие потоки коллекторов должны выдерживать поведение ingress при простое.
- Нельзя допустить регрессии относительно self-hosted развёртывания: один путь кода, а
  не два.

## Рассмотренные варианты

- **A — один L4 load balancer для всего.** TCP passthrough для обеих плоскостей; бинарник
  завершает каждую TLS-сессию, включая публичный API.
- **B — разделённый ingress.** **Сетевой (L4) load balancer с TCP listener** в режиме
  passthrough для плоскости коллекторов и **прикладной (L7) load balancer** для
  HTTP-поверхности control plane.
- **C — один L7 load balancer с управляемым mutual TLS.** Application load balancer сам
  аутентифицирует клиентские сертификаты (режим verify относительно trust store со
  списками отзыва) либо передаёт цепочку целевому сервису как HTTP header.

## Результат решения

Выбранный вариант: **B — разделённый ingress**.

### Последствия

- **Плюс:** плоскость коллекторов побайтово совпадает с self-hosted путём. TCP listener
  не завершает TLS, поэтому бинарник выполняет handshake и сам применяет требование
  сертификата — точно так же, как в локальном развёртывании. В авторизаторе нет отдельной
  cloud-specific ветви, а в audit chain — отдельного cloud-specific случая.
- **Плюс:** публичная поверхность может использовать управляемый сертификат, маршрутизацию
  по host/path и web application firewall, и продукту не приходится реализовывать их
  заново. Firewall — это услуга, которая **оплачивается отдельно**, а не бесплатное свойство
  L7 load balancer; здесь она указана как доступная, а не как включённая.
- **Плюс, с точно обозначенной областью действия:** idle timeout TCP listener
  **настраивается в диапазоне от 60 до 6000 секунд** (`tcp.idle_timeout.seconds`, значение
  по умолчанию — **350**); у TLS listener он **зафиксирован на 350 секундах, и изменить его
  нельзя**. Это timeout **бездействия** — отсутствия байтов, — **а не верхний предел
  продолжительности потока**: поток, который продолжает передавать данные или keepalive
  frames, не обрывается на отметке 350 секунд. Поэтому passthrough не «делает возможными
  долгие потоки»; он позволяет нам задавать бюджет бездействия. Если сформулировать наоборот,
  поскольку важна именно эта часть: **поток без трафика погибает на любом из этих ingress**,
  и клиент должен это пережить.
- **Минус и причина, по которой предыдущий пункт сформулирован как предупреждение:** клиент
  коллектора не настраивает **никакой gRPC keepalive** (по умолчанию в библиотеке он
  выключен), а после неудачной отправки сохраняет мёртвый поток в кэше вместо того, чтобы
  создать его заново. Поэтому период бездействия дольше настроенного timeout, смена лидера
  или развёртывание завершает поток коллектора, который ничто не переподключает. Это
  **не вызвано разделением** — проблема существовала раньше, — но разделение становится
  первым развёртыванием, где посредник будет активно закрывать неактивные соединения, и
  именно здесь этот пробел начинает стоить данных. Цикл переподключения с backoff на стороне
  коллектора — **предварительное условие** для признания этого ingress готовым к production.
- **Минус / компромиссы:** два load balancer означают две почасовые платы и два
  независимых счётчика capacity units; вместе они определяют основную часть постоянного
  месячного минимума небольшого развёртывания. Это реальная регулярная цена за сохранение
  обоих факторов допуска внутри процесса.
- **Минус и требование к сборке, а не примечание:** для **target groups типа IP с
  протоколом TCP или TLS сохранение IP-адреса клиента по умолчанию отключено** — а задачи
  в управляемой container runtime являются IP targets. При сохранении значения по
  умолчанию каждое соединение коллектора приходит в бинарник с частным адресом load
  balancer в качестве source address. Всё, что выводится из адреса, — audit records,
  rate limits, списки разрешённых адресов — с первого дня было бы незаметно неверным.
  Ingress не завершён, пока либо не включён `preserve_client_ip.enabled`, либо бинарник
  не разбирает Proxy Protocol v2 до handshake. Включение сохранения также означает, что
  security group целевого сервиса видит адреса клиентов, а не адрес load balancer;
  network design должен это учитывать.
- **Нейтрально / дальнейшие действия:** какой из двух механизмов восстанавливает source
  address, решит этап реализации, но **выбор должен быть сделан и протестирован, а не
  унаследован из значения по умолчанию**. Критерий приёмки — тест, подтверждающий, что
  записанный source address совпадает с адресом коллектора.

## Почему альтернативы были отклонены

- **A (один L4 load balancer)** — отклонён для *публичной* плоскости, но не для плоскости
  коллекторов. Он дешевле и ближе всего к self-hosted топологии, однако API control plane
  лишился бы управляемых сертификатов, WAF и маршрутизации по host/path, а продукту в
  итоге пришлось бы заново реализовать на L7 то, что уже предоставляет edge. Половина
  варианта A с коллекторами — ровно то, что сохраняет вариант B.
- **C (управляемый mutual TLS на L7)** — отклонён, потому что он **перемещает границу
  доверия**. В режиме verify edge проверяет сертификат, а приложение получает уже
  подтверждённый запрос; в режиме passthrough цепочка сертификатов приходит в header
  `X-Amzn-Mtls-Clientcert`. В обоих случаях транспортный барьер перестаёт применяться
  продуктом и становится утверждением другого компонента — ровно той подменой, проверяемость
  которой этот продукт призван обеспечивать; кроме того, до режима отказа, при котором любой
  имеющий прямой доступ к target может подделать header, достаточно одной ошибки сетевой
  конфигурации. Управляемый trust store со списками отзыва даёт настоящее эксплуатационное
  преимущество, которого продукт сейчас вообще не имеет для сертификатов коллекторов: он
  загружает CA и выполняет обычную проверку X.509 без проверки CRL или OCSP. Если управляемый
  отзыв когда-либо перевесит непосредственное завершение TLS, это потребует **нового ADR**,
  а не поправки к этому.
