# ADR-0013: PDP авторизации — встроенный Cedar + адаптер OPA-over-HTTP

- **Status:** accepted (только ограничение, в пределах стыка `auth.PolicyEvaluator`,
  созданного этой записью) — **изменено ADR-0019 (2026-06-15)**, которая убирает
  базовый permit: правило permit оператора, которое этот оверлей молча нейтрализовал,
  теперь действительно предоставляет доступ, а сам Cedar перенесён в отдельный стык
  как положительный движок грантов с областью действия. Политики только с forbid не
  затронуты; формулировки «никогда не расширять» в разделах о контексте и факторах
  решения ниже в таком прочтении отменены — см. поправку в конце.
- **Date:** 2026-06-04
- **Deciders:** Fran Olivares
- **References:** NHI/MCP-auth contract; изменено ADR-0019 (гранты Cedar с областью действия)

## Контекст и постановка проблемы

Помимо RBAC, платформе нужна точка принятия решений по политикам (PDP) для авторизации на
основе атрибутов. Организации различаются: одни хотят самодостаточный движок, у других уже
есть инфраструктура (estate) OPA. PDP никогда не должна *расширять* доступ — только
ограничивать.

## Факторы, определяющие решение

- Работать самодостаточно (единый бинарный файл, air-gap) без внешнего сервиса политик.
- Вписываться в существующее развёртывание OPA, если оно есть у оператора.
- Инвариант «только ограничение»: политика может запретить, но никогда не предоставить
  доступ сверх RBAC.

## Рассмотренные варианты

- **Оба:** встроенный Cedar (основной, на чистом Go) **и** адаптер OPA-over-HTTP за
  единым стыком, выбираемые оператором.
- **Только Cedar.**
- **Только OPA.**

## Итоговое решение

Выбранный вариант: **оба, за единым стыком `PolicyEvaluator`**. **Cedar** — встроенная
основная PDP на чистом Go; доступен адаптер **OPA-over-HTTP**; оператор выбирает движок
через `OLIVARES_PDP_ENGINE = cedar | opa | none`. Стык ABAC **только ограничивает** (он
применяется по конъюнкции (AND) с RBAC и никогда не расширяет). Инвариант «только
ограничение» проверяется сквозными (end-to-end) тестами.

### Последствия

- **Плюсы:** самодостаточность по умолчанию (Cedar, без sidecar); вписывается в
  инфраструктуру (estate) OPA при необходимости; один стык, два движка.
- **Минусы / компромиссы:** нужно сопровождать два адаптера; усиление защиты транспорта
  для пути OPA (например, mTLS до sidecar) — документированное расширение, ещё не
  завершённое.
- **Нейтрально:** `none` отключает слой ABAC, оставляя RBAC по принципу deny-by-default.

## Почему альтернативы были отклонены

- **Только Cedar** — исключает организации, стандартизированные на OPA.
- **Только OPA** — навязывает внешний сервис политик каждой установке, нарушая поведение
  по умолчанию: самодостаточность / air-gap.

## Поправка (2026-06-15, ADR-0019)

*(Изменяющее решение датировано 2026-06-15; эта отметка добавлена 2026-08-17,
когда проверка реестра решений обнаружила две записи, подписанные с интервалом в
одиннадцать дней и не связанные указанием приоритета. Текст выше не переписывается.)*

**Что больше не верно в написанном виде.** Утверждения из контекста *«PDP никогда
не должна расширять доступ — только ограничивать»* и из факторов решения *«политика
может запретить, но никогда не предоставить доступ сверх RBAC»* читаются как
утверждения обо **всём решении авторизации** и о **Cedar**. После **ADR-0019** такое
прочтение обоих утверждений неверно: Cedar повышен из оверлея только для запретов до
трёхзначного, учитывающего область действия движка **грантов**, а неявный базовый
`permit`, делавший решение Cedar только ограничивающим, удалён; теперь явно заданный
`permit` действительно предоставляет доступ.

**Что верно вместо этого.** Инвариант «только ограничение» сохраняется **в пределах
стыка, созданного этой записью**: `auth.PolicyEvaluator` по-прежнему выполняется после
RBAC и может только дополнительно ограничивать (`core/auth/authorizer.go:100-104`).
Положительный грант находится в **другом, новом** стыке `auth.ScopedAuthorizer`,
подключённом **рядом** с deny-оверлеем, а не внутри него; Authorizer сочетает их как
`Allow = (RBAC ∨ Grant) ∧ ¬Forbid ∧ ¬deny-overlay`
(`core/auth/authorizer.go:157-163`, алгебра в `:161` и `:200`). Deny-by-default,
приоритет forbid над permit и fail-closed при ошибке сохраняются; развёртывание без
заданных грантов принимает те же решения, что и при этой записи. Остальное остаётся
в силе: два движка за одним стыком и селектор
`OLIVARES_PDP_ENGINE = cedar | opa | none` — поставляемое поведение
(`cmd/olivares/wire.go:994-1018`).

**Где находится текущее решение.** `docs/adr/0019-cedar-scoped-grants.md`
(accepted, 2026-06-15, Fran Olivares), которое явно ссылается на эту запись. Читатель,
цитирующий только этот ADR — тот, к которому ведёт термин *ABAC*, — может заключить,
что поставляемый путь положительных грантов нарушает подписанное решение. Это не так:
он следует ADR-0019.
