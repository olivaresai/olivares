# ADR-0005: Встроенный SQLite по умолчанию, Postgres + RLS для масштабирования

- **Status:** accepted
- **Дата:** 2026-06
- **Принявшие решение:** Fran Olivares
- **Ссылки:** реестр решений по стеку (T4); проектирование модели данных

## Контекст и постановка задачи

Control plane хранит мультитенантную модель данных (граф доступа — это *представление
(view)* поверх неё). Он должен работать как single-binary без зависимостей для
небольших / air-gapped установок, но при этом масштабироваться до многохостовых,
мультитенантных развёртываний.

## Движущие факторы решения

- Ноль внешних зависимостей для пути single-binary / air-gap.
- Сильная мультитенантная изоляция при масштабировании.
- Отсутствие CGO, чтобы сохранить чистый Go-статический бинарник.

## Рассмотренные варианты

- **SQLite (чистый Go) → Postgres + row-level security.**
- **Графовая база данных** (Neo4j, Dgraph) для графа доступа.

## Принятое решение

Выбранный вариант: **встроенный SQLite** (`modernc.org/sqlite`, чистый Go, без CGO) для
одного узла и air-gap; **Postgres** (через `pgx`) с **row-level security** по ключу
`tenant_id` для многохостовых, масштабируемых и мультитенантных развёртываний. Граф
доступа моделируется как **представление (view) поверх общей модели данных**, а не как
отдельное хранилище.

### Последствия

- **Хорошо:** single-binary не требует установки базы данных; та же модель
  масштабируется до Postgres с изоляцией через RLS по тенантам.
- **Плохо / компромиссы:** нужно поддерживать два бэкенда хранения; корректность RLS
  необходимо тестировать (она тестируется — под принудительным RLS в CI).
- **Нейтрально:** графу доступа не нужен специальный графовый движок, потому что это
  представление (view).

## Почему альтернативы были отклонены

- **Графовая база данных** — тяжела для self-host и избыточна: граф доступа — это
  представление поверх реляционной модели, а не нагрузка, требующая выделенного
  графового движка.
