# ADR-0019: Cedar как движок позитивных, ограниченных по области грантов (а не overlay только-запретов)

- **Status:** accepted
- **Date:** 2026-06-15
- **Deciders:** Fran Olivares
- **References:** ADR-0013 (PDP — Cedar + OPA)

## Контекст и постановка проблемы

ADR-0013 разместил Cedar за швом `auth.PolicyEvaluator` как **overlay только-запретов**:
неявный базовый `permit(principal, action, resource)` компилировался перед политикой оператора, так
что решение Cedar могло быть только `forbid` (ограничением). Авторизация поэтому была **плоской на
уровне арендатора** — встроенный RBAC выдавал разрешение на весь арендатор, и политика могла лишь
сузить его. Не было способа выразить **позитивный, ограниченный по области грант**: «этот
администратор может управлять агентами только в рабочей области X», «зрители могут читать ресурсы
только под папкой Y», «эта роль может писать в группу агентов `payments`». Плоскость скоупинга
(workspace → agent-group → agent → resource/folder) моделировала дерево, но ничто не *обеспечивало*
гранты вдоль него; access map лишь *наблюдала* (`AccessEdge.Permitted` = «не известно как
разрешённое»).

## Движущие факторы решения

- Выразить позитивные гранты, ограниченные по дереву (workspace, agent-group, поддерево
  ресурсов) и по условиям (модель, чувствительность, AAL) — обеспеченные на реальном пути.
- Сохранить гарантии deny-overlay и deny-by-default, установленные ADR-0013 (forbid по-прежнему
  переопределяет; отсутствующий грант по-прежнему запрещает).
- Не реализовывать разрешение иерархии/членства вручную — использовать формально верифицированный
  движок, который моделирует его нативно.
- Обратная совместимость: развёртывание без авторских грантов должно решать ровно как раньше и
  ничего не платить на горячем пути.

## Результат решения

**Поднять встроенный движок Cedar из overlay только-запретов до трёхзначного, осведомлённого об
области движка грантов, за НОВЫМ швом `auth.ScopedAuthorizer` рядом с (а не внутри) deny-overlay.**

1. **Трёхзначное решение, без хака с базовым permit.** `Authorize` в cedar-go работает по принципу
   deny-by-default и forbid-переопределяет-permit, а его `Diagnostic.Reasons` именует определяющие
   политики. Это восстанавливает нужный Authorizer эффект из единственного вычисления: `Allow` →
   **Grant**; `Deny` с reasons → **Forbid**; `Deny` без reasons → **Abstain** (deny-by-default).
   Базовый permit из ADR-0013 удалён — `permit` теперь действительно выдаёт грант, `forbid`
   по-прежнему ограничивает, а пустая/нерелевантная политика воздерживается, так что решение RBAC
   остаётся в силе (инвариант обратной совместимости).

2. **Алгебра Authorizer становится** `Allow = (RBAC ∨ Grant) ∧ ¬Forbid ∧ ¬deny-overlay`.
   Движок со скоупами выполняется первым (forbid замыкает накоротко, переопределяя RBAC и любой
   грант); база — это RBAC-грант на уровне арендатора ИЛИ позитивный ограниченный грант; нативный
   движок ABAC + любой внешний PDP затем сужают его (эшелонированная защита). Deny-by-default и
   fail-closed сохранены; nil-движок скоупов сводит Authorizer к его поведению из ADR-0013.

3. **Авторитет грантов — ЭТО авторская политика Cedar для каждого арендатора** (поверхность
   авторинга политик), теперь компилируемая в режиме грантов. Движок разрешает родословную
   *истинного* ресурса запроса (читаемую из хранилища по entity id — неподделываемо) в граф
   сущностей Cedar, чьи `Parents` кодируют вложенность, так что транзитивный `in` Cedar выполняет
   обход иерархии. **Мы не добавляли отдельное хранилище структурированных строк грантов**:
   структурированный/консольный авторинг грантов, который *проецируется в* Cedar, — это забота
   слоя структурированного авторинга; движок со скоупами потребляет политику и обеспечивает её.

4. **Гранты только на уровне арендатора; глобальные env Cedar и OPA остаются только-запретами.**
   Слишком широкий глобальный *forbid* лишь запрещает (безопасно); слишком широкий глобальный
   *permit* выдал бы грант сквозь арендаторов (небезопасно). Эта асимметрия решающая: позитивные
   гранты живут в авторской политике конкретного арендатора (которую движок ключует по арендатору),
   тогда как общесистемные env Cedar (`OLIVARES_PDP_*`) и OPA остаются overlay только-ограничений.

### Последствия

- **Хорошо:** ограниченная авторизация корпоративного класса (workspace/agent-group/folder/model/
  sensitivity/AAL), обеспечиваемая в узком месте REST + gRPC; верифицированный движок разрешает
  иерархию/членство; обратная совместимость и deny-by-default сохранены; горячий путь ничего не
  платит, пока арендатор не подключит гранты (движок воздерживается до любого чтения хранилища).
- **Плохо / компромиссы:** арендатор с включёнными грантами платит небольшое, гейтированное чтение
  хранилища для разрешения области сущности на запросах уровня сущности (кэш области на арендатора
  — задокументированное продолжение); условия дерева областей разрешаются только относительно
  живой иерархии в активированном движке, а не в сухом прогоне авторинга.
- **Изменение поведения (задокументировано):** правило оператора `permit`, которое overlay
  ADR-0013 молчаливо нейтрализовал, теперь ВЫДАЁТ грант. Политики, состоящие только из forbid, не
  затрагиваются.

## Почему альтернативы были отвергнуты

- **Отдельная схема структурированных строк грантов в движке со скоупами** — дублирует собственную модель политик
  и разрешение иерархии Cedar; верифицированный движок уже выражает гранты как политики над графом
  сущностей. Структурированный авторинг принадлежит слою структурированного авторинга, проецируясь в Cedar, который движок уже
  потребляет.
- **Одна политика Cedar, генерируемая на грант** — не масштабируется (рост набора политик, churn
  при каждом редактировании гранта); шаблонные политики над разрешённым графом сущностей позволяют
  одному правилу покрыть целую workspace/группу/поддерево.
- **Сделать глобальный env Cedar способным выдавать гранты** — забытая защита по арендатору на
  глобальном permit выдаёт грант сквозь арендаторов. Гранты ограничены политикой конкретного
  арендатора.
