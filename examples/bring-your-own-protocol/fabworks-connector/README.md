# acme.fabworks-erp

An Olivares AI **content-source** connector, generated by
`olivares connector init --template content-source`, then filled in for the
fictional FabWorks ERP protocol.
It serves documents and ACL references through `sdk.ContentSource` for governed
knowledge ingestion.

Declared governance surfaces:
- `knowledge.document`

The `FABWORKS-FILL` markers in `fabworkserp.go` show the small diff from the
generated scaffold: the ERP JSON protocol client plus live delta and ACL
refresh support.

**License:** this repository is yours, and so is the license choice. The
scaffold seeds `Apache-2.0` SPDX headers — recommended for ecosystem
compatibility with the Apache-2.0 SDK — but it is your decision: put your name
in the `SPDX-FileCopyrightText` lines and add a matching `LICENSE` file.

## Build

```sh
go mod tidy   # first time (materializes go.sum for the plugin dependency tree)
go build ./...
```

`go.mod` carries `replace` directives pointing at the local SDK checkout the
scaffold was given; swap them for tagged versions once the first public
`sdk` tags are published.

## Test

```sh
go test ./...
```

`fabworkserp_test.go` proves the full lifecycle the engine drives (Open →
List → Fetch → DeltaList → FetchACL → Close) against the local FabWorks ERP
fixture.

Run the standalone boundary check too:

```sh
./scripts/check-boundary.sh
```

A connector must never link the upstream AGPL engine module — only the
Apache-2.0 SDK. The script checks the real `go list -deps` build graph; it is
the same boundary the upstream repo enforces in its CI. Run it in **your** CI
on every push.

## Sign

```sh
go build -o acme-fabworks-erp ./cmd/...
```

The binary serves the connector over gRPC (hashicorp/go-plugin); the engine
launches and supervises it. The connector code is identical in-process and
out-of-process.

Operators only admit plugins they can verify. Attest the binary with SLSA
provenance — key-based:

```sh
cosign generate-key-pair
cosign attest-blob --key cosign.key --type slsaprovenance1 \
  --predicate predicate.json --bundle acme-fabworks-erp.sigstore.json acme-fabworks-erp
```

or keyless (ambient OIDC identity, e.g. your CI — no key to manage):

```sh
cosign attest-blob --type slsaprovenance1 \
  --predicate predicate.json --bundle acme-fabworks-erp.sigstore.json acme-fabworks-erp
```

`predicate.json` is your SLSA provenance predicate (who built what, from which
commit). Never commit `cosign.key` — `.gitignore` already excludes it.
Alternative: GitHub artifact attestations (`actions/attest-build-provenance`
in your release workflow, verifiable with `gh attestation verify`).

## Register

Either a GitHub release carrying the binary, its sha256 and the
`.sigstore.json` bundle, or an OCI registry:

```sh
oras push ghcr.io/<org>/acme-fabworks-erp:0.1.0 acme-fabworks-erp acme-fabworks-erp.sigstore.json
```

Register the plugin in the operator-owned sources config, pinned by digest and
admitted by the root `connector_trust` policy.

## Operate

The operator wires the plugin into governed knowledge through the `documents`
block in the file named by `OLIVARES_SOURCES_CONFIG`:

```json
{
  "connector_trust": {
    "trusted_keys": ["-----BEGIN PUBLIC KEY-----\n<contents of acme's cosign.pub>\n-----END PUBLIC KEY-----\n"],
    "allowed_predicates": ["https://slsa.dev/provenance/v1"]
  },
  "documents": [
    {
      "name": "fabworks-erp",
      "plugin": {
        "path": "/opt/olivares/connectors/acme-fabworks-erp",
        "sha256": "<hex sha256 of the binary>",
        "bundle": "/opt/olivares/connectors/acme-fabworks-erp.sigstore.json"
      },
      "config": { "base_url": "https://content.example", "token": "store:fabworks-erp-token" }
    }
  ]
}
```

The knowledge module opens the source after the secret store is available and
then drives `List` and `Fetch` during ingest. If you later implement
`DeltaContentSource`, the plugin transport auto-declares `content.delta`. This
example already implements that optional interface, so delta sync and ACL-only
refresh are available to hosts that observe the capability.

`trusted_keys` carries the PEM public-key **material** inline (JSON-escaped),
never a file path. For keyless signing the gate verifies against the Fulcio CA
root, so it needs a trust anchor in `trusted_roots` **plus** the identity pins:

```json
"trusted_roots": ["-----BEGIN CERTIFICATE-----\n<Fulcio root PEM>\n-----END CERTIFICATE-----\n"],
"allowed_identities": ["https://github.com/<org>/<repo>/.github/workflows/release.yml@refs/tags/*"],
"allowed_issuers": ["https://token.actions.githubusercontent.com"]
```

`allowed_identities` and `allowed_issuers` go together (set both or neither);
the gate refuses an enforcing policy that has neither a `trusted_root` nor a
`trusted_key`, so the Fulcio root is mandatory for keyless.

## Governed by construction

> Enforcement is engine-side by construction. A connector never links
> governance code, and a connector cannot opt out.

You write zero governance code in this connector. The engine keys controls on
the configured source identity (`source_type`, `source_ref`), applies scoping,
model access, content controls and audit, and treats `Descriptor.Surfaces` as
catalog/admission metadata only — never an enforcement input.
