# GitOps consumption — Olivares AI control plane

The Helm chart in `../helm/olivares` **will be published** as an **OCI
artifact** to `ghcr.io/olivaresai/charts` once
`../../.github/workflows/release-chart.yml` runs — it publishes only on a
human-pushed `chart-v*` tag (it never auto-publishes), so until that tag is cut the
registry path is **empty** and these manifests have no chart to pull yet. This
directory is the **consumption contract**: ready-to-adapt manifests for the three
mainstream GitOps engines, all targeting that one signed chart once it is published.

| Engine | Files | Entry point |
|---|---|---|
| **Argo CD** (app-of-apps) | `argocd/app-of-apps.yaml`, `argocd/application.yaml` | `kubectl apply -n argocd -f argocd/app-of-apps.yaml` |
| **Flux** | `flux/helmrepository.yaml`, `flux/helmrelease.yaml` | `kubectl apply -f flux/` |
| **Kustomize** | `kustomize/kustomization.yaml` + `kustomize/overlays/prod/` | `kustomize build --enable-helm kustomize/overlays/prod` |
| **Flat manifest** (no Helm) | `../manifests/install.yaml` | `kubectl apply -n olivares-system -f ../manifests/install.yaml` |

The first three are **templates**: pin the chart version and the engine image
**digest** before you roll them out (see *Digest pinning* below). The image digests
committed here are an obvious all-zero `sha256:0000…` placeholder — replace them.

The **flat manifest** (`../manifests/install.yaml`) is the fourth path for an operator
with only `kubectl` — the common air-gapped / locked-down case — needing **neither
Helm nor the Kustomize inflation generator** (`--enable-helm`) on PATH. It is the
*generated* `helm template` output of the same chart with safe single-node defaults
(sqlite, 1 replica, collectors/PDB/NetworkPolicy/ServiceMonitor off), so it stays in
lockstep with the chart: it is regenerated by `task manifests:gen` (never hand-edited)
and CI fails if it drifts (the `manifests` job re-renders and `git diff --exit-code`s
it — the OpenGitOps *declarative · versioned-and-immutable* guarantee). For a real
rollout, pin the image to a digest as below.

## OpenGitOps 1.0 alignment

These manifests implement the four [OpenGitOps v1.0.0](https://opengitops.dev/)
principles end to end:

1. **Declarative** — the entire desired state (chart version, values, image digest,
   namespace) is expressed declaratively in these YAML manifests; nothing is
   `kubectl edit`-ed imperatively.
2. **Versioned and immutable** — desired state is pinned: a chart **SemVer**
   (`targetRevision` / `chart.spec.version` / `helmCharts[].version`) and an
   **immutable image digest**, not a floating tag or range. The state lives in Git
   (Argo `app-of-apps`/Kustomize) or in the immutable OCI artifact (the chart
   itself), so a rollback is a revert to a prior pinned version.
3. **Pulled automatically** — Argo CD and Flux **pull** the chart from the OCI
   registry on their own reconcile interval; nothing is pushed into the cluster by
   a CI runner with cluster credentials.
4. **Continuously reconciled** — the agent (Argo CD / Flux controller) runs in the
   cluster and continuously reconciles live state toward the pinned desired state.
   Drift self-heals when `selfHeal`/auto-sync is enabled (left **opt-in** for the
   workload itself — see below).

## Argo CD (app-of-apps)

`application.yaml` is one Argo CD `Application` (`argoproj.io/v1alpha1`) whose
`source` is the OCI chart (`repoURL: ghcr.io/olivaresai/charts`, `chart:
olivares`). `app-of-apps.yaml` is the parent that tracks this
directory in Git and adopts the child Application(s) — bootstrapping then collapses
to applying one manifest:

```sh
kubectl apply -n argocd -f argocd/app-of-apps.yaml
```

The **child** workload sync is **manual by default** (no `automated:` block): a
security product's deploy is a reviewed action, not a silent auto-apply. The
**parent** auto-syncs only the *set of Application objects* (cheap, safe). Opt into
full continuous reconciliation by uncommenting `automated: { prune, selfHeal }` in
`application.yaml`.

## Flux

`flux/helmrepository.yaml` is a `HelmRepository`
(`source.toolkit.fluxcd.io/v1`, `type: oci`,
`url: oci://ghcr.io/olivaresai/charts`); `flux/helmrelease.yaml` is the
`HelmRelease` (`helm.toolkit.fluxcd.io/v2`) that pins the chart version and the
image digest:

```sh
kubectl apply -f flux/        # HelmRepository + HelmRelease
```

Flux can also **verify the chart's cosign signature before pulling** — the
supply-chain gate on the consumption side. Uncomment the `verify:` block in
`helmrepository.yaml` (keyless `matchOIDCIdentity` pinned to the publisher's
Fulcio identity).

## Kustomize

A base (`kustomize/kustomization.yaml`) + a `prod` overlay
(`kustomize/overlays/prod/`) that demonstrate namespace + image-digest pinning via
the Helm chart inflation generator (`helmCharts`). It requires `--enable-helm`
(and Helm on `PATH`):

```sh
kustomize build --enable-helm kustomize/overlays/prod
```

If your pipeline forbids the inflation generator, render the chart once
(`helm template`) and commit the manifests as a plain `resources:` base — both
shapes are valid Kustomize; the file's top comment documents the choice.

## Digest pinning (do this before production)

Pin the engine image by **digest**, never a bare tag — the air-gap / supply-chain
posture baked into `../helm/olivares/values.yaml` (`image.digest`
takes precedence over `image.tag`; `templates/_helpers.tpl` `olivares.image`):

```sh
# resolve the immutable digest for the appVersion this chart targets
# (Docker Hub is the official registry; the ghcr.io fallback carries the same digest):
crane digest docker.io/olivaresai/olivares:<appVersion>
#  -> sha256:<64-hex>
# fallback coordinate — identical digest, no anonymous-pull rate limit:
crane digest ghcr.io/olivaresai/olivares:<appVersion>
```

Set that into `image.digest` (and leave `image.tag` empty) in whichever manifest
you use. Verify the **chart** signature too (cosign over the OCI manifest, and/or
the Helm `.prov`) before trusting it — see `../helm/README.md`.

## Where this sits in the product

This directory is the **deploy / consumption** side. Two sibling pieces complete
the GitOps story:

- **Health, in the customer's GitOps tool** — `../argocd/` ships a Lua health
  check (`resource_customizations/olivares.ai/ControlPlane/health.lua`) so the
  customer's **Argo CD** reports the health of an Olivares control plane it
  manages (the `olivares.ai/ControlPlane` CRD), instead of a custom resource
  stuck on `Progressing`.
- **Observation, back into the control plane** — `../../connectors/argocd` and
  `../../connectors/flux` are read-first source connectors that parse **exported**
  Argo CD `Application` / Flux `Kustomization`+`HelmRelease` manifests and emit the
  GitOps reconciliation posture (sync / health / drift) as findings onto the event
  bus. They never trigger a sync (acting on a deployment is module VII,
  human-in-the-loop-gated). The GitOps loop is **closed for observation, never for
  action.**
